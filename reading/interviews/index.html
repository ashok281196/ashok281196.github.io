Chapter I

SLAM & State Estimation

Cartographer, GPS-denied return-to-home, EKF/UKF/Factor Graphs, multi-rate sensor fusion, and visual degradation under occlusion are core state-estimation territory. Frame your answers with rigorous mathematical formulations and real-world failure mode analysis.

1.1

Walk me through a SLAM pipeline like Cartographer — scan matching, submaps, loop closure.

rating — near-certain

Google Cartographer decouples state estimation into a local real-time front-end and a global asynchronous back-end. The front-end accumulates range scans into local grid submaps using high-frequency Ceres-based non-linear scan matching, while the back-end optimizes a pose graph of submaps using branch-and-bound loop closure verification.

The fundamental architectural insight of Cartographer is that short-term local drift is small enough to build locally consistent submaps, while global drift over long trajectories is corrected asynchronously by pose graph optimization over finished submap nodes.

1. Local Front-End (Scan-to-Submap Matching)

Incoming LiDAR scans $P = \{p_i\}_{i=1}^K$ in frame coordinates are mapped into the local submap coordinate frame via rigid transform $T_{\xi} = (R_\theta, t)$ parameterized by pose $\xi = (p_x, p_y, \theta)$. The scan matcher solves a non-linear least squares problem minimizing grid probability residuals using Ceres Solver:

$$\arg\min_{\xi} \sum_{i=1}^{K} \left( 1 - M_{\text{smooth}}(T_{\xi} \cdot p_i) \right)^2 + w_{\text{odom}} \| \xi \ominus \xi_{\text{odom}} \|_{\Sigma_{\text{odom}}}^2$$

where $M_{\text{smooth}}(x)$ is a bicubicly-interpolated grid cell probability value. To prevent local minima divergence during aggressive motion, initial guess $\xi_{\text{odom}}$ is provided by high-rate IMU pre-integration or wheel odometry.

// Ceres Cost Function for 2D Scan Matching against Grid Submap
struct ScanMatcherCostFunction {
    ScanMatcherCostFunction(const SensorScan& scan, const ProbabilityGrid& grid)
        : scan_(scan), grid_(grid) {}

    template <typename T>
    bool operator()(const T* const pose, T* residual) const {
        T x = pose[0], y = pose[1], theta = pose[2];
        for (size_t i = 0; i < scan_.points.size(); ++i) {
            T px = x + cos(theta) * scan_.points[i].x - sin(theta) * scan_.points[i].y;
            T py = y + sin(theta) * scan_.points[i].x + cos(theta) * scan_.points[i].y;
            T probability = grid_.GetBicubicProbability(px, py);
            residual[i] = T(1.0) - probability;
        }
        return true;
    }
    const SensorScan& scan_;
    const ProbabilityGrid& grid_;
};

2. Submap Generation & Lifecycles

A submap starts empty as a probability grid (typically $5\text{cm}$ resolution). Each accepted scan updates grid probability via odds ratio updates $O(x) = M(x)/(1-M(x))$: $O_{\text{new}}(x) = O_{\text{old}}(x) \cdot O_{\text{hit/miss}}$. To ensure computational tractability, a submap transitions to "finished" once $N_{\text{scans}} \approx 100-200$ frames are inserted. At any time, two submaps are concurrently active: one accumulating scans and one being finalized.

3. Global Back-End & Branch-and-Bound Loop Closure

When a submap is finalized, it becomes a node in the global pose graph. Cartographer searches for loop closure constraints by matching recent scans against all historic finalized submaps within a search window $W$. To make global grid search real-time without GPU acceleration, it employs Real-Time Correlative Scan Matching accelerated by a Branch-and-Bound (B&B) tree search on a multi-resolution grid pyramid:

  • Grid Pyramid: Precomputes coarse grids where cell value $M_{\text{coarse}}(x) = \max_{y \in \text{window}} M(y)$.
  • Bounding: The score of any scan in a coarse cell bounds the maximum achievable score of all child cells in the fine grid. If $Score_{\text{coarse}} < Score_{\text{best\_known}}$, the entire branch is pruned.

4. Pose Graph Optimization with Huber Robust Loss

Upon accepting candidate loop closure relative transforms $T_{i,j}$, Ceres minimizes the global graph cost function:

$$\arg\min_{\chi} \sum_{i} \| \xi_i \ominus (\xi_{i-1} \cdot \Delta\xi_{i-1,i}) \|_{\Sigma_{\text{local}}}^2 + \sum_{i,j} \rho\left( \| \xi_i \ominus (\xi_j \cdot T_{i,j}) \|_{\Sigma_{\text{loop}}}^2 \right)$$

where $\rho(r)$ is the Huber Robust Loss function ($\rho(r) = r^2$ for $|r|\le \delta$, $2\delta|r|-\delta^2$ for $|r|>\delta$). The Huber loss down-weights erroneous loop closure constraints (false positives from perceptual aliasing), preventing map destruction.

A single false loop closure accepted by the back-end will bend the entire global map permanently. Always tune loop closure verification to be ultra-conservative: require geometric verification score > 0.85 and Huber loss cutoff $\delta = 0.1\text{m}$.
1.2

How would you handle GPS-denied return-to-home on a drone?

rating — near-certain

A robust GPS-denied Return-To-Home (RTH) architecture relies on Visual-Inertial Odometry (VIO) keyframe graph navigation rather than absolute global coordinates. The drone records an active $SE(3)$ pose graph during outbound flight and retraces it during emergency return.

Do not trust absolute coordinates when GPS drops out. Absolute coordinates compound drift continuously. Retracing a recorded visual keyframe graph guarantees that drift shrinks as the drone approaches its launch origin because it revisits known visual features.

1. System State Architecture & Data Structure

During normal outbound flight (GPS healthy or VIO nominal), the autonomy stack logs a lightweight topological pose graph at $2\text{Hz}$:

struct KeyframeNode {
    uint32_t id;
    double timestamp;
    Eigen::Matrix4d T_world_robot; // SE(3) Pose
    std::vector<cv::KeyPoint> keypoints;
    cv::Mat descriptors;           // DBoW2 / NetVLAD feature vector
    pcl::PointCloud<pcl::PointXYZ>::Ptr local_point_cloud;
};
std::vector<KeyframeNode> trajectory_graph;

2. Failover State Machine & Traversal

Upon triggering GPS loss / link disconnection:

  1. State Transition: Switch EKF3 input from GPS position measurements to tight-coupled VIO (stereo RealSense D435i + onboard IMU) producing relative pose updates $\Delta T \in SE(3)$ at $30\text{Hz}$.
  2. Heading Inversion: Command a $180^\circ$ yaw rotation in place while maintaining altitude via laser/baro altimeter.
  3. Path Inversion & Smoothing: Reverse the keyframe trajectory list. Apply B-spline interpolation across keyframe positions to generate smooth velocity targets $v_{\text{cmd}}(t)$ for the local trajectory planner (DWA / TEB).
  4. Visual Drift Correction (Relocalization): As the drone flies backward along the flight path, run feature matching (ORB/SuperPoint + RANSAC PnP) against stored keyframe descriptors. Detect re-visited keyframes to apply instant pose corrections, eliminating dead-reckoning integration drift.
1.3

EKF vs. UKF vs. factor-graph optimization — how do they differ, and why did ArduPilot pick EKF?

rating — likely

State estimation algorithms trade off computational complexity, non-linear representation accuracy, and smoothing capabilities across past states.

1. Extended Kalman Filter (EKF)

EKF linearizes non-linear dynamics $f(x, u)$ and measurement models $h(x)$ using first-order Taylor series expansions around the current estimate state $\hat{x}_k$ via Jacobian matrices $F_k = \frac{\partial f}{\partial x}\big|_{\hat{x}_{k-1}}$ and $H_k = \frac{\partial h}{\partial x}\big|_{\hat{x}_k^-}$:

$$\text{Prediction: } \hat{x}_k^- = f(\hat{x}_{k-1}, u_k), \quad P_k^- = F_k P_{k-1} F_k^T + Q_k$$ $$\text{Update: } K_k = P_k^- H_k^T \left( H_k P_k^- H_k^T + R_k \right)^{-1}, \quad \hat{x}_k = \hat{x}_k^- + K_k \left( z_k - h(\hat{x}_k^-) \right), \quad P_k = (I - K_k H_k) P_k^-$$

Limitation: Unimodal Gaussian assumption. Once a state update is finalized at step $k$, past estimates cannot be revised upon receiving out-of-order measurements or loop closures.

2. Unscented Kalman Filter (UKF)

UKF avoids computing analytical Jacobians. It deterministically samples $2L+1$ Sigma Points $\chi_i$ around state mean $\mu$ with covariance $P$ using the Unscented Transform ($\gamma = \sqrt{L + \lambda}$):

$$\chi_0 = \mu, \quad \chi_i = \mu + \left(\sqrt{(L+\lambda)P}\right)_i, \quad \chi_{i+L} = \mu - \left(\sqrt{(L+\lambda)P}\right)_i$$

Sigma points are passed directly through the exact non-linear function $Y_i = f(\chi_i)$, capturing 2nd-order Taylor series terms. Compute cost scales as $\mathcal{O}(L^3)$ due to matrix square root (Cholesky decomposition) per update step.

3. Factor Graph Optimization (Smoothing / iSAM2)

Maintains a graph where nodes represent robot states $X = \{x_0, \dots, x_N\}$ and edges represent non-linear factor costs $f_k(X_k)$. Solves the full joint Maximum A Posteriori (MAP) inference via non-linear least squares:

$$X^* = \arg\min_{X} \sum_{k} \| h_k(X_k) - z_k \|_{\Sigma_k}^2$$

Using iSAM2 (incremental Smoothing and Mapping), factor graphs convert non-linear factors into a Bayes Tree, updating only affected variables during incremental steps, allowing past state revision upon loop closure.

4. Why ArduPilot Selected EKF3

ArduPilot runs its primary flight controller loop on STM32 microcontrollers (Cortex-M7 at $216\text{MHz}$). EKF3 maintains a 24-state vector (Position, Velocity, Quaternion Attitude, Gyro/Accel Biases, Earth Magnetic Field, Body Magnetic Field, Wind Velocity). The EKF prediction/update cycle completes in $<150\mu\text{s}$, fitting tightly within the $1\text{kHz}$ RTOS task loop. Factor graphs are computationally impossible on bare-metal MCU hardware due to dynamic memory requirements and unbounded optimization execution times.

ArduPilot EKF3 Layout
EKF3 uses multiple parallel EKF instances ("lanes") running on separate IMU hardware sensors. If one IMU vibrates excessively, EKF3 automatically switches to a healthier lane mid-flight.
1.4

How does vision-based state estimation degrade under occlusion or IR obstruction?

rating — likely

Visual-Inertial Odometry (VIO) degrades rapidly under optical occlusion, low texture, or IR oversaturation. Robust estimation architectures prevent filter divergence via Mahalanobis distance measurement gating and covariance inflation management.

1. Outlier Gating via Mahalanobis Distance

Before fusing an incoming visual landmark observation $z_k$, the estimator computes the residual covariance $S_k = H_k P_k^- H_k^T + R_k$ and innovation $\nu_k = z_k - h(\hat{x}_k^-)$. The squared Mahalanobis distance $d_M^2$ is evaluated against a Chi-Squared $\chi^2$ distribution gate threshold:

$$d_M^2 = \nu_k^T S_k^{-1} \nu_k < \chi^2_{\alpha, m}$$

If $d_M^2 > \chi^2$ (e.g., due to lens smudge or partial occlusion producing corrupted feature positions), the measurement is rejected instantly, preventing corrupted updates from pulling the state estimate off track.

2. Covariance Growth During Blind Dead-Reckoning

When complete visual dropout occurs (e.g., passing through smoke or optical sensor failure), the filter stops applying measurement update equations ($K_k = 0$). State propagation relies exclusively on IMU accelerometer and gyroscope integration:

$$P_{k+1} = F_k P_k F_k^T + Q_k$$

In the absence of correction updates $R_k$, the position uncertainty covariance $P_{pp}$ grows exponentially with time $t^3$ (due to double-integration of uncorrected accelerometer bias $b_a$).

3. Visual Relocalization & State Recovery Sequence

// Pseudocode: VIO Recovery State Machine
if (tracked_features_count < MIN_FEATURES_THRESHOLD) {
    estimator_status = VIO_TRACKING_LOST;
    // Freeze visual updates, rely on IMU + Baro dead reckoning
    fuse_visual_updates = false;
} else if (estimator_status == VIO_TRACKING_LOST) {
    // Attempt 3D-2D PnP RANSAC alignment against keyframe map
    Eigen::Matrix4d T_recovery;
    if (solve_pnp_ransac(current_frame, keyframe_database, T_recovery)) {
        // Reset Error State EKF covariance and re-align state vector
        esekf.reset_attitude_and_position(T_recovery);
        fuse_visual_updates = true;
        estimator_status = VIO_NOMINAL;
    }
}
1.5

How do you fuse sensors at very different rates — IMU at 1kHz, camera at 30Hz, GPS at 5Hz?

rating — likely

Multi-rate sensor fusion requires an Error-State Kalman Filter (ESKF) coupled with a temporal circular buffer to handle asynchronous measurement latency without blocking high-rate prediction.

1. Error-State Kalman Filter Split

The state is split into true state $x$, nominal state $\tilde{x}$, and error state $\delta x$ ($x = \tilde{x} \oplus \delta x$):

  • Nominal State $\tilde{x}$ ($1\text{kHz}$): Propagated asynchronously by high-rate IMU readings via raw kinematic integration (non-linear manifold integration). No covariance calculations in this fast path.
  • Error State $\delta x$ (Asynchronous): Linearized error dynamics $\delta \dot{x} = F_{\text{err}} \delta x + w$. Covariance $P$ is updated only when lower-rate sensors arrive.

2. Delayed Measurement Handling via Ring Buffer

To fuse a camera measurement arriving at $t_{\text{now}}$ with timestamp $t_{\text{cam}} = t_{\text{now}} - 80\text{ms}$:

  1. Maintain a circular buffer of historical nominal states $\tilde{x}(\tau)$ and covariance matrices $P(\tau)$ for the past $200\text{ms}$.
  2. Retrieve stored state $\tilde{x}(t_{\text{cam}})$ and $P(t_{\text{cam}})$ corresponding to frame capture time.
  3. Compute innovation $\nu = z_{\text{cam}} - h(\tilde{x}(t_{\text{cam}}))$ and Kalman Gain $K$.
  4. Update error state $\delta x(t_{\text{cam}}) = K \nu$ and inject back into nominal state: $\tilde{x}_{\text{corrected}}(t_{\text{cam}}) = \tilde{x}(t_{\text{cam}}) \oplus \delta x(t_{\text{cam}})$.
  5. Re-propagate nominal state from $t_{\text{cam}}$ to $t_{\text{now}}$ using stored IMU readings in the buffer.

2.3

Global vs. local planners — what's the difference, and when do you re-plan?

rating — possible

Global and local planners operate on fundamentally different mathematical abstractions, search spaces, and time horizons.

1. Global Planner: Hybrid A* on $SE(2)$

Finds a globally optimal path from start to goal over the complete known map. Standard A* treats the robot as a point on a discrete 2D grid. Hybrid A* searches continuous 3D state space $(x, y, \theta)$, enforcing non-holonomic kinematic constraints (minimum turning radius $R_{\min}$ via Dubins/Reeds-Shepp curves):

$$f(n) = g(n) + h(n), \quad h(n) = \max\left( h_{\text{Reed-Shepp}}(n), h_{\text{2D-A*}}(n) \right)$$

2. Local Planner: Dynamic Window Approach (DWA)

Operates in velocity space $(v, \omega)$ at $20\text{Hz}$ within a rolling sensor window. Computes admissible velocity search space $V_r = V_s \cap V_a \cap V_d$ (where $V_s$ is maximum hardware velocity, $V_a$ is braking distance velocity limit, $V_d$ is acceleration limits). Evaluates candidate trajectories over horizon $\tau$ by maximizing objective function $G(v, \omega)$:

$$G(v, \omega) = \alpha \cdot \text{heading}(v, \omega) + \beta \cdot \text{dist}(v, \omega) + \gamma \cdot \text{velocity}(v, \omega)$$

3. Re-planning Triggers

  • Local Planner: Re-calculates velocity commands $(v, \omega)$ every control loop iteration ($20\text{Hz}-50\text{Hz}$) regardless of map changes.
  • Global Planner: Re-plans asynchronously when: (a) a new obstacle intersects the current global path within distance $D_{\text{check}}$, (b) goal pose moves, or (c) local planner reports progress stall for $T_{\text{stall}} > 3.0\text{s}$.

2.5

What is a costmap inflation layer, and why does it matter?

rating — possible

The inflation layer inflates obstacle boundaries by propagating costs outward from obstacle cells to ensure the planner accounts for the robot's physical footprint while treating the robot center as a point mass.

Mathematical Inflation Decay Function

For any cell at Euclidean distance $d$ from the nearest obstacle cell:

$$\text{Cost}(d) = \begin{cases} 254 (\text{LETHAL}), & \text{if } d \le r_{\text{inscribed}} \\ (C_{\text{inscribed}} - 1) \cdot e^{-\alpha \cdot (d - r_{\text{inscribed}})}, & \text{if } r_{\text{inscribed}} < d \le r_{\text{inflation}} \\ 0, & \text{if } d > r_{\text{inflation}} \end{cases}$$

where $r_{\text{inscribed}}$ is the radius of the robot's inscribed circle, $r_{\text{inflation}}$ is the maximum inflation radius, and $\alpha$ is the cost decay factor. Without inflation, global path planners route waypoints directly along obstacle edges, causing physical chassis collisions when turning.

3.2

Explain your 200kHz EtherCAT/CAN control loop — what makes that hard?

rating — near-certain · your strongest story

At a $200\text{kHz}$ sampling rate, the total timing budget per cycle is precisely **$5.0\mu\text{s}$**. Any CPU stall, cache miss, or dynamic allocation instantly causes deadline overrun.

1. 5.0 Microsecond Cycle Budget Breakdown

  • $0.0 - 1.0\mu\text{s}$: SPI / DMA Sensor Readout: Read raw gyro/encoder registers over high-speed SPI ($40\text{MHz}$) directly into MCU Tightly-Coupled Memory (ITCM/DTCM).
  • $1.0 - 3.0\mu\text{s}$: Control Math Execution: Execute floating-point PI/PD loop. Uses Cortex-M7 hardware single-cycle FPU instructions. Trigonometric calculations use lookup tables. Zero `malloc` calls.
  • $3.0 - 4.2\mu\text{s}$: Actuator Wrench / Motor Command Assembly: Format EtherCAT Process Data Object (PDO) or CAN-FD frame bytes. Write directly to peripheral registers.
  • $4.2 - 5.0\mu\text{s}$: Timing Headroom / Margin: Safety margin reserved for interrupt context switching.

2. Hardware Management: DTCM & Cache Invalidation

Standard MCU SRAM passes through L1 Data Cache, introducing non-deterministic cache-miss latencies ($20-50$ CPU cycles). We map the hot control loop memory directly into **Data Tightly-Coupled Memory (DTCM)** at address `0x20000000`, guaranteeing single-cycle zero-wait-state memory access bypass of cache controllers.

3.3

What is priority inversion, and how do you prevent it?

rating — likely

Priority Inversion occurs when a High-Priority Task ($T_H$) is indirectly blocked by a Medium-Priority Task ($T_M$) because $T_H$ is waiting on a mutex held by a Low-Priority Task ($T_L$). $T_M$ preempts $T_L$ (since $T_M > T_L$), extending $T_H$'s wait time indefinitely.

Priority Inheritance Protocol (PIP) Mechanism

Under PIP, when $T_H$ attempts to acquire a mutex currently held by $T_L$, the RTOS scheduler temporarily elevates the priority of $T_L$ to match $T_H$ ($\text{Priority}(T_L) \leftarrow \text{Priority}(T_H)$). $T_L$ executes without preemption by $T_M$, releases the mutex, and instantly reverts to its original low priority, allowing $T_H$ to acquire the mutex immediately.

3.4

CAN bus arbitration vs. EtherCAT synchronization — how do they differ?

rating — likely

CAN and EtherCAT solve fieldbus communication using fundamentally different physical and data-link layer protocols.

1. CAN 2.0 / CAN-FD CSMA/CR Arbitration

CAN is a multi-master broadcast bus using **Carrier Sense Multiple Access with Collision Resolution (CSMA/CR)**. Arbitration occurs bit-by-bit using dominant (`0`, driven low voltage) and recessive (`1`, high impedance) bus states. If Node A transmits CAN ID `0x100` (`00100000000`) and Node B transmits `0x104` (`00100000100`), at the 9th bit Node B sees dominant `0` while outputting `1`, loses arbitration silently, and stops transmitting, allowing Node A's frame to proceed without collision.

2. EtherCAT Distributed Clocks (DC) Synchronization

EtherCAT uses a Master-Slave ring topology with **Processing-on-The-Fly**. An Ethernet frame passes through hardware EtherCAT Slave Controller (ESC) ASICs, which extract and insert data within nanoseconds while the frame flows physically through the chip. **Distributed Clocks (DC)** synchronize all slave hardware timers to a master reference clock by measuring propagation delay $t_{\text{prop}}$ across nodes:

$$t_{\text{prop}} = \frac{(t_4 - t_1) - (t_3 - t_2)}{2}$$

This allows EtherCAT slaves to trigger PWM updates simultaneously with sub-microsecond jitter ($<100\text{ns}$).

3.6

Hard vs. soft real-time — where's the line in your stack?

rating — possible

The distinction between hard and soft real-time is defined by the utility function $U(t)$ when a task deadline $T_{\text{deadline}}$ is missed:

  • Hard Real-Time ($U(t) \to -\infty$ for $t > T_{\text{deadline}}$): Missing a deadline constitutes complete system failure (e.g., $200\text{kHz}$ motor commutation loop, EtherCAT DC frame synchronization, EKF IMU prediction step). Handled via dedicated RTOS tasks with high priorities and zero memory allocation.
  • Soft Real-Time ($U(t)$ degrades gracefully for $t > T_{\text{deadline}}$): Missing a deadline degrades system performance but causes no safety risk (e.g., GCS telemetry packet streaming, H.264 video bitrate encoding, UI rendering). Handled on Linux compute nodes using standard POSIX threads (`SCHED_OTHER`).

4.4

How do you synchronize clocks across robots and ground stations on a mesh network?

rating — possible

Synchronizing network clocks across distributed agents relies on PTP over wired backbones and GPS PPS over wireless mesh nodes.

1. PTP (IEEE 1588) over Wired Ethernet

PTP exchanges hardware-timestamped packets (`Sync`, `Follow_Up`, `Delay_Req`, `Delay_Resp`) to compute network offset $o$ and propagation delay $d$:

$$d = \frac{(t_2 - t_1) + (t_4 - t_3)}{2}, \quad o = \frac{(t_2 - t_1) - (t_4 - t_3)}{2}$$

Achieves sub-microsecond accuracy over low-jitter switches, but degrades over asymmetric wireless links.

2. GPS PPS (Pulse Per Second) for Wireless Swarms

Each robot captures the hardware GPS PPS square-wave edge on a micro-controller timer input pin, zeroing the local microsecond counter top-of-second with $<100\text{ns}$ absolute UTC alignment across all field assets.

Learning-Based Robotics

Bridging learning-based policies with real-time robotic systems requires handling multimodal action distributions and deterministic sim-to-real domain randomization.

6.1

What is one-shot / few-shot imitation learning, and how would you apply it to a cobot task?

rating — possible

One-shot imitation learning parameterizes robot trajectories using **Dynamic Movement Primitives (DMPs)**. A single kinesthetic human demonstration is encoded as a set of non-linear differential equations:

$$\tau \dot{v} = K (g - y) - D v + \left(g - y_0\right) f(x)$$

where $f(x) = \frac{\sum w_i \psi_i(x)}{\sum \psi_i(x)} x$ is a forcing function learned via linear regression over radial basis functions $\psi_i(x)$. Adaptations to new target object poses $g_{\text{new}}$ are executed analytically by updating goal parameters in real time without retraining network weights.

6.2

Where do diffusion models fit into robotics beyond image generation?

rating — possible

Diffusion Policies represent robot action distributions $p(a|o)$ as an iterative denoising process. Unlike Gaussian MLP policies which average multiple valid grasp trajectories into an invalid middle collision path, Diffusion Policies represent multimodal distributions effectively:

$$a^{k-1} = \frac{1}{\sqrt{\alpha_k}} \left( a^k - \frac{\beta_k}{\sqrt{1 - \bar{\alpha}_k}} \epsilon_\theta(a^k, o, k) \right) + \sigma_k z$$

To run real-time at $20\text{Hz}$, policies use **DDIM sampling** (reducing denoising steps from 100 to 5) coupled with TensorRT INT8 optimization on Nvidia Jetson Orin hardware.

6.3

rating — unlikely, but keep it ready

Genetic Algorithms (GA) optimize non-differentiable trajectory parameters or controller gains in physics simulation (Isaac Gym / Gazebo). Chromosomes encode controller parameters $P = [K_p, K_i, K_d, \phi_{\text{phase}}]$. Evaluation runs 1000 parallel environments testing candidate survival against fitness function $F = -\int (e^2 + w_u u^2) dt$. Best candidates undergo **Sim-to-Real Domain Randomization** (varying ground friction $\mu \in [0.2, 1.2]$, motor payload $m \pm 30\%$, latency delay $t_{\text{delay}} \in [0, 20\text{ms}]$) before deployment to hardware.

Chapter VIII

Manipulation & Kinematics

Kinematic analysis of 6-DOF manipulators requires Lie Group representations, singularity-robust numerical IK solvers, and passivity-based latency control.

8.1

How do you solve forward and inverse kinematics for a 6-DOF arm in real time?

rating — possible

Forward Kinematics (FK) computes end-effector pose $\mathbf{T}_{b,e} \in SE(3)$ given joint angles $\mathbf{\theta} \in \mathbb{R}^6$ using the **Product of Exponentials (PoE)** formulation over Lie Algebra $se(3)$:

$$\mathbf{T}(\mathbf{\theta}) = e^{[\mathbf{S}_1]\theta_1} e^{[\mathbf{S}_2]\theta_2} \dots e^{[\mathbf{S}_6]\theta_6} \mathbf{M}$$

where $\mathbf{S}_i$ are joint screw axes and $\mathbf{M} \in SE(3)$ is the home configuration pose. Inverse Kinematics (IK) computes $\mathbf{\theta}$ given target pose $\mathbf{T}_{\text{target}}$. Analytical solvers (IKFast) solve closed-form polynomial roots in $<2\mu\text{s}$ for arms with spherical wrists. For numerical IK, compute joint velocity updates $\mathbf{\dot{\theta}}$ via the Manipulator Jacobian $\mathbf{J}(\mathbf{\theta}) \in \mathbb{R}^{6 \times 6}$ ($\mathbf{\dot{x}} = \mathbf{J}(\mathbf{\theta})\mathbf{\dot{\theta}}$).

8.2

How do you handle kinematic singularities during teleoperation?

rating — possible

At a kinematic singularity, $\det(\mathbf{J}(\mathbf{\theta})) = 0$, causing pseudo-inverse $\mathbf{J}^+ = \mathbf{J}^T (\mathbf{J}\mathbf{J}^T)^{-1}$ entries to approach infinity ($\mathbf{\dot{\theta}} \to \infty$). To prevent wild joint motor spikes, implement **Damped Least Squares (DLS / Levenberg-Marquardt)** inverse kinematics:

$$\mathbf{J}^* = \mathbf{J}^T \left( \mathbf{J}\mathbf{J}^T + \lambda^2 \mathbf{I} \right)^{-1}$$

where $\lambda$ is an adaptive damping factor adjusted based on the smallest singular value $\sigma_{\min}$ of $\mathbf{J}$:

$$\lambda^2 = \begin{cases} 0, & \text{if } \sigma_{\min} \ge \epsilon \\ \left(1 - \left(\frac{\sigma_{\min}}{\epsilon}\right)^2\right) \lambda_{\max}^2, & \text{if } \sigma_{\min} < \epsilon \end{cases}$$
8.3

How do you implement force feedback in teleoperation, accounting for latency?

rating — possible

Communication latency $T_{\text{delay}} > 20\text{ms}$ introduces positive phase shift into bilateral haptic feedback loops, causing energy growth and violent physical instability. To guarantee stability, implement **Wave Variable Transformation (Passivity Control)**:

$$\text{Master Wave Transmit: } u_m(t) = \frac{1}{\sqrt{2b}} \left( F_m(t) + b v_m(t) \right)$$ $$\text{Slave Wave Receive: } v_s(t) = \frac{1}{\sqrt{2b}} \left( F_s(t) - b v_s(t) \right)$$

where $b$ is the characteristic wave impedance. Wave variables encode force and velocity signals into passive energy flows, guaranteeing passivity ($\int_0^t P(\tau) d\tau \ge 0$) under arbitrary constant transmission delays.

How do you ensure zero-downtime, safe OTA updates for embedded robotics platforms?

rating — possible

Safe Over-The-Air (OTA) firmware updates use dual **A/B Partition Layouts** managed by U-Boot bootloader environment variables.

OTA Sequence Execution Steps

  1. Verify signed image manifest using RSA-4096 / Ed25519 public keys.
  2. Flash image to inactive Partition B (`/dev/mmcblk0p3`).
  3. Set U-Boot environment variables: `bootcount=0`, `bootlimit=3`, `upgrade_available=1`, `active_partition=B`.
  4. Reboot system. Upon boot, a systemd health-check service runs integration tests (sensor checks, CAN bus dry-run).
  5. If health checks pass $\to$ clear `upgrade_available=0` (commits Partition B). If health check fails or system hangs $\to$ hardware watchdog resets MCU, U-Boot increments `bootcount > bootlimit`, and automatically falls back to Partition A.
