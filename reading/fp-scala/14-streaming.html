Part IV · Effects and I/O

Streaming I/O & Where Next

IO alone handles one-shot effects well but large data badly. We look at why lazy I/O fails, build the core of a pull-based stream with guaranteed resource cleanup, and finish with a map from this book to the libraries real Scala teams use.

14.1The Problem: Big Files

Task: does a file have more than 40,000 lines? With the IO from Chapter 13, the honest version is imperative code inside one big IO:

def linesGt40k(filename: String): IO[Boolean] = IO {
  val src = io.Source.fromFile(filename)
  try
    var count = 0
    val lines = src.getLines()
    while count <= 40000 && lines.hasNext do
      lines.next()
      count += 1
    count > 40000
  finally src.close()
}

It's correct: it stops early, uses constant memory and always closes the file. But the logic (count, stop at a threshold) is fused with the I/O. If we now want "skip blank lines", "only count lines with an error" or "stop at the first match", we write a new loop each time. We lost the composability of Part I.

Why not a lazy iterator?

Return IO[Iterator[String]] and let callers use filter, take, map? This is lazy I/O, and it's broken: when should the file close? If the iterator closes it at the end, a caller who stops early leaks the handle. If the caller must close it, they can forget. And the iterator is mutable, so passing it to two functions gives wrong results. The resource's lifetime has escaped.

Lazy I/O is the classic trap: the code looks functional, but file handles, sockets and DB cursors leak whenever a consumer stops early or throws. The fix isn't more care; it's an abstraction that owns the resource for its whole lifetime.

14.2A Stream Transducer

Start without effects. Describe a stream transformation as a small state machine that, at each step, either emits a value, asks for the next input, or stops:

enum Process[I, O]:
  case Emit(head: O, tail: Process[I, O] = Halt[I, O]())
  case Await(recv: Option[I] => Process[I, O])    // None means: input is exhausted
  case Halt()

  def apply(s: LazyList[I]): LazyList[O] = this match
    case Halt()        => LazyList()
    case Await(recv)   => s match
      case h #:: t => recv(Some(h))(t)
      case _       => recv(None)(s)
    case Emit(h, t)    => h #:: t(s)

Simple building blocks:

object Process:
  def liftOne[I, O](f: I => O): Process[I, O] =
    Await:
      case Some(i) => Emit(f(i))
      case None    => Halt()

  def filter[I](p: I => Boolean): Process[I, I] =
    Await[I, I] {
      case Some(i) if p(i) => Emit(i)
      case _               => Halt()
    }.repeat

  def take[I](n: Int): Process[I, I] =
    if n <= 0 then Halt()
    else Await:
      case Some(i) => Emit(i, take(n - 1))
      case None    => Halt()

  def count[I]: Process[I, Int] =
    def go(n: Int): Process[I, Int] = Await:
      case Some(_) => Emit(n + 1, go(n + 1))
      case None    => Halt()
    go(0)

(repeat restarts a process when it halts, turning "handle one element" into "handle all of them".) The important combinator is pipe, written |>: feed the output of one process into another. It's a function composition for state machines, and it fuses: each element flows through the whole pipeline before the next is read, as with lazy lists.

val moreThan40k: Process[String, Boolean] =
  filter[String](_.nonEmpty) |> count |> exists(_ > 40000)

The logic is now pure, reusable and testable on a LazyList in memory. The I/O is a separate driver that reads lines from a file, feeds them in, and closes the file when the process halts, including when it halts early.

14.3Adding Effects and Resource Safety

Generalise Await so that instead of waiting for a pure input, it requests an effect F[A] (like reading a line through IO), and give every process a way to clean up:

enum Process[F[_], O]:
  case Await[F[_], A, O](req: F[A], recv: Either[Throwable, A] => Process[F, O]) extends Process[F, O]
  case Emit(head: O, tail: Process[F, O])
  case Halt(err: Throwable)          // End (normal), Kill (stopped by consumer), or a real error

Three ideas make it safe:

  1. Halt carries a reason. Normal end, killed by a consumer (e.g. take(5) got enough) or failed.
  2. onHalt / onComplete. Every process can attach a finaliser that runs on any kind of halt. A resource is acquired and its release attached in one combinator, so they can't be separated.
  3. Downstream kills upstream. When a consumer halts early, the pipe sends Kill to the producer, which runs its finalisers. Early exit can't leak.
// shape of a safe resource combinator
def resource[R, O](acquire: IO[R])(use: R => Process[IO, O])(release: R => Process[IO, O]): Process[IO, O]

def lines(filename: String): Process[IO, String] =
  resource(IO(io.Source.fromFile(filename)))(
    src => /* emit src.getLines() one at a time */ ???
  )(src => eval_(IO(src.close())))

// the whole program: pure description, run once at the edge
val program = lines("big.log") |> filter(_.nonEmpty) |> count |> exists(_ > 40000)
A streaming library is a description language for incremental, effectful pipelines where resource lifetime is part of the description. Composition stays pure, memory stays constant, and the file closes whether the pipeline finishes, fails or stops early.

Resource safety here plays the role RAII plays in C++: tie release to the structure, not to the programmer's discipline. The difference is that a stream's lifetime isn't a lexical scope; it's however long the pipeline runs. The stream library tracks that lifetime the way a destructor tracks scope.

This design is roughly where fs2 (Functional Streams for Scala) started. Modern fs2 uses a pull-based core and chunked elements for speed, but the ideas are the ones in this chapter.

14.5Where Next: The Real Libraries

Everything you built has a production version. You'll recognise all of them now:

  • cats: Monoid, Functor, Applicative, Monad, Traverse, Validated, plus monad transformers (EitherT, OptionT). It's Part III as a library.
  • cats-effect: an IO like Chapter 13's, but async, cancellable, with lightweight fibers, Resource for safe acquisition and release, and structured concurrency. Where Par was heading.
  • fs2: streaming on top of cats-effect. Chapter 14 grown up. Used for files, Kafka, HTTP bodies, sockets.
  • ZIO: an alternative effect system with errors and dependencies in the type: ZIO[R, E, A] is roughly Reader + Either + IO in one type.
  • ScalaCheck: Chapter 8, with shrinking. cats-parse and fastparse: Chapter 9.
  • http4s, doobie, Tapir: HTTP, SQL and API description built on the above.

A first real program with cats-effect, runnable with scala-cli:

//> using scala 3.5
//> using dep org.typelevel::cats-effect:3.5.7

import cats.effect.{IO, IOApp}
import cats.syntax.all.*
import scala.concurrent.duration.*

object Main extends IOApp.Simple:
  def fetch(i: Int): IO[Int] = IO.sleep(100.millis) *> IO(i * i)

  val run: IO[Unit] =
    for
      results <- (1 to 10).toList.parTraverse(fetch)   // traverse, in parallel
      _       <- IO.println(s"sum of squares = ${results.sum}")
    yield ()

Look at what's there: a for-comprehension over IO, *> from Chapter 9, and traverse from Chapter 12 running in parallel. Ten 100 ms fetches finish in about 100 ms.

14.6How to Keep Going

  1. Redo Part I exercises from memory a month from now. If foldRight, traverse and State.flatMap come out without thinking, you've got the foundation.
  2. Read the cats source for Traverse and Validated. It'll look familiar.
  3. Build something small and real with cats-effect and fs2: tail a log file, parse each line with cats-parse, aggregate with a monoid, expose the result over http4s. That one project touches every part of this book.
  4. Bring the ideas back to C++. std::expected with and_then, ranges pipelines, pure "core" functions with an effectful shell, monoidal reductions with std::reduce. The language changes; the design habits carry over.
The lasting lesson isn't Scala or monads. It's a way of designing: make effects explicit, keep the core pure, find the algebra, state the laws, and choose the least powerful abstraction that does the job.
Lazy I/O
Exposing an effectful source as a lazy collection; leaks resources when consumers stop early.
Stream transducer / Process
A state machine that consumes input and emits output incrementally.
Pipe (|>)
Composing two stream transformations; elements flow through both, one at a time.
Finaliser
Cleanup attached to a stream that runs on every kind of termination.
Fiber
A lightweight logical thread managed by an effect runtime like cats-effect or ZIO.
  • Imperative loops in IO are correct but don't compose; lazy I/O composes but leaks.
  • Stream transducers describe incremental processing as pure, composable state machines.
  • Effectful streams tie resource release to the stream, so early exit can't leak.
  • cats, cats-effect, fs2 and ZIO are this book's ideas at production strength.
