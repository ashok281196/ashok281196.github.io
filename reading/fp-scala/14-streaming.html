Part IV · Effects and I/O

Streaming I/O & Where Next

IO alone handles one-shot effects well but large data badly. We look at why a hand-written loop doesn't compose and why lazy I/O leaks, build stream transducers in C++ that compose with a pipe operator, run them over a 50,000-line file that's always closed, and finish with where these ideas live in real C++.

14.1The Problem: Big Files

Task: does a log file have more than 40,000 non-blank lines? The honest imperative version:

bool more_than_40k(const std::string& path) {
    std::ifstream in(path);                 // RAII: closed on every exit path
    std::string line;
    int count = 0;
    while (count <= 40000 && std::getline(in, line))
        if (!line.empty()) ++count;
    return count > 40000;
}

It's correct: it stops early, uses constant memory, and always closes the file. But the logic (skip blanks, count, stop at a threshold) is fused with the I/O. Now someone wants "only lines containing ERROR", or "the first 5 matches", or the same logic over a socket instead of a file. Each time we write a new loop. We've lost the composability of Part I.

Why not a lazy range over the file?

Return a lazy range of lines, and let callers use filter and take? This is lazy I/O. In C++ it's std::views::istream or a generator over an ifstream:

auto lines_of(std::istream& in);        // a lazy view: who owns `in`? when is it closed?

The view doesn't own the stream, so the caller has to keep the file alive exactly as long as some consumer is still pulling, and close it afterwards. Return the view from a function that opened the file, and it dangles. Make the range own the file, and an early-stopping consumer that stashes the range somewhere keeps the file open indefinitely. The resource's lifetime has escaped from the code that knows when processing is finished.

Lazy I/O is the classic trap: the code looks functional, but file handles, sockets and DB cursors leak or dangle whenever a consumer stops early, stores the range, or throws. The fix isn't more care; it's an abstraction that owns the resource for exactly the duration of a run.

14.2A Stream Transducer

First, without effects. Describe a stream transformation as a tiny state machine that, at each step, either emits a value, asks for the next input, or stops:

template <typename I, typename O> struct PNode;
template <typename I, typename O> struct Process { std::shared_ptr<const PNode<I, O>> node; };

template <typename I, typename O> struct PNode {
    struct Emit  { O head; Process<I, O> tail; };                                // output a value, continue
    struct Await { std::function<Process<I, O>(std::optional<I>)> recv; };    // need input (nullopt = end)
    struct Halt  {};                                                           // done
    std::variant<Emit, Await, Halt> v;
};

Building blocks are small recursive definitions (the helpers emit, await and halt just construct nodes):

template <typename I, typename P> Process<I, I> filter(P p) {
    return await<I, I>([p](std::optional<I> i) -> Process<I, I> {
        if (!i) return halt<I, I>();
        return p(*i) ? emit<I, I>(*i, filter<I>(p)) : filter<I>(p);
    });
}

template <typename I> Process<I, int> count(int n = 0) {
    return await<I, int>([n](std::optional<I> i) -> Process<I, int> {
        if (!i) return halt<I, int>();
        return emit<I, int>(n + 1, count<I>(n + 1));     // running count
    });
}

template <typename I, typename P> Process<I, bool> exists(P p) {   // emits once, then halts
    return await<I, bool>([p](std::optional<I> i) -> Process<I, bool> {
        if (!i) return emit<I, bool>(false);
        return p(*i) ? emit<I, bool>(true) : exists<I>(p);
    });
}

The key combinator is pipe: feed the output of one process into another. We spell it |, like ranges:

template <typename I, typename M, typename O>
Process<I, O> operator|(Process<I, M> p1, Process<M, O> p2) {
    // p2 halted       → halt (and never pull from p1 again)
    // p2 emits h      → emit h, continue with p1 | rest of p2
    // p2 awaits:
    //   p1 emits h    → feed h to p2
    //   p1 halted     → tell p2 the input is over
    //   p1 awaits     → await an input I, give it to p1, keep piping
}

Now pipelines compose, and the logic is pure and testable on an in-memory vector:

auto more_than_40k_nonblank =
      filter<std::string>([](const std::string& s) { return !s.empty(); })
    | count<std::string>()
    | exists<int>([](int n) { return n > 40000; });

Each element flows through the whole pipeline before the next is read, as with lazy lists. And because exists halts as soon as it knows the answer, the pipe stops pulling: in the listing, running exists(x > 2) against an infinite source pulls exactly 3 values.

14.3Effects and Resource Safety

The process only describes the transformation. A driver runs it against a source of input, pulling only when the process asks:

template <typename I, typename O, typename Pull>
std::vector<O> drive(Process<I, O> p, Pull&& pull) {           // pull: () -> optional<I>
    std::vector<O> out;
    for (;;) {
        if (auto* e = get_if<Emit>(...))       { out.push_back(e->head); p = e->tail; }
        else if (auto* a = get_if<Await>(...)) { p = a->recv(pull()); }
        else return out;                                        // halted: stop pulling
    }
}

Resource safety comes from who owns the resource. The file belongs to the source, and the source lives exactly as long as one run:

class LineSource {                      // owns the file; RAII closes it
    std::unique_ptr<Handle> h_;         // Handle wraps std::ifstream, logs open/close
public:
    LineSource(const std::string& path, FileLog* log);
    std::optional<std::string> operator()();     // next line, or nullopt at EOF
};

template <typename O>
std::vector<O> run_file(const std::string& path, Process<std::string, O> p, FileLog* log) {
    LineSource src(path, log);
    return drive(p, src);
}   // the file is closed here: at EOF, on early halt, or if anything throws

Running the pipeline over a 50,000-line file:

read 44446 of 50000 lines, file closed: 1

It stopped as soon as the answer was known, and the file was closed. Asking for the first 3 non-blank lines reads 4 lines and closes the file; a search that never matches reads all 50,000 and closes it. The listing asserts all three. The pipeline itself never mentions files, so the same more_than_40k_nonblank works on a socket or a vector.

A streaming library is a description language for incremental pipelines in which the resource's lifetime is part of the description. Composition stays pure, memory stays constant, and cleanup happens whether the pipeline finishes, fails or stops early.

The book generalises Await to request an effect F[A] (like reading a line through IO) and attaches finalisers to every process with onHalt, so that when a downstream consumer halts, upstream is killed and runs its cleanup. That's how it gets resource safety in a garbage-collected language. In C++ we get the same guarantee more directly with RAII: the driver owns the source, and scope exit is the finaliser. This design grew into Scala's fs2 library.

14.5Where These Ideas Live in Real C++

  • Errors as values: std::optional and std::expected with transform/and_then/or_else (C++23). Use them at API boundaries instead of exceptions for expected failures.
  • Laziness and fusion: std::ranges views, and C++23 std::generator for coroutine-based lazy sequences. Range-v3 has more adaptors.
  • Monoids and parallel folds: std::reduce / std::transform_reduce with execution policies; oneTBB's parallel_reduce.
  • Persistent data: the immer library (persistent vectors, maps, sets with structural sharing), used for undo/redo and safe sharing across threads.
  • Effects as values: std::execution senders/receivers (C++26), libunifex, and coroutine frameworks where a task is a description that runs when awaited.
  • Property testing: RapidCheck. Parsing: PEGTL, Boost.Spirit, lexy.
  • Pure core, imperative shell: no library needed. It's the habit with the biggest payoff in robotics and embedded code: keep control laws, planners and state machines pure, and keep drivers and I/O at the edges.

A small "everything together" exercise you can do in Compiler Explorer: read numbers from a string stream with a Process pipeline, parse each with std::from_chars into an expected, collect them with an applicative Validated traverse that reports every bad line, and combine the good ones with fold_map into (count, sum, min, max) using a product monoid. That's Chapters 4, 10, 12 and 14 in about 60 lines.

14.6How to Keep Going

  1. Redo the Part I exercises from memory in a month. If fold_right, traverse and State::flat_map come out without thinking, the foundation is there.
  2. Read the original book with this companion beside it. Its Scala will read easily now, and the "In the book" boxes map each idea back.
  3. Refactor one real module of your own code toward a pure core: pick a state machine or controller, make its step function (State, Input) → (State, Output), and property-test it.
  4. Try a functional language for a week (Scala, Haskell, OCaml or F#). The ideas feel different when the language makes them the default.
The lasting lesson isn't a particular language or monads. It's a way of designing: make effects explicit, keep the core pure, find the algebra, state the laws, and choose the least powerful abstraction that does the job.
Lazy I/O
Exposing an effectful source as a lazy range; leaks or dangles when consumers stop early.
Stream transducer / Process
A state machine that consumes input and emits output incrementally.
Pipe
Composing two stream transformations; elements flow through both, one at a time.
Driver
The loop that runs a process against a real source, owning the resource for the run.
  • Imperative loops are correct but don't compose; lazy I/O composes but leaks.
  • Stream transducers describe incremental processing as pure, composable state machines.
  • A driver that owns the source makes cleanup automatic, even on early stop (RAII).
  • Modern C++ already ships most of these ideas; this book is how to use them on purpose.
