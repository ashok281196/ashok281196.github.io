Property-Based Testing

Instead of writing test cases, write laws and let a library try them on hundreds of random inputs. We design a small ScalaCheck-style library, reusing the State type from Chapter 6, and see the design process from Chapter 7 again.

8.1The Idea

An example-based test checks one input: assert(reverse(List(1,2,3)) == List(3,2,1)). A property states something true for all inputs, and a test library generates many inputs to try it on:

// with the real ScalaCheck library
val intList = Gen.listOf(Gen.choose(0, 100))

val prop =
  forAll(intList)(ns => ns.reverse.reverse == ns) &&
  forAll(intList)(ns => ns.headOption == ns.reverse.lastOption)

prop.check()   // + OK, passed 100 tests.

When a property fails, a good library also shrinks the failing input to the smallest case that still fails, so instead of a 73-element list you see List(0, -1).

Laws from Chapter 7, like y.map(id) == y, become properties directly. That's one reason pure code and laws go together: they can be tested automatically.

Example tests are spot checks: an inspector picks three bolts and measures them. Property tests are a rule ("every bolt is within 0.1 mm") plus a machine that measures thousands of random bolts and, when it finds a bad one, also finds the simplest description of what makes it bad.

8.2Choosing What to Test

Coming up with properties is a skill. Good sources:

  • Round trips: decode(encode(x)) == x, xs.reverse.reverse == xs.
  • Invariants: xs.sorted has the same length and elements as xs, and each element is ≤ the next.
  • Comparison with a simple model: your fast LRUCache behaves like a slow, obviously correct version on any sequence of operations.
  • Algebraic laws: associativity, identity, fork(x) == x.

8.3Generators

A generator produces random values of some type. To produce a random value we need an RNG and must return the new one. We have a type for exactly that:

opaque type Gen[+A] = State[RNG, A]

object Gen:
  def unit[A](a: => A): Gen[A] = State.unit(a)

  def choose(start: Int, stopExclusive: Int): Gen[Int] =
    State(nonNegativeInt).map(n => start + n % (stopExclusive - start))

  def boolean: Gen[Boolean] =
    State(nonNegativeInt).map(_ % 2 == 0)

  extension [A](self: Gen[A])
    def map[B](f: A => B): Gen[B] = State.map(self)(f)
    def flatMap[B](f: A => Gen[B]): Gen[B] = State.flatMap(self)(f)

    def listOfN(n: Int): Gen[List[A]] =
      State.traverse(List.fill(n)(self))(g => g)

    def run(rng: RNG): (A, RNG) = State.run(self)(rng)

(State.map(self)(f) calls Chapter 6's State extension method directly, by name. Writing self.map(f) here would call Gen's own map and loop forever, because inside this object Gen and State are the same type.) We didn't write any new machinery: random generation is State over RNG, and everything from Chapter 6 applies.

With flatMap, a generator can depend on a previously generated value. That's how you generate a list of random length, or a pair where the second element depends on the first:

def listOfRandomLength[A](g: Gen[A]): Gen[List[A]] =
  Gen.choose(0, 20).flatMap(n => g.listOfN(n))

val orderedPair: Gen[(Int, Int)] =
  for
    a <- Gen.choose(0, 100)
    b <- Gen.choose(a, 101)
  yield (a, b)

Write union[A](g1: Gen[A], g2: Gen[A]): Gen[A], which picks from either with equal probability, and weighted[A](g1: (Gen[A], Double), g2: (Gen[A], Double)): Gen[A].

Show solution
def union[A](g1: Gen[A], g2: Gen[A]): Gen[A] =
  boolean.flatMap(b => if b then g1 else g2)

val double01: Gen[Double] = State(double)    // from Chapter 6

def weighted[A](g1: (Gen[A], Double), g2: (Gen[A], Double)): Gen[A] =
  val threshold = g1(1).abs / (g1(1).abs + g2(1).abs)
  double01.flatMap(d => if d < threshold then g1(0) else g2(0))

Both are "generate a value, use it to choose a generator": flatMap.

8.4Properties as Values

What should a property be? Following Chapter 7: start from how we'd use it. We want to run it, see pass or fail, and on failure see the input and how many tests passed first. We also want to choose how many cases to run and to combine properties with &&.

type TestCases = Int
type FailedCase = String
type SuccessCount = Int

enum Result:
  case Passed
  case Falsified(failure: FailedCase, successes: SuccessCount)

  def isFalsified: Boolean = this match
    case Passed          => false
    case Falsified(_, _) => true

opaque type Prop = (TestCases, RNG) => Result

A property is a function: given a number of cases and a generator state, it produces a result. Running and describing are separate again.

object Prop:
  def forAll[A](as: Gen[A])(f: A => Boolean): Prop =
    (n, rng) =>
      randomLazyList(as)(rng)
        .zip(LazyList.from(0))
        .take(n)
        .map { (a, i) =>
          try
            if f(a) then Result.Passed
            else Result.Falsified(a.toString, i)
          catch case e: Exception =>
            Result.Falsified(s"$a threw: ${e.getMessage}", i)
        }
        .find(_.isFalsified)
        .getOrElse(Result.Passed)

  // an infinite lazy list of generated values (Chapter 5's unfold)
  def randomLazyList[A](g: Gen[A])(rng: RNG): LazyList[A] =
    LazyList.unfold(rng)(r => Some(g.run(r)))

  extension (self: Prop)
    def &&(that: Prop): Prop =
      (n, rng) => self(n, rng) match
        case Result.Passed => that(n, rng)
        case failed        => failed

    def check(n: TestCases = 100, rng: RNG = SimpleRNG(System.currentTimeMillis)): Result =
      self(n, rng)

Notice how much of Part I this reuses. Generation is State. The stream of test cases is a lazy list built with unfold. find stops at the first failure without generating the rest. And a thrown exception is caught at the boundary and turned into a value.

8.5Sized Generation and Shrinking

Random lists of length 0 to 20 rarely hit edge cases like the empty list, and when a big list fails, the counterexample is hard to read. Two approaches:

  • Shrinking: after a failure, try smaller versions of the failing input (drop elements, halve numbers) and keep the smallest that still fails. ScalaCheck and Hypothesis do this.
  • Sized generation: generate small inputs first and grow. If a property fails at size 3, you'll see the size-3 case before any size-50 case.

Sized generation is easy to add: a generator that depends on a size.

opaque type SGen[+A] = Int => Gen[A]

extension [A](g: Gen[A])
  def list: SGen[List[A]] = n => g.listOfN(n)
  def nonEmptyList: SGen[List[A]] = n => g.listOfN(n.max(1))

A forAll that takes an SGen runs the property at sizes 0, 1, 2, ... up to a maximum, splitting the test budget across sizes.

Write a property for List.sorted on List[Int] using forAll.

Show solution
val smallInt = Gen.choose(-10, 10)

val sortedProp = Prop.forAll(listOfRandomLength(smallInt)): ns =>
  val s = ns.sorted
  val ordered = s.isEmpty || s.zip(s.tail).forall((a, b) => a <= b)
  val samePerm = s.groupBy(identity).view.mapValues(_.size).toMap ==
                 ns.groupBy(identity).view.mapValues(_.size).toMap
  ordered && samePerm

"Ordered" alone would accept a function that returns Nil. "Same elements with the same counts" closes that gap. Using a small range of ints makes duplicates likely, which tests the duplicate handling.

8.6Testing Laws

We can now test the parallelism laws from Chapter 7. Equality of two Pars means equality of their results when run:

def equal[A](p1: Par[A], p2: Par[A]): Par[Boolean] =
  p1.map2(p2)(_ == _)

val es = java.util.concurrent.Executors.newCachedThreadPool

val mapLaw = Prop.forAll(Gen.choose(0, 100)): n =>
  equal(Par.unit(n).map(identity), Par.unit(n)).run(es).get

val forkLaw = Prop.forAll(Gen.choose(0, 100)): n =>
  equal(Par.fork(Par.unit(n)), Par.unit(n)).run(es).get

Run the fork law with a fixed pool of size 1 and the blocking implementation, and the test hangs, which reproduces the deadlock from Chapter 7.

A passing property test isn't proof. It's evidence from N random cases. Generators that never produce the interesting inputs (empty lists, Int.MinValue, duplicates, unicode) will pass forever. Think about the distribution of your generators as carefully as about the property.

8.7What We Learned About Design

We designed the library the same way as in Chapter 7: from usage, primitives first, representation last. And we found the same combinators on Gen that we had on Option, State and Par: unit, map, flatMap, listOfN (which is sequence). Three libraries in, with completely different purposes, and the same interface keeps appearing.

In real projects, use ScalaCheck (or Hypothesis in Python, RapidCheck in C++). The point of this chapter isn't the library; it's that a test library falls out naturally once generators are State and properties are values.
Property
A statement that must hold for all inputs, checked on many generated inputs.
Generator
A description of how to produce random values of a type; here State[RNG, A].
Shrinking
Reducing a failing input to a minimal failing case.
Sized generation
Generating inputs of increasing size, so small counterexamples appear first.
  • Property tests check laws against many random inputs.
  • Good properties: round trips, invariants, comparison with a model, algebraic laws.
  • Generators are State over RNG; flatMap makes dependent generation easy.
  • A property is a function from (test count, RNG) to a result.
  • The Chapter 7 laws become executable tests.
