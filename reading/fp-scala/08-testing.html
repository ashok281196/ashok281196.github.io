Property-Based Testing

Instead of writing test cases, write laws and let a library try them on hundreds of random inputs. We design a small QuickCheck-style library in C++, reusing the State idea from Chapter 6, and watch it find a bug from a counterexample.

8.1The Idea

An example-based test checks one input: EXPECT_EQ(reverse({1,2,3}), (vector{3,2,1})). A property states something true for all inputs, and a library generates many inputs to try it on:

auto int_list = list_of_random_length(choose(-10, 10));

auto prop =
    for_all(int_list, [](std::vector<int> ns) { return reversed(reversed(ns)) == ns; }) &&
    for_all(int_list, [](std::vector<int> ns) { return ns.empty() || ns.front() == reversed(ns).back(); });

prop.check();   // + OK, passed 100 tests.

When a property fails, a good library also shrinks the failing input to the smallest case that still fails, so instead of an 18-element vector you see [0, -1].

The laws from Chapter 7, like map(y, id) == y, become properties directly. That's one reason pure code and laws go together: they can be tested automatically.

Example tests are spot checks: an inspector measures three bolts. Property tests are a rule ("every bolt is within 0.1 mm") plus a machine that measures thousands of random bolts and, when it finds a bad one, also finds the simplest description of what makes it bad.

8.2Choosing What to Test

Coming up with properties is a skill. Good sources:

  • Round trips: decode(encode(x)) == x, serialise then parse a message, reverse twice.
  • Invariants: after sorting, the vector has the same elements and each is ≤ the next.
  • Comparison with a simple model: your lock-free queue behaves like a std::deque under any sequence of operations; your SIMD routine matches the scalar one.
  • Algebraic laws: associativity, identity, fork(x) == x.

8.3Generators

A generator produces random values of some type. To produce one we need an RNG and must return the new one. We already have a type for exactly that: a State action over RNG.

template <typename A>
class Gen {
    std::function<std::pair<A, RNG>(RNG)> run_;
public:
    using value_type = A;
    explicit Gen(std::function<std::pair<A, RNG>(RNG)> f) : run_(std::move(f)) {}
    std::pair<A, RNG> run(RNG r) const { return run_(r); }

    static Gen unit(A a);
    template <typename F> auto flat_map(F f) const;   // exactly State::flat_map
    template <typename F> auto map(F f) const;        // exactly State::map
    Gen<std::vector<A>> list_of_n(int n) const;      // exactly sequence / traverse
};

Gen<int> choose(int start, int stop_exclusive) {
    return Gen<int>(non_negative_int).map([=](int n) { return start + n % (stop_exclusive - start); });
}
Gen<bool> boolean() {
    return Gen<int>(non_negative_int).map([](int n) { return n % 2 == 0; });
}

The method bodies are copied from State in Chapter 6 (the full listing has them). Random generation is state over RNG, so everything carries over unchanged.

With flat_map, a generator can depend on an earlier generated value. That's how you generate a vector of random length, or a pair where the second element depends on the first:

template <typename A>
Gen<std::vector<A>> list_of_random_length(Gen<A> g, int max_len = 20) {
    return choose(0, max_len + 1).flat_map([g](int n) { return g.list_of_n(n); });
}

auto ordered_pair = choose(0, 100).flat_map([](int a) {
    return choose(a, 101).map([a](int b) { return std::pair{a, b}; });
});

Write union_(g1, g2), picking from either with equal probability, and weighted({g1, w1}, {g2, w2}).

Show solution
template <typename A> Gen<A> union_(Gen<A> g1, Gen<A> g2) {
    return boolean().flat_map([g1, g2](bool b) { return b ? g1 : g2; });
}

template <typename A>
Gen<A> weighted(std::pair<Gen<A>, double> g1, std::pair<Gen<A>, double> g2) {
    double threshold = std::abs(g1.second) / (std::abs(g1.second) + std::abs(g2.second));
    return double01().flat_map([=](double d) { return d < threshold ? g1.first : g2.first; });
}

Both are "generate a value, use it to choose a generator": flat_map.

8.4Properties as Values

What should a property be? Following Chapter 7, start from use. We want to run it, see pass or fail, and on failure see the input and how many tests passed first. We want to choose how many cases to run and to combine properties with &&.

struct Passed {};
struct Falsified { std::string failure; int successes; };
using Result = std::variant<Passed, Falsified>;

class Prop {
    std::function<Result(int, RNG)> run_;      // (number of cases, generator state) -> result
public:
    explicit Prop(std::function<Result(int, RNG)> f) : run_(std::move(f)) {}
    Result run(int n, RNG r) const { return run_(n, r); }

    Prop operator&&(const Prop& that) const {
        auto self = *this;
        return Prop([self, that](int n, RNG r) {
            auto res = self.run(n, r);
            return std::holds_alternative<Falsified>(res) ? res : that.run(n, r);
        });
    }
};

A property is a function from (test count, RNG) to a result. Describing it and running it are separate again. Now the central function:

template <typename A, typename F>
Prop for_all(Gen<A> gen, F f) {
    return Prop([gen, f](int n, RNG rng) -> Result {
        for (int i = 0; i < n; ++i) {
            auto [a, next] = gen.run(rng);
            rng = next;
            try {
                if (!f(a)) return Falsified{show(a), i};
            } catch (const std::exception& e) {
                return Falsified{show(a) + " threw: " + e.what(), i};
            }
        }
        return Passed{};
    });
}

Notice how much of Part I this reuses: generation is State, results are a sum type, and a thrown exception is caught at the boundary and turned into a value. Running a deliberately false property, "every vector has fewer than 15 elements", prints the counterexample:

! Falsified after 0 passed tests: [-5, -10, 8, -4, -6, 3, 6, 7, 5, -9, 0, 9, 2, 0, 7, -8, 6, 1]

The book walks through generating test cases as a lazy stream (Chapter 5's unfold) and stopping at the first failure. Our loop does the same thing directly. The book's Gen is literally State[RNG, A], as ours is in all but name.

8.5Sized Generation and Shrinking

That counterexample is hard to read. Two remedies:

  • Shrinking: after a failure, try smaller versions of the failing input (drop elements, move numbers toward zero) and keep the smallest that still fails. The 18-element vector above would shrink to a 15-element vector of zeros.
  • Sized generation: generate small inputs first and grow. If a property fails at size 3, you see the size-3 case before any size-50 case.

Sized generation is a generator that depends on a size: using SGen<A> = std::function<Gen<A>(int)>. A for_all taking an SGen runs at sizes 0, 1, 2, ... up to a maximum, splitting the test budget across sizes.

Write a property for std::sort on std::vector<int>.

Show solution
auto sorted_prop = for_all(list_of_random_length(choose(-10, 10)), [](std::vector<int> ns) {
    auto s = ns;
    std::sort(s.begin(), s.end());
    bool ordered = std::is_sorted(s.begin(), s.end());
    std::map<int, int> c1, c2;                // same elements, same counts
    for (int x : ns) ++c1[x];
    for (int x : s)  ++c2[x];
    return ordered && c1 == c2;
});

"Ordered" alone would accept a function that returns an empty vector. "Same elements with the same counts" closes that gap. A small range of values makes duplicates likely, which exercises the duplicate handling.

8.6Testing Laws

Laws turn directly into properties. Chapter 4's functor law for optionals, "transforming with the identity changes nothing":

auto opt_gen = union_(choose(0, 100).map([](int x) { return std::optional<int>(x); }),
                      Gen<std::optional<int>>::unit(std::nullopt));

auto map_identity = for_all(opt_gen, [](std::optional<int> o) {
    return o.transform([](int x) { return x; }) == o;
});

Chapter 7's laws work the same way: run(pool, map(unit(n), id)) == n, and run(pool, fork(unit(n))) == n. Run the fork law against the blocking implementation on a one-thread pool and the test hangs, reproducing the deadlock.

A passing property test isn't proof. It's evidence from N random cases. A generator that never produces the interesting inputs (empty vectors, INT_MIN, duplicates, NaN, non-ASCII strings) will pass forever. Think about your generators' distribution as hard as about the property.

8.7In Practice

For real C++ projects, use RapidCheck (QuickCheck for C++, with shrinking and gtest/Catch2 integration) or the property support in libraries like fuzztest. The point of this chapter isn't the library; it's that a test library falls out naturally once generators are State and properties are values. And the same interface keeps showing up: Gen has unit, map, flat_map and list_of_n (which is sequence), just like optional, State and Par.

Laws you write while designing (Chapter 7) become tests for free. Pure functions plus property tests give you far more coverage per line of test code than example tests do.
