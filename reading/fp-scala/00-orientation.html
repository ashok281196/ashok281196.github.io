Orientation & Setup

What the red book teaches, why we're learning it in C++, how to study a book made of exercises, and the C++20/23 features we'll use as our functional toolkit.

0.1Why This Book Has a Reputation

Most programming books show you finished tools and explain how to use them. Functional Programming in Scala (the "red book") does the reverse. It gives you a constraint, no side effects, and then asks you to build the tools yourself, one exercise at a time. You write a linked list. Then an optional value. Then a random number generator that never mutates anything. Around chapter 6 you notice that the last three things you built have functions with exactly the same shape. Around chapter 11 the book names that shape: a monad.

The difficulty isn't the syntax. You're asked to discover the abstractions rather than be told them, and discovering takes effort. That's also why it sticks.

Learning FP from a list of definitions ("a monad is a type with flatMap and unit satisfying three laws") is like learning chess from the rulebook. The red book makes you play hundreds of small games first, so when you finally read the rule, you've already used it.

0.2Why C++

The ideas in the book aren't about Scala. Pure functions, immutable data, errors as values, laziness, monoids and monads are design ideas, and modern C++ has picked up most of them: std::optional and std::expected with monadic operations, lazy ranges, lambdas, concepts, std::variant. This companion teaches every concept with C++ code, so the ideas land in the language you already think in.

C++ also makes some things harder, and those spots are instructive. We'll meet each one where it comes up:

0.3How to Study It

  1. Read the signature, then stop. Most exercises give you a type, like "a function from List<A> and A → B to List<B>". Before writing anything, ask: what values do I have, what do I need to produce, and what can I do with what I have? Often only one implementation compiles.
  2. Use the compiler as your teacher. Type errors are hints. Concepts make them readable.
  3. Get stuck for ten minutes, not two hours. Then open the solution, understand it, close it, and write it again from memory the next day.
  4. Re-derive, don't memorise. The goal is to be able to write fold or flat_map for a new type, not to remember the one for lists.
When you're stuck on an FP exercise, follow the types. Write down every value you have in scope and its type. The answer is almost always "combine these in the only way that makes the types line up."

0.5The Functional C++ Toolkit

This is the subset of C++ the rest of the book leans on. Skim it now; come back when a later block looks unfamiliar.

Functions as values

auto inc = [](int n) { return n + 1; };             // a lambda: an unnamed function object
auto twice = [](auto f, int x) { return f(f(x)); }; // generic lambda: takes any callable
twice(inc, 5);                                      // 7

std::function<int(int)> g = inc;   // type-erased: any callable with this signature
                                   // costs an allocation and an indirect call; use when you must store it

Generic functions, with concepts

template <typename A, std::invocable<A> F>
auto apply_twice(F f, A a) { return f(f(a)); }

Concepts constrain what a template accepts, so errors point at the call site instead of 300 lines into the template.

Sum types and "pattern matching"

struct Circle { double r; };
struct Rect   { double w, h; };
using Shape = std::variant<Circle, Rect>;     // one of these, never both

// the overload-set trick: build a visitor from several lambdas
template <typename... Fs> struct overloaded : Fs... { using Fs::operator()...; };

double area(const Shape& s) {
    return std::visit(overloaded{
        [](const Circle& c) { return 3.14159 * c.r * c.r; },
        [](const Rect& r)   { return r.w * r.h; },
    }, s);
}

If you add a case to the variant and forget a lambda, std::visit fails to compile. That's the exhaustiveness check functional languages give you.

Values, not objects

struct Point { int x, y; bool operator==(const Point&) const = default; };

const Point p{1, 2};
const Point q{.x = p.x, .y = 5};   // "copy with a change": p is untouched
auto [x, y] = q;                   // structured binding takes it apart

Structs with = default comparison, passed and returned by value, are FP's immutable records. Mark things const by default; reach for mutation only inside a function where no one can see it.

For the original book: val ≈ const auto; def f[A](...) ≈ a function template; A => B ≈ a callable (lambda or std::function<B(A)>); enum with cases ≈ std::variant; match ≈ std::visit; trait ≈ an abstract base or a concept; Option ≈ std::optional; Either ≈ std::expected.

Write template <typename A, typename Gt> bool is_sorted(std::span<const A> as, Gt gt) that returns true if no element is "greater than" the one after it. Use recursion on a subspan instead of a loop, just to practise.

Show solution
template <typename A, typename Gt>
bool is_sorted(std::span<const A> as, Gt gt) {
    if (as.size() < 2) return true;
    return !gt(as[0], as[1]) && is_sorted(as.subspan(1), gt);
}

std::vector v{1, 2, 3};
is_sorted<int>(v, std::greater{});   // true

The function is generic: it doesn't know what A is, so it must use gt to compare. That's your first taste of types constraining an implementation.
