Functional Data Structures

If nothing can be mutated, how do you "add" to a list? We build an immutable singly linked list from scratch, see why sharing makes it cheap, and find the one function, fold, that most list operations are built from.

3.1Immutable by Construction

A functional data structure is operated on only by pure functions. You never change it in place. "Adding" an element returns a new structure, and the old one is still there, unchanged.

That sounds expensive. It isn't, because of structural sharing: the new structure reuses the parts of the old one it didn't change. Since nothing can be mutated, sharing is always safe.

3.2Defining a List

A list is either empty, or an element followed by another list. That "either/or" maps directly to an enum, which is Scala's algebraic data type (ADT):

enum List[+A]:
  case Nil
  case Cons(head: A, tail: List[A])

object List:
  def apply[A](as: A*): List[A] =       // variadic: List(1, 2, 3)
    if as.isEmpty then Nil
    else Cons(as.head, apply(as.tail*))

import List.*

List(1, 2, 3) is Cons(1, Cons(2, Cons(3, Nil))). Draw it as boxes: each Cons holds a value and an arrow to the rest.

What does +A mean?

The + makes List covariant: if Dog is a subtype of Animal, then List[Dog] is a subtype of List[Animal]. This also lets one Nil serve every list: Nil is a List[Nothing], and Nothing is a subtype of every type, so Nil fits anywhere a List[Int] or List[String] is expected.

In C++, std::vector<Dog*> is unrelated to std::vector<Animal*>. That's correct for a mutable container: if it converted, you could push a Cat* into a vector of dogs. An immutable list has no "push into this list" operation, so covariance is safe. Immutability is what makes variance work.

3.3Pattern Matching

We take lists apart with match. Each case is a shape to compare against, and it binds names to the parts:

def sum(ints: List[Int]): Int = ints match
  case Nil              => 0
  case Cons(x, xs)      => x + sum(xs)

def product(ds: List[Double]): Double = ds match
  case Nil              => 1.0
  case Cons(0.0, _)     => 0.0        // match a literal; _ ignores the rest
  case Cons(x, xs)      => x * product(xs)

Notice the definitions follow the data. The list has two cases, so the function has two cases. The tail is a list, so the function recurses on it. Most functions over ADTs write themselves this way.

Implement tail (everything but the first element) and setHead (replace the first element). Both should take constant time. What should tail(Nil) do?

Show solution
def tail[A](as: List[A]): List[A] = as match
  case Nil         => sys.error("tail of empty list")
  case Cons(_, t)  => t

def setHead[A](as: List[A], h: A): List[A] = as match
  case Nil         => sys.error("setHead on empty list")
  case Cons(_, t)  => Cons(h, t)

Both are O(1) because they share t: no copying. For Nil we have three choices: throw, return Nil, or return an Option. Throwing is honest for now. Chapter 4 gives us the better answer.

Implement drop[A](as: List[A], n: Int): List[A] and dropWhile[A](as: List[A], f: A => Boolean): List[A], which removes elements from the front while they match the predicate.

Show solution
@tailrec
def drop[A](as: List[A], n: Int): List[A] =
  if n <= 0 then as
  else as match
    case Nil        => Nil
    case Cons(_, t) => drop(t, n - 1)

@tailrec
def dropWhile[A](as: List[A], f: A => Boolean): List[A] = as match
  case Cons(h, t) if f(h) => dropWhile(t, f)     // a guard
  case _                  => as

3.4What Sharing Can't Do

def append[A](a1: List[A], a2: List[A]): List[A] = a1 match
  case Nil        => a2
  case Cons(h, t) => Cons(h, append(t, a2))

append copies a1 but shares all of a2. Its cost depends only on the length of the first list.

Now try init: all elements except the last.

def init[A](as: List[A]): List[A] = as match
  case Nil          => sys.error("init of empty list")
  case Cons(_, Nil) => Nil
  case Cons(h, t)   => Cons(h, init(t))

This copies every node, O(n), because every Cons on the way to the end points to something that changes. A singly linked list is cheap at the front and expensive at the back. Choose structures to match how you'll use them: Scala's standard Vector is a wide immutable tree with effectively constant-time access at both ends.

A singly linked list is a chain of train cars, each coupled to the one behind it. You can add a new engine at the front without touching the train. To remove the last car, you'd have to rebuild every coupling from the front, because each car "contains" the rest of the train.

3.5Finding Fold

Look at sum and product side by side:

case Nil         => 0              |   case Nil         => 1.0
case Cons(x, xs) => x + sum(xs)    |   case Cons(x, xs) => x * product(xs)

They differ in two places: the value for Nil and the operator that combines the head with the result for the tail. Make both parameters:

def foldRight[A, B](as: List[A], acc: B, f: (A, B) => B): B = as match
  case Nil         => acc
  case Cons(x, xs) => f(x, foldRight(xs, acc, f))

def sum(ns: List[Int])         = foldRight(ns, 0, _ + _)
def product(ns: List[Double])  = foldRight(ns, 1.0, _ * _)

A useful picture: foldRight replaces the constructors. Every Cons becomes f and the Nil becomes acc.

Cons(1, Cons(2, Cons(3, Nil)))
   f(1,    f(2,    f(3, acc)))

Try it with Cons and Nil themselves: foldRight(xs, Nil, Cons(_, _)) gives back the same list. That's a quick check that fold captures the full structure of a list.

foldLeft: the stack-safe one

foldRight isn't tail-recursive: it calls itself and then still has to apply f. A long list will overflow the stack. foldLeft combines from the left with an accumulator, and is a loop:

@tailrec
def foldLeft[A, B](as: List[A], acc: B, f: (B, A) => B): B = as match
  case Nil         => acc
  case Cons(x, xs) => foldLeft(xs, f(acc, x), f)
foldLeft:   f(f(f(acc, 1), 2), 3)
foldRight:  f(1, f(2, f(3, acc)))

For an associative operator like + both give the same result. For others, like subtraction or building a list, the order matters.

Write length and reverse using foldLeft.

Show solution
def length[A](as: List[A]): Int =
  foldLeft(as, 0, (n, _) => n + 1)

def reverse[A](as: List[A]): List[A] =
  foldLeft(as, Nil: List[A], (acc, a) => Cons(a, acc))

The type ascription Nil: List[A] helps inference. Without it, Scala infers B from the bare Nil as List[Nothing], and then rejects Cons(a, acc) because a List[A] isn't a List[Nothing].

Write foldRight in terms of foldLeft, so it no longer overflows the stack.

Show solution
def foldRightSafe[A, B](as: List[A], acc: B, f: (A, B) => B): B =
  foldLeft(reverse(as), acc, (b, a) => f(a, b))

Reverse first, then fold from the left with the arguments swapped. It costs an extra pass and an extra list, but it's stack-safe. This is what you'd use in practice.

3.6The Big Three: map, filter, flatMap

Most list processing combines three operations. All of them are folds.

def map[A, B](as: List[A])(f: A => B): List[B] =
  foldRightSafe(as, Nil: List[B], (a, acc) => Cons(f(a), acc))

def filter[A](as: List[A])(p: A => Boolean): List[A] =
  foldRightSafe(as, Nil: List[A], (a, acc) => if p(a) then Cons(a, acc) else acc)

def concat[A](ls: List[List[A]]): List[A] =
  foldRightSafe(ls, Nil: List[A], append)

def flatMap[A, B](as: List[A])(f: A => List[B]): List[B] =
  concat(map(as)(f))

Note the separate parameter list (f: A => B). Scala infers types left to right across parameter lists, so by the time it reaches f it already knows A, and you can write map(xs)(_ + 1) without type annotations.

flatMap deserves attention: each element produces a list of results, and they're flattened. flatMap(List(1,2,3))(i => List(i, i)) is List(1,1,2,2,3,3). You'll see flatMap in almost every chapter from here on.

Implement filter using only flatMap.

Show solution
def filterViaFlatMap[A](as: List[A])(p: A => Boolean): List[A] =
  flatMap(as)(a => if p(a) then List(a) else Nil)

Keep an element by returning a one-element list; drop it by returning an empty one. flatMap is more powerful than map or filter: both can be written with it.

Write zipWith[A, B, C](as: List[A], bs: List[B])(f: (A, B) => C): List[C], combining elements pairwise and stopping at the shorter list.

Show solution
def zipWith[A, B, C](as: List[A], bs: List[B])(f: (A, B) => C): List[C] =
  (as, bs) match
    case (Cons(a, at), Cons(b, bt)) => Cons(f(a, b), zipWith(at, bt)(f))
    case _                          => Nil

Matching on a tuple lets you take two structures apart at once. (Not tail-recursive; make it so with an accumulator plus a final reverse as practice.)

3.7Trees

Same technique, different shape. A binary tree is either a leaf holding a value or a branch with two subtrees:

enum Tree[+A]:
  case Leaf(value: A)
  case Branch(left: Tree[A], right: Tree[A])

  def size: Int = this match
    case Leaf(_)      => 1
    case Branch(l, r) => 1 + l.size + r.size

  def depth: Int = this match
    case Leaf(_)      => 0
    case Branch(l, r) => 1 + (l.depth max r.depth)

  def map[B](f: A => B): Tree[B] = this match
    case Leaf(a)      => Leaf(f(a))
    case Branch(l, r) => Branch(l.map(f), r.map(f))

The pattern repeats: one case per constructor, and recursion wherever the type refers to itself. And again, these functions share a skeleton, which we can extract as a fold.

Write fold[B](f: A => B, g: (B, B) => B): B on Tree, then rewrite size, depth and map using it.

Show solution
  def fold[B](f: A => B, g: (B, B) => B): B = this match
    case Leaf(a)      => f(a)
    case Branch(l, r) => g(l.fold(f, g), r.fold(f, g))

  def sizeViaFold: Int  = fold(_ => 1, 1 + _ + _)
  def depthViaFold: Int = fold(_ => 0, (dl, dr) => 1 + (dl max dr))
  def mapViaFold[B](f: A => B): Tree[B] =
    fold(a => Leaf(f(a)): Tree[B], Branch(_, _))

Just like foldRight for lists: fold replaces Leaf with f and Branch with g. Every ADT has such a fold, and once you have it, most other functions are one-liners.

Pattern matching on an enum is checked for exhaustiveness. If you forget a case, the compiler warns you. Treat that warning as an error. It's one of the biggest practical wins of ADTs over class hierarchies with virtual methods.

Algebraic data type (ADT)
A type defined as a choice between cases (sum), each holding some fields (product). In Scala 3, an enum.
Structural sharing
New immutable structures reusing unchanged parts of old ones.
Covariance (+A)
F[Sub] is a subtype of F[Super]. Safe for immutable containers.
Fold
A function that replaces each constructor of a data structure with a function, reducing it to a single value.
  • Immutable structures return new versions and share what didn't change.
  • An ADT plus pattern matching: functions follow the shape of the data.
  • foldRight replaces constructors. foldLeft is a stack-safe loop.
  • map, filter and flatMap are all folds, and flatMap can express the other two.
