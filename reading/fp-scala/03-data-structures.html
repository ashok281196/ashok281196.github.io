Part I · Foundations

Functional Data Structures

If nothing can be mutated, how do you "add" to a list? We build a persistent singly linked list in C++ on shared_ptr, see why sharing makes it cheap, find the one function (fold) that most list operations are built from, and model trees as std::variant.

3.1Immutable by Construction

A functional data structure is only operated on by pure functions. You never change it in place. "Adding" an element returns a new structure; the old one still exists, unchanged.

That sounds expensive, but it isn't, because of structural sharing: the new structure reuses every part of the old one it didn't change. Since nothing is ever mutated, sharing is always safe, even across threads. Such structures are also called persistent.

The standard library has no persistent containers (std::vector and std::list are mutable and deep-copy on copy), so we build one.

3.2Defining a List

A list is either empty, or an element followed by another list. Each node is immutable once built, and several lists can point to the same node, so std::shared_ptr manages lifetimes:

template <typename T>
class List {
    struct Node {
        T head;
        std::shared_ptr<Node> tail;
    };
    std::shared_ptr<Node> node_;            // null means the empty list (Nil)
    explicit List(std::shared_ptr<Node> n) : node_(std::move(n)) {}

public:
    List() = default;                       // Nil
    static List cons(T h, List t) {         // Cons(h, t): O(1), shares t
        return List(std::make_shared<Node>(Node{std::move(h), std::move(t.node_)}));
    }
    bool empty() const        { return !node_; }
    const T& head() const     { return node_->head; }
    List tail() const         { return List(node_->tail); }
};

template <typename T>
List<T> cons(T h, List<T> t) { return List<T>::cons(std::move(h), std::move(t)); }

The full listing adds an initializer_list constructor so you can write List<int>{1, 2, 3}, meaning cons(1, cons(2, cons(3, List<int>{}))). Draw it as boxes: each node holds a value and an arrow to the rest.

There are no setters. Once built, a List can only be read, taken apart, or used to build new lists.

The book writes enum List[+A] { case Nil; case Cons(head: A, tail: List[A]) } and takes it apart with match. Scala's garbage collector handles sharing; here shared_ptr does. The +A (covariance) lets a List[Dog] be used as a List[Animal]; C++ templates are invariant, so we don't get that.

3.3Functions Follow the Data

int sum(const List<int>& xs) {
    return xs.empty() ? 0 : xs.head() + sum(xs.tail());
}

double product(const List<double>& xs) {
    if (xs.empty()) return 1.0;
    if (xs.head() == 0.0) return 0.0;      // short-circuit
    return xs.head() * product(xs.tail());
}

The list has two cases (empty or not), so the function has two cases. The tail is a list, so the function recurses on it. Most functions over recursive data write themselves this way.

Write tail (everything but the first element) and set_head (replace the first element). Both must be O(1). What should they do on an empty list?

Show solution
template <typename T> List<T> tail(const List<T>& xs) {
    if (xs.empty()) throw std::logic_error("tail of empty list");
    return xs.tail();
}
template <typename T> List<T> set_head(const List<T>& xs, T h) {
    if (xs.empty()) throw std::logic_error("set_head on empty list");
    return cons(std::move(h), xs.tail());
}

Both are O(1) because they share the tail. For the empty case we can throw, return empty, or return std::optional. Throwing is honest for now; Chapter 4 gives the better answer.

Write drop(xs, n) and drop_while(xs, p), which removes elements from the front while they satisfy p.

Show solution
template <typename T> List<T> drop(List<T> xs, int n) {
    while (n-- > 0 && !xs.empty()) xs = xs.tail();
    return xs;
}
template <typename T, typename P> List<T> drop_while(List<T> xs, P p) {
    while (!xs.empty() && p(xs.head())) xs = xs.tail();
    return xs;
}

A loop that reassigns a local handle. The lists themselves are never modified, so the function is pure.

3.4What Sharing Can and Can't Do

template <typename T>
List<T> append(const List<T>& a, const List<T>& b) {
    return a.empty() ? b : cons(a.head(), append(a.tail(), b));
}

append copies the nodes of a and shares all of b. Its cost depends only on the first list.

Now init, all elements except the last:

template <typename T>
List<T> init(const List<T>& xs) {
    if (xs.empty()) throw std::logic_error("init of empty list");
    if (xs.tail().empty()) return {};
    return cons(xs.head(), init(xs.tail()));
}

This copies every node, O(n), because every node on the way to the end points at something that changes. A singly linked list is cheap at the front and expensive at the back. Pick structures to match how you use them; production persistent libraries (like immer for C++) use wide trees that are cheap at both ends.

A singly linked list is a chain of train cars, each coupled to the one behind. You can add a new engine at the front without touching the train. Removing the last car means rebuilding every coupling from the front, because each car "contains" the rest of the train.

The destructor can overflow the stack. A list of a million nodes is a chain of a million shared_ptrs. Destroying the head destroys the next node, which destroys the next, recursively. The full listing gives List a destructor that unlinks the chain in a loop while it's the sole owner. Garbage-collected languages don't have this trap; any recursive unique_ptr or shared_ptr structure in C++ does.

3.5Finding Fold

Look at sum and product side by side:

empty → 0               |  empty → 1.0
head + sum(tail)        |  head * product(tail)

They differ in two places: the value for the empty list, and how the head combines with the result for the tail. Make both parameters:

template <typename T, typename B, typename F>
B fold_right(const List<T>& xs, B acc, F f) {
    return xs.empty() ? acc : f(xs.head(), fold_right(xs.tail(), std::move(acc), f));
}

int sum(const List<int>& xs) { return fold_right(xs, 0, std::plus{}); }

A useful picture: fold_right replaces the constructors. Every cons becomes f, and the empty list becomes acc:

cons(1, cons(2, cons(3, Nil)))
   f(1,    f(2,    f(3, acc)))

fold_left: the loop

fold_right recurses and then still has to apply f, so a long list overflows the stack. fold_left combines from the left with an accumulator, which in C++ we write as the loop it is:

template <typename T, typename B, typename F>
B fold_left(List<T> xs, B acc, F f) {
    while (!xs.empty()) { acc = f(std::move(acc), xs.head()); xs = xs.tail(); }
    return acc;
}
fold_left:   f(f(f(acc, 1), 2), 3)
fold_right:  f(1, f(2, f(3, acc)))

For an associative operation like + both give the same result. For subtraction, or building a list, order matters.

The book writes foldLeft as tail recursion with @tailrec. In C++, fold_left is std::accumulate or C++23's std::ranges::fold_left, and fold_right is std::ranges::fold_right, which iterates backwards instead of recursing.

Write length and reverse with fold_left.

Show solution
template <typename T> int length(const List<T>& xs) {
    return fold_left(xs, 0, [](int n, const T&) { return n + 1; });
}
template <typename T> List<T> reverse(const List<T>& xs) {
    return fold_left(xs, List<T>{},
                     [](List<T> acc, const T& a) { return cons(a, std::move(acc)); });
}

Write fold_right_safe using fold_left, so it no longer recurses.

Show solution
template <typename T, typename B, typename F>
B fold_right_safe(const List<T>& xs, B acc, F f) {
    return fold_left(reverse(xs), std::move(acc),
                     [&f](B b, const T& a) { return f(a, std::move(b)); });
}

Reverse, then fold from the left with the arguments swapped. One extra pass and an extra list, but stack-safe. That's what you'd use in practice.

3.6The Big Three: map, filter, flat_map

Most list processing combines three operations, and all three are folds:

template <typename T, typename F>
auto map(const List<T>& xs, F f) {
    using U = std::invoke_result_t<F, const T&>;
    return fold_right_safe(xs, List<U>{},
        [&f](const T& a, List<U> acc) { return cons(f(a), std::move(acc)); });
}

template <typename T, typename P>
List<T> filter(const List<T>& xs, P p) {
    return fold_right_safe(xs, List<T>{},
        [&p](const T& a, List<T> acc) { return p(a) ? cons(a, std::move(acc)) : acc; });
}

template <typename T>
List<T> concat(const List<List<T>>& ls) {
    return fold_right_safe(ls, List<T>{},
        [](const List<T>& l, List<T> acc) { return append(l, acc); });
}

template <typename T, typename F>
auto flat_map(const List<T>& xs, F f) { return concat(map(xs, f)); }

std::invoke_result_t computes the result type of f, so map can change the element type, say from List<int> to List<std::string>.

flat_map deserves attention: each element produces a list, and the lists are flattened. flat_map({1,2,3}, x ↦ {x, x}) is {1,1,2,2,3,3}. With ranges it's views::transform(f) | views::join. You'll see flat_map in almost every chapter from here on.

Implement filter using only flat_map.

Show solution
template <typename T, typename P>
List<T> filter_via_flat_map(const List<T>& xs, P p) {
    return flat_map(xs, [&p](const T& a) { return p(a) ? List<T>{a} : List<T>{}; });
}

Keep an element by returning a one-element list, drop it with an empty one. flat_map is more powerful than map or filter: both can be written with it.

Write zip_with(as, bs, f), combining elements pairwise and stopping at the shorter list.

Show solution
template <typename A, typename B, typename F>
auto zip_with(const List<A>& as, const List<B>& bs, F f) {
    using C = std::invoke_result_t<F, const A&, const B&>;
    if (as.empty() || bs.empty()) return List<C>{};
    return cons(f(as.head(), bs.head()), zip_with(as.tail(), bs.tail(), f));
}

3.7Trees, With std::variant

Same technique, different shape. A binary tree is a leaf holding a value, or a branch with two subtrees. "One of these cases" is a sum type, which in C++ is std::variant:

template <typename T>
struct Tree {
    struct Leaf   { T value; };
    struct Branch { std::shared_ptr<const Tree> left, right; };
    std::variant<Leaf, Branch> v;
};

template <typename... Fs> struct overloaded : Fs... { using Fs::operator()...; };

template <typename T> int size(const Tree<T>& t) {
    return std::visit(overloaded{
        [](const typename Tree<T>::Leaf&)     { return 1; },
        [](const typename Tree<T>::Branch& b) { return 1 + size(*b.left) + size(*b.right); },
    }, t.v);
}

template <typename T> int depth(const Tree<T>& t) {
    return std::visit(overloaded{
        [](const typename Tree<T>::Leaf&)     { return 0; },
        [](const typename Tree<T>::Branch& b) { return 1 + std::max(depth(*b.left), depth(*b.right)); },
    }, t.v);
}

std::visit with an overload set is C++'s pattern matching: one lambda per case. Forget a case and it doesn't compile, which is the exhaustiveness check you want from sum types. The pattern repeats: one case per alternative, recursion wherever the type refers to itself. And again, these functions share a skeleton.

Write fold(t, f, g) for trees: f handles a leaf's value, g combines the results of two subtrees. Then rewrite size, depth and a map_tree with it.

Show solution
template <typename T, typename F, typename G>
auto fold(const Tree<T>& t, F f, G g) -> std::invoke_result_t<F, const T&> {
    return std::visit(overloaded{
        [&](const typename Tree<T>::Leaf& l)   { return f(l.value); },
        [&](const typename Tree<T>::Branch& b) { return g(fold(*b.left, f, g), fold(*b.right, f, g)); },
    }, t.v);
}

template <typename T> int size_via_fold(const Tree<T>& t) {
    return fold(t, [](const T&) { return 1; }, [](int l, int r) { return 1 + l + r; });
}
template <typename T> int depth_via_fold(const Tree<T>& t) {
    return fold(t, [](const T&) { return 0; }, [](int l, int r) { return 1 + std::max(l, r); });
}
template <typename T, typename F> auto map_tree(const Tree<T>& t, F f) {
    using U = std::invoke_result_t<F, const T&>;
    return fold(t, [&](const T& a) { return leaf<U>(f(a)); },
                   [](Tree<U> l, Tree<U> r) { return branch(std::move(l), std::move(r)); });
}

Just like fold_right for lists, fold replaces Leaf with f and Branch with g. Every recursive sum type has such a fold, and once you have it, most other functions are one-liners.

Persistent data structure
An immutable structure whose "updates" return new versions that share unchanged parts with old ones.
Algebraic data type
A type built from sums (one of several cases: std::variant) and products (several fields: a struct).
Structural sharing
New immutable structures reusing nodes of old ones, here through shared_ptr.
Fold
A function that replaces each constructor of a data structure with a function, reducing it to one value.
  • Persistent structures return new versions and share what didn't change.
  • In C++, build them from shared_ptr to immutable nodes, and destroy long chains iteratively.
  • fold_right replaces constructors; fold_left is the loop.
  • map, filter and flat_map are all folds, and flat_map can express the other two.
  • Sum types are std::variant; pattern matching is std::visit with an overload set.
