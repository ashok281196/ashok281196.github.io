Strictness & Laziness

Chaining transforms on vectors builds a new vector at every step. By delaying evaluation we can fuse those steps into one pass, stop early, and even describe infinite sequences. We build a memoised lazy list in C++ to see how, then recognise the same idea in std::ranges views.

5.1The Problem: Intermediate Containers

std::vector<int> xs{1, 2, 3, 4};
auto a = map(xs, plus10);       // new vector
auto b = filter(a, is_even);    // another new vector
auto c = map(b, times3);        // and another

Three allocations, three full passes. Each step finishes the whole input before the next starts. For four elements it doesn't matter; for a million, or a pipeline that only needs the first result, it's wasteful. A hand-written loop would do it in one pass with no temporaries.

We want to write the pipeline with separate, reusable steps but have it run like the hand-fused loop. The key is non-strictness.

5.2Strict and Non-Strict

A function is strict in an argument if it always evaluates it. In C++, every ordinary function is strict in every argument: arguments are evaluated before the call. A few built-in operators aren't:

false && (std::cout << "!!", true);    // prints nothing
cond ? expensive_a() : expensive_b();  // only one branch runs

To write our own non-strict function, pass a thunk: a zero-argument function that computes the value when called.

template <typename A>
A if2(bool cond, const std::function<A()>& on_true, const std::function<A()>& on_false) {
    return cond ? on_true() : on_false();
}

if2<int>(false, [] () -> int { throw std::runtime_error("boom"); },
                [] { return 3; });   // 3; the throwing thunk never runs

Evaluated each time, unless memoised

int maybe_twice(bool b, const std::function<int()>& i) { return b ? i() + i() : 0; }

maybe_twice(true, [] { std::cout << "hi\n"; return 42; });   // prints "hi" TWICE

A thunk runs every time it's called. To evaluate once and remember the result, wrap it:

template <typename T>
class Lazy {
    mutable std::function<T()> f_;
    mutable std::optional<T> v_;
public:
    explicit Lazy(std::function<T()> f) : f_(std::move(f)) {}
    const T& get() const {
        if (!v_) { v_ = f_(); f_ = nullptr; }   // compute on first use, then cache
        return *v_;
    }
};

Scala has this built in. A by-name parameter x: => Int makes the compiler wrap the argument in a thunk for you, and lazy val is Lazy with thread-safe initialisation. In C++ you write the lambda yourself at the call site. That's more noise, but nothing is hidden.

Lazy above isn't thread-safe: two threads calling get() at once can both run f_. For shared lazies, guard with std::call_once (that's what a function-local static does for you too).

5.3A Lazy List

A lazy list is a list where "what's the next element, and what's the rest?" is a memoised thunk. Nothing is computed until someone asks for a step:

template <typename T>
class LazyList {
public:
    using Step = std::optional<std::pair<T, LazyList>>;   // nothing, or (head, rest)
private:
    struct Node {
        std::function<Step()> thunk;
        std::optional<Step> memo;
    };
    std::shared_ptr<Node> n_;
public:
    explicit LazyList(std::function<Step()> f)
        : n_(std::make_shared<Node>(Node{std::move(f), std::nullopt})) {}
    LazyList() : LazyList([] { return Step{}; }) {}          // empty

    const Step& step() const {                                // force one step, at most once
        if (!n_->memo) { n_->memo = n_->thunk(); n_->thunk = nullptr; }
        return *n_->memo;
    }
};

Because the memo lives in a shared node, every copy of a LazyList sees the same cached result: each step is computed at most once, however many times it's read.

Write take(ll, n) and take_while(ll, p). They must do no work until the result is consumed.

Show solution
template <typename T> LazyList<T> take(LazyList<T> ll, int n) {
    return LazyList<T>([ll, n]() -> typename LazyList<T>::Step {
        if (n <= 0) return std::nullopt;
        const auto& s = ll.step();
        if (!s) return std::nullopt;
        return std::pair{s->first, take(s->second, n - 1)};
    });
}
template <typename T, typename P> LazyList<T> take_while(LazyList<T> ll, P p) {
    return LazyList<T>([ll, p]() -> typename LazyList<T>::Step {
        const auto& s = ll.step();
        if (!s || !p(s->first)) return std::nullopt;
        return std::pair{s->first, take_while(s->second, p)};
    });
}

Calling take just builds one node holding a lambda. The recursive call is inside the lambda, so it only happens when someone asks for that step.

5.4A Lazy Fold Can Stop Early

Here's the trick that makes everything work. Write fold_right so the result for the rest of the list is passed to f as a thunk:

template <typename T, typename B, typename F>
B fold_right(LazyList<T> ll, std::function<B()> acc, F f) {
    const auto& s = ll.step();
    if (!s) return acc();
    auto rest = s->second;
    return f(s->first, std::function<B()>([rest, acc, f] { return fold_right<T, B, F>(rest, acc, f); }));
}

If f never calls the thunk, the rest of the list is never touched:

template <typename T, typename P> bool exists(LazyList<T> ll, P p) {
    return fold_right<T, bool>(ll, [] { return false; },
        [&p](const T& a, const std::function<bool()>& rest) { return p(a) || rest(); });
}

|| doesn't call rest() once p(a) is true, so exists stops at the first match, like a loop with break, while being a fold.

Write for_all with fold_right, and lazy versions of map, filter and append.

Show solution
template <typename T, typename P> bool for_all(LazyList<T> ll, P p) {
    return fold_right<T, bool>(ll, [] { return true; },
        [&p](const T& a, const std::function<bool()>& rest) { return p(a) && rest(); });
}

template <typename T, typename F>
auto map(LazyList<T> ll, F f) -> LazyList<std::invoke_result_t<F, const T&>> {
    using U = std::invoke_result_t<F, const T&>;
    return LazyList<U>([ll, f]() -> typename LazyList<U>::Step {
        const auto& s = ll.step();
        if (!s) return std::nullopt;
        return std::pair{f(s->first), map(s->second, f)};
    });
}

template <typename T, typename P> LazyList<T> filter(LazyList<T> ll, P p) {
    return LazyList<T>([ll, p]() -> typename LazyList<T>::Step {
        LazyList<T> cur = ll;
        while (const auto& s = cur.step()) {        // skip non-matches in a loop
            if (p(s->first)) return std::pair{s->first, filter(s->second, p)};
            auto next = s->second; cur = next;
        }
        return std::nullopt;
    });
}

template <typename T> LazyList<T> append(LazyList<T> a, std::function<LazyList<T>()> b) {
    return LazyList<T>([a, b]() -> typename LazyList<T>::Step {
        const auto& s = a.step();
        if (!s) return b().step();
        return std::pair{s->first, append(s->second, b)};
    });
}

Each one returns a new node holding a lambda, and recursion happens only inside the lambda, so building a pipeline does no work. The full listing also has flat_map.

5.5Watching It Run

Instrument the pipeline from 5.1 to log each call:

auto pipeline = filter(map(xs, plus10_logged), is_even_logged);
// nothing printed yet: the pipeline is only a description
to_vector(pipeline);   // {12, 14}
map 1 → filter 11 (odd, skip)
map 2 → filter 12 (keep)
map 3 → filter 13 (odd, skip)
map 4 → filter 14 (keep)

Each element goes all the way through the pipeline before the next element is touched. No intermediate containers are built. That's the fused loop we wanted, assembled from separate combinators. The full listing checks this exact trace with an assert.

It also means find does only as much work as needed, even written with filter:

template <typename T, typename P> std::optional<T> find(LazyList<T> ll, P p) {
    auto matches = filter(ll, p);
    const auto& s = matches.step();      // forces only up to the first match
    return s ? std::optional<T>(s->first) : std::nullopt;
}

5.6Infinite Lists, and unfold

Nothing runs until it's needed, so a lazy list can be infinite:

LazyList<int> from(int n) {
    return LazyList<int>([n]() -> LazyList<int>::Step { return std::pair{n, from(n + 1)}; });
}

to_vector(take(from(5), 3));                    // {5, 6, 7}
find(from(1), [](int x) { return x * x > 50; }); // 8

fold_right consumes a list down to a value. Its opposite, unfold, produces a list from a seed. You give it a starting state and a function that says either "stop" or "here's the next element and the next state":

template <typename A, typename S, typename F>     // F: S -> optional<pair<A, S>>
LazyList<A> unfold(S state, F f) {
    return LazyList<A>([state, f]() -> typename LazyList<A>::Step {
        auto r = f(state);
        if (!r) return std::nullopt;
        return std::pair{r->first, unfold<A>(r->second, f)};
    });
}

LazyList<long> fibs() {
    return unfold<long>(std::pair{0L, 1L}, [](std::pair<long, long> s) {
        return std::optional{std::pair{s.first, std::pair{s.second, s.first + s.second}}};
    });
}
template <typename A> LazyList<A> continually(A a) {
    return unfold<A>(a, [](A s) { return std::optional{std::pair{s, s}}; });
}

Functions like unfold that produce data lazily are called corecursive. A corecursive function doesn't need to terminate; it just needs to keep producing.

Two C++-specific traps. (1) On an infinite list, anything that looks at every element (to_vector, for_all when it's true) never finishes. Laziness lets you describe infinite data; you still have to consume it with something that stops. (2) Don't build ones as a list whose tail points back to itself. With shared_ptr, a cycle is never freed: that's a memory leak. Generating it with unfold avoids the cycle. Garbage-collected languages, including the book's Scala, can use the self-referential version safely.

Write map and take using unfold. What does the state need to hold?

Show solution
template <typename T, typename F> auto map_via_unfold(LazyList<T> ll, F f) {
    using U = std::invoke_result_t<F, const T&>;
    return unfold<U>(ll, [f](LazyList<T> cur) -> std::optional<std::pair<U, LazyList<T>>> {
        const auto& s = cur.step();
        if (!s) return std::nullopt;
        return std::pair{f(s->first), s->second};
    });
}

template <typename T> LazyList<T> take_via_unfold(LazyList<T> ll, int n) {
    return unfold<T>(std::pair{ll, n}, [](std::pair<LazyList<T>, int> st)
                     -> std::optional<std::pair<T, std::pair<LazyList<T>, int>>> {
        if (st.second <= 0) return std::nullopt;
        const auto& s = st.first.step();
        if (!s) return std::nullopt;
        return std::pair{s->first, std::pair{s->second, st.second - 1}};
    });
}

The state is whatever you need to remember between steps: the rest of the input, plus a counter for take.

5.7You Already Use This: std::ranges Views

C++20 views are lazy, fused pipelines built on the same idea:

auto r = std::views::iota(1)                                   // infinite: 1, 2, 3, ...
       | std::views::transform([](int x) { return x + 10; })
       | std::views::filter([](int x) { return x % 2 == 0; })
       | std::views::take(2);
// nothing has run yet
for (int x : r) std::cout << x << ' ';                        // 12 14

Building r computes nothing. Iterating pulls elements through the whole pipeline one at a time, and take(2) stops the infinite iota. Two differences from our LazyList: views aren't memoised (iterate twice and the work is done twice), and they hold references to their source, so a view must not outlive the container it views.

The big idea is separating the description of a computation from its evaluation. A lazy list or a view says what sequence; the consumer decides how much of it to compute. Chapter 7 separates "what to compute in parallel" from scheduling it; Chapter 13 separates "what effects to perform" from performing them.

Caching a computed value so it's evaluated at most once.

View

  • Thunks delay evaluation; Lazy adds caching.
  • A lazy list with a lazy fold_right can stop early and fuses pipelines into one pass.
  • Laziness allows infinite structures, as long as the consumer stops. Avoid shared_ptr cycles.
  • unfold generates lists from a seed; it's the dual of fold.
  • std::ranges views are the standard's lazy pipelines.
