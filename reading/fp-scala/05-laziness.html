Strictness & Laziness

Chaining map and filter on lists builds a new list at every step. By delaying evaluation we can fuse those steps into one pass, stop early, and even describe infinite sequences. We'll build a lazy list of our own to see how.

5.1The Problem: Intermediate Lists

List(1, 2, 3, 4).map(_ + 10).filter(_ % 2 == 0).map(_ * 3)

This builds three lists: one after map, one after filter, and the final one. Each step traverses the whole input before the next starts. For four elements it doesn't matter; for a million, or for a pipeline that only needs the first result, it's wasteful. A hand-written while loop would do it in one pass.

We want to write the pipeline with high-level combinators but have it run like the fused loop. The key is non-strictness.

5.2Strict and Non-Strict

A function is strict in a parameter if it always evaluates that argument. Most functions are. Some aren't, and you already use them:

false && { println("!!"); true }    // prints nothing
if input.isEmpty then sys.error("empty") else input   // only one branch runs

&&, || and if are non-strict. We can write our own non-strict functions with by-name parameters, which you saw in Chapter 4:

def if2[A](cond: Boolean, onTrue: => A, onFalse: => A): A =
  if cond then onTrue else onFalse

if2(false, sys.error("fail"), 3)   // 3; the error is never evaluated

Under the hood, a by-name argument is passed as a thunk: a zero-argument function () => A the callee calls when it needs the value.

Evaluated each time, unless cached

def maybeTwice(b: Boolean, i: => Int) = if b then i + i else 0

maybeTwice(true, { println("hi"); 1 + 41 })
// prints "hi" TWICE, returns 84

A by-name parameter is re-evaluated at every reference. To evaluate once and remember, use lazy val:

def maybeTwice2(b: Boolean, i: => Int) =
  lazy val j = i          // not evaluated yet
  if b then j + j else 0  // evaluated on first use, then cached

maybeTwice2(true, { println("hi"); 1 + 41 })   // prints "hi" once

A thunk is a std::function<A()>; a lazy val is a thunk plus std::call_once and a cached result. Scala generates the thread-safe initialisation for you.

5.3A Lazy List

Take the list from Chapter 3 and make the head and tail thunks:

enum LazyList[+A]:
  case Empty
  case Cons(h: () => A, t: () => LazyList[A])

object LazyList:
  // "smart constructor": caches head and tail so each is computed at most once
  def cons[A](hd: => A, tl: => LazyList[A]): LazyList[A] =
    lazy val head = hd
    lazy val tail = tl
    Cons(() => head, () => tail)

  def empty[A]: LazyList[A] = Empty

  def apply[A](as: A*): LazyList[A] =
    if as.isEmpty then empty
    else cons(as.head, apply(as.tail*))

Use cons, never Cons directly. It's the smart constructor that adds caching. Without it, each time someone looked at the head, the head expression would run again.

A first helper, to see what's inside:

  def toList: List[A] =
    @annotation.tailrec
    def go(ll: LazyList[A], acc: List[A]): List[A] = ll match
      case Cons(h, t) => go(t(), h() :: acc)
      case Empty      => acc.reverse
    go(this, Nil)

(This and the following methods go inside enum LazyList.)

Write take(n: Int): LazyList[A] and takeWhile(p: A => Boolean): LazyList[A]. They should do no work until the result is consumed.

Show solution
  def take(n: Int): LazyList[A] = this match
    case Cons(h, t) if n > 1  => LazyList.cons(h(), t().take(n - 1))
    case Cons(h, _) if n == 1 => LazyList.cons(h(), LazyList.empty)
    case _                    => LazyList.empty

  def takeWhile(p: A => Boolean): LazyList[A] = this match
    case Cons(h, t) if p(h()) => LazyList.cons(h(), t().takeWhile(p))
    case _                    => LazyList.empty

The recursive call sits inside cons's by-name tail, so it doesn't run until someone asks for the tail. Calling take(3) just returns one Cons immediately.

5.4A Lazy Fold Can Stop Early

Here's the trick that makes everything work. Write foldRight with a by-name second argument to f:

  def foldRight[B](acc: => B)(f: (A, => B) => B): B = this match
    case Cons(h, t) => f(h(), t().foldRight(acc)(f))
    case Empty      => acc

The recursion t().foldRight(acc)(f) is passed to f unevaluated. If f doesn't look at it, the rest of the list is never touched:

  def exists(p: A => Boolean): Boolean =
    foldRight(false)((a, b) => p(a) || b)    // || doesn't evaluate b if p(a)

exists stops at the first match, like a loop with break, but it's a fold.

Using foldRight, write forAll, map, filter, append and flatMap. They must stay lazy.

Show solution
  def forAll(p: A => Boolean): Boolean =
    foldRight(true)((a, b) => p(a) && b)

  def map[B](f: A => B): LazyList[B] =
    foldRight(LazyList.empty[B])((a, acc) => LazyList.cons(f(a), acc))

  def filter(p: A => Boolean): LazyList[A] =
    foldRight(LazyList.empty[A])((a, acc) => if p(a) then LazyList.cons(a, acc) else acc)

  def append[A2 >: A](that: => LazyList[A2]): LazyList[A2] =
    foldRight(that)((a, acc) => LazyList.cons(a, acc))

  def flatMap[B](f: A => LazyList[B]): LazyList[B] =
    foldRight(LazyList.empty[B])((a, acc) => f(a).append(acc))

In each, acc is by-name, and it's passed into cons's by-name tail, so it stays unevaluated.

5.5Watching It Run

Trace the pipeline from 5.1 on a lazy list, asking for the result with toList:

LazyList(1,2,3,4).map(_ + 10).filter(_ % 2 == 0).toList

map 1 → 11 · filter 11 → odd, skip
map 2 → 12 · filter 12 → even, emit 12
map 3 → 13 · filter 13 → odd, skip
map 4 → 14 · filter 14 → even, emit 14
→ List(12, 14)

Each element goes all the way through the pipeline before the next element is touched. No intermediate lists are built. That's the fused loop we wanted, assembled from separate combinators. Lazy lists are sometimes called "first-class loops".

It also means that something like find does only as much work as needed:

  def find(p: A => Boolean): Option[A] = filter(p).headOption

Even though it's written with filter, it stops at the first match.

5.6Infinite Lists

Since nothing runs until it's needed, a lazy list can be infinite:

val ones: LazyList[Int] = LazyList.cons(1, ones)

ones.take(5).toList           // List(1, 1, 1, 1, 1)
ones.exists(_ % 2 != 0)       // true
ones.map(_ + 1).exists(_ % 2 == 0)   // true
ones.forAll(_ == 1)           // never terminates! (stack overflow)

On an infinite list, anything that must look at every element (forAll when it's true, toList, length) never finishes. Laziness lets you describe infinite data. You still have to consume it with something that stops.

Write continually[A](a: A): LazyList[A], from(n: Int): LazyList[Int] (n, n+1, n+2, ...) and fibs: LazyList[Int] (0, 1, 1, 2, 3, 5, ...).

Show solution
def continually[A](a: A): LazyList[A] =
  lazy val single: LazyList[A] = LazyList.cons(a, single)
  single

def from(n: Int): LazyList[Int] =
  LazyList.cons(n, from(n + 1))

val fibs: LazyList[Int] =
  def go(cur: Int, next: Int): LazyList[Int] =
    LazyList.cons(cur, go(next, cur + next))
  go(0, 1)

continually refers to itself, so it's one node pointing to itself in memory. from creates new nodes as you go.

5.7unfold: the General Generator

foldRight consumes a list down to a value. Its opposite, unfold, produces a list from a seed. You give it a starting state and a function that either says "stop" or gives the next element and the next state:

def unfold[A, S](state: S)(f: S => Option[(A, S)]): LazyList[A] =
  f(state) match
    case Some((a, next)) => LazyList.cons(a, unfold(next)(f))
    case None            => LazyList.empty

val fibsViaUnfold = unfold((0, 1)) { case (cur, next) => Some((cur, (next, cur + next))) }
def fromViaUnfold(n: Int) = unfold(n)(s => Some((s, s + 1)))

Folding consumes data; unfolding produces it. Functions that consume are recursive; functions like unfold that produce lazily are called corecursive. A corecursive function doesn't need to terminate. It just needs to keep producing.

Write map and take using unfold.

Show solution
  def mapViaUnfold[B](f: A => B): LazyList[B] =
    unfold(this):
      case Cons(h, t) => Some((f(h()), t()))
      case Empty      => None

  def takeViaUnfold(n: Int): LazyList[A] =
    unfold((this, n)):
      case (Cons(h, t), k) if k > 0 => Some((h(), (t(), k - 1)))
      case _                        => None

The state is whatever you need to remember: the rest of the list, plus a counter for take.

5.8The Big Idea: Description vs Evaluation

Step back. A lazy list is a description of a computation that produces elements. Building it does nothing. Running it (toList, exists, take(5).toList) decides how much of that description to evaluate.

Separating the description of a computation from its evaluation is the theme of the whole book. Lazy lists separate "what sequence" from "how much of it". Chapter 7 separates "what to compute in parallel" from "how to schedule it". Chapter 13 separates "what effects to perform" from "performing them".

Scala's standard LazyList works like ours: lazy, memoised, with all the combinators.

Strict / non-strict
Whether a function always evaluates an argument or may skip it.
Thunk
An unevaluated expression packaged as () => A.
Memoisation
Caching a computed value so it's evaluated at most once (lazy val).
Smart constructor
A function that builds a value while enforcing extra invariants, here caching.
Corecursion / unfold
Producing data step by step from a seed, possibly forever.
  • By-name parameters and lazy val delay evaluation.
  • A lazy list with a lazy foldRight can stop early and fuses pipelines into one pass.
  • Laziness allows infinite structures, as long as the consumer stops.
  • unfold generates lists from a seed; it's the dual of fold.
