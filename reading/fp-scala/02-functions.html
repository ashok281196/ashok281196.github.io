Functions, Recursion & Types

Loops without mutation, functions that take and return functions, and generic functions so constrained by their types that there's only one way to write them.

2.1Loops Become Recursion

If we can't mutate a counter, how do we loop? Write a function that calls itself with the next value of the counter. The loop variables become parameters.

// imperative
long factorial_loop(int n) {
    long acc = 1;
    for (int i = n; i > 0; --i) acc *= i;
    return acc;
}

// recursive: i and acc become parameters
long factorial_go(int i, long acc) {
    if (i <= 0) return acc;
    return factorial_go(i - 1, acc * i);
}
long factorial(int n) { return factorial_go(n, 1); }

Read factorial_go as a loop body: "if we're done, return the accumulator; otherwise go round again with i - 1 and an updated accumulator." An inner function with an accumulator is how most FP loops are written.

Tail calls, and where C++ differs

In factorial_go, the recursive call is the last thing the function does. Nothing waits for its result. That's a tail call, and a tail call can reuse the current stack frame, so it's really a jump: a loop.

Compare:

long factorial_naive(int n) {
    return n <= 0 ? 1 : n * factorial_naive(n - 1);   // must multiply AFTER the call returns
}

Each frame waits to multiply by n, so deep inputs overflow the stack.

Here's the catch: C++ doesn't guarantee tail-call elimination. GCC and Clang usually do it at -O2, but not at -O0, not when a destructor must run after the call, and not when an argument's address escapes. Clang has [[clang::musttail]] to require it; standard C++ has nothing. So in C++:

  • Use accumulator-style recursion freely when the depth is small (trees, parsers).
  • For loops over large or unbounded inputs, write the loop, or use an algorithm like std::accumulate, and keep the function pure by keeping the mutation local.
  • Chapter 13 shows trampolining, which makes deep recursion safe without relying on the optimiser.

Scala's @tailrec annotation makes the compiler prove a self-recursive function is a loop, or fail to compile. That's why the book writes almost every loop as tail recursion. In C++ you get the same reasoning (the parameters are the loop state) but the guarantee comes from writing the loop.

Write long fib(int n) in accumulator style, with fib(0) = 0, fib(1) = 1.

Show solution
long fib_go(int k, long prev, long cur) {
    return k == 0 ? prev : fib_go(k - 1, cur, prev + cur);
}
long fib(int n) { return fib_go(n, 0, 1); }

Two accumulators: the pair (prev, cur) slides along the sequence. Each step is (a, b) → (b, a + b).

2.2Higher-Order Functions

Functions are values: you can pass them, return them and store them. A function that takes or returns another function is a higher-order function (HOF). The STL is full of them: std::sort takes a comparator, std::transform takes a function.

std::string format_abs(int x)       { return "The absolute value of " + ...; }
std::string format_factorial(int n) { return "The factorial of " + ...; }

They differ only in a name and a function. Make the differences parameters:

std::string format_result(const std::string& name, int n,
                          const std::function<long(int)>& f) {
    return "The " + name + " of " + std::to_string(n) + " is " + std::to_string(f(n));
}

format_result("absolute value", -42, [](int x) { return long(std::abs(x)); });
format_result("factorial", 7, factorial);

The basic FP move: whatever varies becomes a function parameter.

std::function is convenient but type-erased: it may heap-allocate and always calls indirectly. In generic code, prefer a template parameter (template <typename F>, or std::invocable with a concept) so the lambda can be inlined. Use std::function when you need to store callables of different types in one place.

2.3Polymorphic Functions

A search that only works on strings:

int find_first(std::span<const std::string> ss, const std::string& key) {
    for (size_t i = 0; i < ss.size(); ++i)
        if (ss[i] == key) return static_cast<int>(i);
    return -1;
}

Nothing about the algorithm depends on strings. Generalise the element type to A and, since we can't compare an unknown A to a key, take a predicate:

template <typename A, typename Pred>
    requires std::predicate<Pred, const A&>
int find_first(std::span<const A> as, Pred p) {
    for (size_t i = 0; i < as.size(); ++i)
        if (p(as[i])) return static_cast<int>(i);
    return -1;
}

std::vector xs{7, 9, 13};
find_first<int>(xs, [](int x) { return x == 9; });   // 1

A function template that works the same way for every A is parametrically polymorphic. If it only uses what the concept promises, it can't inspect or create As; it can only move around the ones it's given.

Scala checks a generic function once, at its definition, and only allows what the signature promises. C++ templates are checked at each instantiation, so a template can secretly call a.size() on its A. Concepts close most of that gap. In this book, treat a template's concept as its whole contract, the way Scala treats a type parameter.

2.4Following the Types to the Implementation

The less a function knows about its types, the fewer ways there are to write it. Sometimes there's exactly one. Take:

partial1 : (A, (A, B) → C) → (B → C)
  1. We must return a function from B. So start with a lambda [...](B b) { ... }.
  2. Inside we must produce a C. The only thing that produces a C is f.
  3. f needs an A and a B. We have a (capture it) and b.
template <typename A, typename F>
auto partial1(A a, F f) {
    return [a, f](auto b) { return f(a, b); };
}

auto add = [](int a, int b) { return a + b; };
partial1(10, add)(5);   // 15

No cleverness: the types left one option. You'll use this technique all the way through the book.

With a generic signature, ask: what do I have, what do I need, and which values produce the thing I need? Then fill the holes one at a time. Returning a lambda that captures what it needs is how C++ "returns a function".

Implement curry: from a function of (A, B) → C, make A → (B → C).

Show solution
template <typename F>
auto curry(F f) {
    return [f](auto a) { return [f, a](auto b) { return f(a, b); }; };
}

curry(add)(2)(3);   // 5

Capture by value. A lambda returned from a function that captured by reference would dangle.

Implement the reverse: from A → B → C, make (A, B) → C.

Show solution
template <typename F>
auto uncurry(F f) {
    return [f](auto a, auto b) { return f(a)(b); };
}

Implement compose(f, g), returning a function that takes a and returns f(g(a)).

Show solution
template <typename F, typename G>
auto compose(F f, G g) {
    return [f, g](auto a) { return f(g(a)); };
}

// left-to-right version reads like a pipeline
template <typename F, typename G>
auto and_then(F f, G g) { return compose(g, f); }

2.5Pipelines

Once functions compose, you can describe a transformation without mentioning the data:

auto normalise = and_then(trim, lower);
normalise("  HeLLo ");   // "hello"

C++20 ranges use the same idea with |: v | std::views::filter(p) | std::views::transform(f) composes two transformations into one before any data flows. We'll see in Chapter 5 that ranges are also lazy, which is the next big idea.
