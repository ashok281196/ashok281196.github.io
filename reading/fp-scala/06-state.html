Purely Functional State

How do you write a random number generator, a parser position or a simulation step without mutation? Return the new state with the result. Then make that pattern pleasant with a State type, and catch a first glimpse of a monad.

6.1The Problem With rand()

std::mt19937 gen(42);
gen();   // 1608637542
gen();   // 3421126067 — same expression, different value

Calling the engine isn't RT: operator() updates the engine's hidden state. That hurts in practice. A test of a dice-rolling function fails occasionally; to reproduce it you need the exact sequence of states the engine went through, but the engine is shared, and every other caller advanced it too.

6.2Make the State Explicit

Don't update the state in place. Return the new state alongside the value, and let the caller decide what to do with it.

struct RNG {
    std::uint64_t seed;
    // a linear congruential generator with java.util.Random's constants
    std::pair<int, RNG> next_int() const {
        std::uint64_t new_seed = (seed * 0x5DEECE66DULL + 0xBULL) & 0xFFFFFFFFFFFFULL;
        int n = static_cast<int>(static_cast<std::uint32_t>(new_seed >> 16));
        return {n, RNG{new_seed}};    // a value AND the generator to use next
    }
};

RNG rng{42};
auto [n1, rng2] = rng.next_int();    // 16159453
auto [n2, rng3] = rng2.next_int();   // -1281479697
rng.next_int().first;                // 16159453 again: fully reproducible

next_int is a pure function from a state to a (value, new state) pair. Same input, same output. To get a different number, pass the new generator. (Note the unsigned arithmetic: the same formula with signed 64-bit integers overflows, which is undefined behaviour in C++. The listing was checked with the undefined-behaviour sanitizer.)

The old engine is a shared deck that anyone can draw from. The new RNG hands you the top card and a new deck without that card. The old deck still exists and still has the same top card, so anyone holding it draws the same card.

Write non_negative_int(RNG) returning a value in [0, INT_MAX], and random_double(RNG) in [0, 1). Careful: INT_MIN has no positive counterpart.

Show solution
std::pair<int, RNG> non_negative_int(RNG rng) {
    auto [i, r] = rng.next_int();
    return {i < 0 ? -(i + 1) : i, r};
}
std::pair<double, RNG> random_double(RNG rng) {
    auto [i, r] = non_negative_int(rng);
    return {i / (static_cast<double>(INT_MAX) + 1), r};
}

-(i + 1) maps -1 → 0, ..., INT_MIN → INT_MAX, so every negative maps to a distinct non-negative without overflowing.

6.3The Pain of Threading State

std::pair<std::tuple<int, double, int>, RNG> int_double_int(RNG rng) {
    auto [i1, r1] = rng.next_int();
    auto [d,  r2] = random_double(r1);
    auto [i2, r3] = r2.next_int();
    return {{i1, d, i2}, r3};
}

It works, but it's tedious and fragile. Pass r1 twice by accident and two "random" values come out identical. The pattern is always the same: take a state, produce a value and a new state, feed the new state to the next step. When code repeats a pattern, extract it.

6.4A Type for State Actions

Every function above has the shape RNG → (A, RNG). Name it:

template <typename A>
using Rand = std::function<std::pair<A, RNG>(RNG)>;

const Rand<int> int_ = [](RNG r) { return r.next_int(); };

A Rand<A> is a description of how to produce a random A: a program waiting for a generator. Now write combinators that build bigger Rands from smaller ones and do the threading for us:

template <typename A>
Rand<A> unit(A a) { return [a](RNG r) { return std::pair{a, r}; }; }   // constant; state passes through

template <typename A, typename F>
auto map(Rand<A> s, F f) -> Rand<std::invoke_result_t<F, A>> {
    return [s, f](RNG rng) {
        auto [a, rng2] = s(rng);
        return std::pair{f(a), rng2};
    };
}

const Rand<int> non_negative_even =
    map(Rand<int>(non_negative_int), [](int i) { return i - i % 2; });

Look at map: the threading is written once, inside the combinator. Users of map never touch a generator.

Write map2(ra, rb, f), then sequence (a vector of Rands to a Rand of a vector), then ints(count).

Show solution
template <typename A, typename B, typename F>
auto map2(Rand<A> ra, Rand<B> rb, F f) -> Rand<std::invoke_result_t<F, A, B>> {
    return [ra, rb, f](RNG rng) {
        auto [a, r1] = ra(rng);
        auto [b, r2] = rb(r1);
        return std::pair{f(a, b), r2};
    };
}

template <typename A>
Rand<std::vector<A>> sequence(std::vector<Rand<A>> rs) {
    return [rs](RNG rng) {
        std::vector<A> out;
        for (const auto& r : rs) { auto [a, next] = r(rng); out.push_back(a); rng = next; }
        return std::pair{out, rng};
    };
}

Rand<std::vector<int>> ints(int count) {
    return sequence(std::vector<Rand<int>>(count, int_));
}

Compare sequence with traverse for optionals in Chapter 4: walk the inputs, combine each result with what we have so far, and pass something along. Only the "something" changed.

6.5When map2 Isn't Enough: flat_map

Generate a number in [0, n). The obvious way, map(non_negative_int, i ↦ i % n), is slightly biased: unless INT_MAX + 1 is a multiple of n, small numbers come up more often. The fix is to retry when the number lands in the uneven top part of the range. But retrying means the next step depends on the value we got, and map can't choose which Rand to run next. We need:

template <typename A, typename F>                       // F: A -> Rand<B>
auto flat_map(Rand<A> r, F f) -> std::invoke_result_t<F, A> {
    return [r, f](RNG rng) {
        auto [a, rng2] = r(rng);
        return f(a)(rng2);                              // the value chooses the next action
    };
}

Rand<int> non_negative_less_than(int n) {
    return flat_map(Rand<int>(non_negative_int), [n](int i) -> Rand<int> {
        int mod = i % n;
        if (i + (n - 1) - mod >= 0) return unit(mod);   // not in the biased region
        return non_negative_less_than(n);               // retry with the next state
    });
}
map transforms a result. map2 combines independent results. flat_map lets a result decide what happens next. It's strictly more powerful: map and map2 can both be written using flat_map and unit.

std::uniform_int_distribution does the same rejection trick inside, with a mutable engine. The book's nonNegativeLessThan is exactly this function, written with flatMap.

Reimplement map using only flat_map and unit.

Show solution
template <typename A, typename F>
auto map_via_flat_map(Rand<A> r, F f) -> Rand<std::invoke_result_t<F, A>> {
    using B = std::invoke_result_t<F, A>;
    return flat_map(r, [f](A a) { return unit<B>(f(a)); });
}

Same shape as map2 for optionals in Chapter 4: flat_map on the outside, wrap the result with unit.

6.6Generalising: State<S, A>

Nothing in unit, map, map2 or flat_map used anything specific to random numbers. They work for any state. Replace RNG with a type parameter S, and make the combinators members so they chain left to right:

template <typename S, typename A>
class State {
    std::function<std::pair<A, S>(S)> run_;
public:
    using value_type = A;
    explicit State(std::function<std::pair<A, S>(S)> f) : run_(std::move(f)) {}
    std::pair<A, S> run(S s) const { return run_(std::move(s)); }

    static State unit(A a) { return State([a](S s) { return std::pair{a, std::move(s)}; }); }

    template <typename F>                                   // F: A -> State<S, B>
    auto flat_map(F f) const -> std::invoke_result_t<F, A> {
        auto self = *this;
        return std::invoke_result_t<F, A>([self, f](S s) {
            auto [a, s1] = self.run(std::move(s));
            return f(a).run(std::move(s1));
        });
    }

    template <typename F>                                   // F: A -> B
    auto map(F f) const -> State<S, std::invoke_result_t<F, A>> {
        using B = std::invoke_result_t<F, A>;
        return flat_map([f](A a) { return State<S, B>::unit(f(a)); });
    }
};

template <typename S> State<S, S> get() {                  // read the state
    return State<S, S>([](S s) { return std::pair{s, s}; });
}
template <typename S> State<S, std::monostate> set(S s) {  // replace it
    return State<S, std::monostate>([s](S) { return std::pair{std::monostate{}, s}; });
}
template <typename S, typename F> State<S, std::monostate> modify(F f) {
    return get<S>().flat_map([f](S s) { return set<S>(f(s)); });
}

get, set and modify are the primitives. std::monostate stands in for "no interesting value" (the book's Unit). Rand<A> is now just State<RNG, A>.

The book writes opaque type State[S, +A] = S => (A, S) and composes steps with a for-comprehension that reads almost like imperative code. C++ has no such syntax, so we chain .flat_map(...).map(...). The meaning is identical: each step receives the state the previous step left behind.

6.7Worked Example: A Turnstile

A metro turnstile starts locked. Inserting a token unlocks it (if locked). Pushing through an unlocked gate locks it again and counts a passenger; anything else does nothing. Inputs arrive as a list; we want the final counts.

enum class Input { Token, Push };
struct Gate { bool locked; int tokens; int passengers; };

Gate step(Input i, Gate g) {                       // the rules: a plain pure function
    if (i == Input::Token && g.locked)  return {false, g.tokens + 1, g.passengers};
    if (i == Input::Push  && !g.locked) return {true, g.tokens, g.passengers + 1};
    return g;
}

State<Gate, std::pair<int, int>> simulate(std::vector<Input> inputs) {
    return traverse<Gate>(inputs, [](Input i) {
               return modify<Gate>([i](Gate g) { return step(i, g); });
           })
        .flat_map([](auto) { return get<Gate>(); })
        .map([](Gate g) { return std::pair{g.tokens, g.passengers}; });
}

simulate({Input::Token, Input::Push, Input::Push, Input::Token, Input::Push})
    .run(Gate{true, 0, 0});
// ({2, 2}, Gate{true, 2, 2})

The rules live in step, which is trivial to unit-test. The sequencing lives in State. The simulation is a value you can run against any starting gate, as many times as you like.

Write traverse<S>(as, f), where f returns a State<S, B> for each input, producing a State<S, vector<B>>. It must handle 200,000 inputs.

Show solution
template <typename S, typename A, typename F>
auto traverse(std::vector<A> as, F f)
    -> State<S, std::vector<typename std::invoke_result_t<F, A>::value_type>> {
    using B = typename std::invoke_result_t<F, A>::value_type;
    return State<S, std::vector<B>>([as, f](S s) {
        std::vector<B> out;
        for (const auto& a : as) {
            auto [b, s2] = f(a).run(std::move(s));
            out.push_back(b);
            s = std::move(s2);
        }
        return std::pair{out, s};
    });
}

A fold of map2s would be correct too, but running it nests one function call per element and overflows the stack on long inputs. The loop is still pure: the mutation of s and out is local to one run (Exercise 1.3).

Don't reuse an old state. auto [a, _] = int_(rng); auto [b, __] = int_(rng); gives a == b. That's not a bug in RNG; it's exactly what RT promises. Composing with State combinators instead of passing generators by hand removes this whole class of mistake.

Five different types, the same five operations, and each time map, map2 and sequence could be written from unit and flat_map. That's not a coincidence. In Part III we write those derived functions once, for all of these types. For now, keep noticing.

State action
A function S → (A, S): take a state, produce a value and the next state.
get / set / modify
The primitive State actions that read, replace and update the state.
Combinator
A function that builds new values of a type from existing ones (map, map2, flat_map).
std::monostate
A type with one value, used for "this step returns nothing interesting".
  • Pure state: return the new state along with the result.
  • Name the shape S → (A, S) and write the threading once, in combinators.
  • flat_map lets one step's result choose the next step.
  • C++ chains .flat_map().map() where Scala uses a for-comprehension.
  • The same operations keep appearing on every type. Part III explains why.
