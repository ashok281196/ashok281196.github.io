Purely Functional State

How do you write a random number generator, a parser position or a game loop without mutation? Return the new state with the result. Then make that pattern pleasant with a State type, and meet your first glimpse of a monad.

6.1The Problem With Random

val rng = scala.util.Random()
rng.nextInt()   // -1151252339
rng.nextInt()   // 1957568493  — same expression, different value

nextInt isn't RT: it updates a hidden seed inside rng. That hurts in a practical way. Say a test of a dice-rolling function fails occasionally. To reproduce it you need the exact sequence of states the generator went through, and that state is hidden and was mutated by every other caller.

6.2Make the State Explicit

The fix: don't update the state in place. Return the new state next to the value, and let the caller decide what to do with it.

trait RNG:
  def nextInt: (Int, RNG)   // a value AND the generator to use next

case class SimpleRNG(seed: Long) extends RNG:
  def nextInt: (Int, RNG) =
    // a linear congruential generator, the same constants as java.util.Random
    val newSeed = (seed * 0x5DEECE66DL + 0xBL) & 0xFFFFFFFFFFFFL
    val n = (newSeed >>> 16).toInt
    (n, SimpleRNG(newSeed))
val rng = SimpleRNG(42)
val (n1, rng2) = rng.nextInt    // (16159453, SimpleRNG(...))
val (n2, rng3) = rng2.nextInt   // (-1281479697, ...)
rng.nextInt                     // (16159453, ...) again: fully reproducible

nextInt is now a pure function from a state to a (value, new state) pair. Same input, same output. To get a different number, you pass the new generator.

The old Random is a shared deck of cards that anyone can draw from. The new RNG hands you the top card and a new deck without that card. The old deck still exists and still has the same top card, so anyone holding it gets the same draw.

Write nonNegativeInt(rng: RNG): (Int, RNG) returning a value in [0, Int.MaxValue], and double(rng: RNG): (Double, RNG) in [0, 1). Careful: Int.MinValue has no positive counterpart.

Show solution
def nonNegativeInt(rng: RNG): (Int, RNG) =
  val (i, r) = rng.nextInt
  (if i < 0 then -(i + 1) else i, r)

def double(rng: RNG): (Double, RNG) =
  val (i, r) = nonNegativeInt(rng)
  (i / (Int.MaxValue.toDouble + 1), r)

-(i + 1) maps -1 → 0, ..., Int.MinValue → Int.MaxValue, so every negative maps to a distinct non-negative.

6.3The Pain of Threading State

Now generate three random values:

def intDoubleInt(rng: RNG): ((Int, Double, Int), RNG) =
  val (i1, r1) = rng.nextInt
  val (d,  r2) = double(r1)
  val (i2, r3) = r2.nextInt
  ((i1, d, i2), r3)

It works, but it's tedious and easy to get wrong. Pass r1 twice by accident and two values are no longer independent. The pattern is always the same: take a state, produce a value and a new state, feed the new state to the next step. When code repeats a pattern, we extract it.

6.4A Type for "State Actions"

Every function above has the shape RNG => (A, RNG). Give it a name:

type Rand[+A] = RNG => (A, RNG)

val int: Rand[Int] = _.nextInt

A Rand[A] is a description of how to produce a random A: a program waiting for a generator. Now we write combinators that build bigger Rands from smaller ones and do the state threading for us:

def unit[A](a: A): Rand[A] =
  rng => (a, rng)                  // a constant; state passes through

def map[A, B](s: Rand[A])(f: A => B): Rand[B] =
  rng =>
    val (a, rng2) = s(rng)
    (f(a), rng2)

val nonNegativeEven: Rand[Int] =
  map(nonNegativeInt)(i => i - i % 2)

Look at map: the threading is written once, inside the combinator. Users of map never see a generator.

Write map2[A, B, C](ra: Rand[A], rb: Rand[B])(f: (A, B) => C): Rand[C], then sequence[A](rs: List[Rand[A]]): Rand[List[A]], then ints(count: Int): Rand[List[Int]].

Show solution
def map2[A, B, C](ra: Rand[A], rb: Rand[B])(f: (A, B) => C): Rand[C] =
  rng =>
    val (a, r1) = ra(rng)
    val (b, r2) = rb(r1)
    (f(a, b), r2)

def both[A, B](ra: Rand[A], rb: Rand[B]): Rand[(A, B)] =
  map2(ra, rb)((_, _))

def sequence[A](rs: List[Rand[A]]): Rand[List[A]] =
  rs.foldRight(unit(Nil: List[A]))((r, acc) => map2(r, acc)(_ :: _))

def ints(count: Int): Rand[List[Int]] =
  sequence(List.fill(count)(int))

Compare sequence with the one for Option in Chapter 4. Same fold, same map2, same unit-of-empty-list start. Only the type changed.

6.5When map2 Isn't Enough: flatMap

Generate a number in [0, n). The obvious way, map(nonNegativeInt)(_ % n), is slightly biased: if Int.MaxValue isn't a multiple of n, small numbers come up more often. The fix is to retry when the number falls in the uneven top part of the range. But retrying means the next step depends on the value we got, and map can't decide which Rand to run next. We need:

def flatMap[A, B](r: Rand[A])(f: A => Rand[B]): Rand[B] =
  rng =>
    val (a, rng2) = r(rng)
    f(a)(rng2)                  // the value chooses the next action

def nonNegativeLessThan(n: Int): Rand[Int] =
  flatMap(nonNegativeInt): i =>
    val mod = i % n
    if i + (n - 1) - mod >= 0 then unit(mod)   // no overflow: not in the biased region
    else nonNegativeLessThan(n)                // retry with the next state
map transforms a result. map2 combines independent results. flatMap lets a result decide what happens next. It's strictly more powerful: both map and map2 can be written using flatMap and unit.

Reimplement map and map2 using only flatMap and unit.

Show solution
def mapViaFlatMap[A, B](r: Rand[A])(f: A => B): Rand[B] =
  flatMap(r)(a => unit(f(a)))

def map2ViaFlatMap[A, B, C](ra: Rand[A], rb: Rand[B])(f: (A, B) => C): Rand[C] =
  flatMap(ra)(a => map(rb)(b => f(a, b)))

Same shape as map2 for Option: flatMap outside, map inside.

6.6Generalising: State

Nothing in unit, map, map2 or flatMap used anything specific to random numbers. They work for any state. Replace RNG with a type parameter S:

opaque type State[S, +A] = S => (A, S)

object State:
  def apply[S, A](f: S => (A, S)): State[S, A] = f
  def unit[S, A](a: A): State[S, A] = s => (a, s)

  def get[S]: State[S, S] = s => (s, s)              // read the state
  def set[S](s: S): State[S, Unit] = _ => ((), s)    // replace it
  def modify[S](f: S => S): State[S, Unit] =
    for
      s <- get[S]
      _ <- set(f(s))
    yield ()

  extension [S, A](underlying: State[S, A])
    def run(s: S): (A, S) = underlying(s)

    def map[B](f: A => B): State[S, B] =
      flatMap(a => unit(f(a)))

    def map2[B, C](sb: State[S, B])(f: (A, B) => C): State[S, C] =
      for
        a <- underlying
        b <- sb
      yield f(a, b)

    def flatMap[B](f: A => State[S, B]): State[S, B] =
      s =>
        val (a, s1) = underlying(s)
        f(a)(s1)

type Rand[A] = State[RNG, A]

An opaque type is a type alias that's only transparent inside its defining scope. Outside, users can't treat a State as a plain function, so they must use the combinators. At runtime it's still just the function, with no wrapper object.

get, set and modify are the primitives. With them and a for-comprehension, stateful code reads almost like imperative code, but every step is pure.

Think of a State[S, A] as a function you'd write as std::pair<A, S> step(S s), the style you use when you want a deterministic, replayable simulation step with no globals. flatMap is the code that chains steps and passes the state along so you don't have to.

6.7Worked Example: A Turnstile

A metro turnstile is locked. Inserting a token unlocks it (if locked). Pushing through a locked gate does nothing; through an unlocked one locks it again and counts a passenger. Inputs arrive as a list; we want the final counts.

enum Input:
  case Token, Push

case class Gate(locked: Boolean, tokens: Int, passengers: Int)

def step(i: Input)(g: Gate): Gate = (i, g) match
  case (Input.Token, Gate(true, t, p))  => Gate(false, t + 1, p)
  case (Input.Push,  Gate(false, t, p)) => Gate(true, t, p + 1)
  case _                                 => g          // anything else: no change

def simulate(inputs: List[Input]): State[Gate, (Int, Int)] =
  for
    _ <- State.traverse(inputs)(i => State.modify(step(i)))
    g <- State.get[Gate]
  yield (g.tokens, g.passengers)

simulate(List(Input.Token, Input.Push, Input.Push, Input.Token, Input.Push))
  .run(Gate(true, 0, 0))
// ((2, 2), Gate(true, 2, 2))

The rules live in a pure function step that is easy to test on its own. The sequencing lives in State. traverse works on State too (see the exercise).

Add traverse[S, A, B](as: List[A])(f: A => State[S, B]): State[S, List[B]] to the State object. Make it stack-safe for long lists.

Show solution
  def traverse[S, A, B](as: List[A])(f: A => State[S, B]): State[S, List[B]] =
    s =>
      var state = s               // local mutation, invisible to callers
      val out = List.newBuilder[B]
      for a <- as do
        val (b, s2) = f(a).run(state)
        out += b
        state = s2
      (out.result(), state)

The fold-and-map2 version (as.foldRight(unit(Nil))((a, acc) => f(a).map2(acc)(_ :: _))) is correct but nests a function call per element when it runs, so it overflows on long inputs. This version is a loop. It's still pure: the mutation is local to the call (Chapter 1, Exercise 1.3).

Don't reuse an old state. With RNG by hand, val (a, _) = int(rng); val (b, _) = int(rng) gives a == b. That's not a bug in RNG. It's exactly what RT promises. Using State combinators instead of passing generators by hand removes this whole class of mistake.

Five different types, the same five operations, and in each case map, map2 and sequence could be written in terms of unit and flatMap. That's not a coincidence. In Part III we'll write those derived functions once, for all of these types. For now, keep noticing.

State action / state transition
A function S => (A, S): consume a state, produce a value and the next state.
Opaque type
A type alias hidden outside its scope. Type-safe like a wrapper, free at runtime like an alias.
get / set / modify
The primitive State actions that read, replace and update the state.
Combinator
A function that builds new values of a type out of existing ones (map, map2, flatMap).
  • Pure state: return the new state along with the result.
  • Name the shape S => (A, S) and write the threading once, in combinators.
  • flatMap lets one step's result choose the next step.
  • For-comprehensions over State read like imperative code, but stay pure.
  • The same operations keep appearing on every type. Part III explains why.
