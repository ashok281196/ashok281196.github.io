Part II · Functional Design

Designing a Library: Parallelism

Part II is about the design process more than any particular library. We design a small parallel-computation API in C++ from scratch: start from how we'd like to use it, find the primitives, choose a representation late, and use an algebraic law to find a real deadlock, which we then demonstrate and fix.

7.1How Functional Design Works

Object-oriented design usually starts from the representation: which classes, which fields, which methods mutate them. Functional design inverts that:

  1. Write example code using the API you wish you had.
  2. Let the examples tell you what types and functions you need. Leave their bodies empty.
  3. Find the smallest set of primitive functions; express everything else as derived combinators.
  4. Write down laws: equations the functions must satisfy.
  5. Only then pick a representation that satisfies the laws.

A set of types and functions plus the laws that relate them, with the representation left open, is called an algebra. That's what "algebraic design" means.

7.2Starting From an Example

Summing by divide and conquer:

int sum(std::span<const int> ints) {
    if (ints.size() <= 1) return ints.empty() ? 0 : ints[0];
    auto l = ints.first(ints.size() / 2), r = ints.subspan(ints.size() / 2);
    return sum(l) + sum(r);
}

The halves are independent, so they could run in parallel. Invent a type for "a computation that may run in parallel and yields an A": Par<A>. We need to create one and to get its result:

template <typename A> Par<A> unit(A a);     // wrap a value
template <typename A> A get(Par<A> p);      // wait for the result

int sum(std::span<const int> ints) {
    ...
    Par<int> sum_l = unit(sum(l)), sum_r = unit(sum(r));
    return get(sum_l) + get(sum_r);
}

Substitute sum_l and sum_r into the last line: get(unit(sum(l))) + get(unit(sum(r))). Whatever order the compiler evaluates the operands in, one get waits for its half to finish before the other half has even started. Everything runs sequentially. The substitution model just exposed a design flaw: get (waiting) is a side effect, and we called it too early.

This is the classic std::async mistake: std::async(f).get() + std::async(g).get() serialises, because each future is waited on before the next one is created. And a temporary std::future from std::async blocks in its destructor, which can serialise code that looks parallel.

7.3Combine Without Waiting: map2 and fork

Instead of extracting values to add them, combine the parallel computations:

template <typename A, typename B, typename F>
Par<C> map2(Par<A> pa, Par<B> pb, F f);     // C = result of f(A, B)

Par<int> sum(std::span<const int> ints) {
    if (ints.size() <= 1) return unit(ints.empty() ? 0 : ints[0]);
    auto l = ..., r = ...;
    return map2(sum(l), sum(r), std::plus{});
}

The result is a Par<int>, a description. No waiting happens inside sum.

Should unit start a thread? If so, unit(1) wastes a thread on nothing. Better to make forking explicit:

template <typename A> Par<A> unit(A a);                         // already computed; no thread
template <typename A> Par<A> fork(std::function<Par<A>()> pa); // run on a separate logical thread
template <typename A> Par<A> lazy_unit(std::function<A()> a) { // derived!
    return fork<A>([a] { return unit(a()); });
}

Par<int> sum(std::span<const int> ints) {
    if (ints.size() <= 1) return unit(ints.empty() ? 0 : ints[0]);
    auto l = ints.first(ints.size() / 2), r = ints.subspan(ints.size() / 2);
    return map2(fork<int>([l] { return sum(l); }),
                fork<int>([r] { return sum(r); }), std::plus{});
}

Now the programmer decides where parallelism happens, and lazy_unit fell out as a combination of two primitives. fork takes a thunk so that even building the forked computation is deferred.

7.4Separating Description From Running

Where do the threads come from? If fork grabbed a global pool, the library would be hard to test and configure. Instead, Par values are pure descriptions, and running takes a pool you provide: description vs evaluation, again.

Now, finally, choose a representation. A Par needs a pool to run, and running gives a result we can wait on:

template <typename A>
using Par = std::function<std::shared_future<A>(ThreadPool&)>;

template <typename A> Par<A> unit(A a) {
    return [a](ThreadPool&) { std::promise<A> p; p.set_value(a); return p.get_future().share(); };
}

template <typename A> Par<A> fork(std::function<Par<A>()> pa) {
    return [pa](ThreadPool& pool) {
        auto p = std::make_shared<std::promise<A>>();
        auto fut = p->get_future().share();
        pool.submit([pa, p, &pool] { p->set_value(pa()(pool).get()); });   // waits inside the pool
        return fut;
    };
}

template <typename A, typename B, typename F>
auto map2(Par<A> pa, Par<B> pb, F f) -> Par<std::invoke_result_t<F, A, B>> {
    using C = std::invoke_result_t<F, A, B>;
    return [pa, pb, f](ThreadPool& pool) {
        auto fa = pa(pool);           // start both BEFORE waiting on either
        auto fb = pb(pool);
        return std::async(std::launch::deferred,
                          [fa, fb, f]() -> C { return f(fa.get(), fb.get()); }).share();
    };
}

ThreadPool is a 40-line fixed-size pool in the full listing. Note that map2 starts both computations before waiting on either, which is exactly what the naive version got wrong. With a big enough pool, sum of 1..64 returns 2080.

Write async_f(f), turning A → B into A → Par<B>. Then sequence for Par, and par_map(vector<A>, f) that maps in parallel.

Show solution
template <typename A, typename F> auto async_f(F f) {
    using B = std::invoke_result_t<F, A>;
    return [f](A a) { return lazy_unit<B>([f, a] { return f(a); }); };
}

template <typename A> Par<std::vector<A>> sequence(std::vector<Par<A>> ps) {
    Par<std::vector<A>> acc = unit(std::vector<A>{});
    for (auto it = ps.rbegin(); it != ps.rend(); ++it)
        acc = map2(*it, acc, [](A a, std::vector<A> v) { v.insert(v.begin(), a); return v; });
    return acc;
}

template <typename A, typename F> auto par_map(std::vector<A> as, F f) {
    using B = std::invoke_result_t<F, A>;
    std::vector<Par<B>> ps;
    for (auto& a : as) ps.push_back(async_f<A>(f)(a));
    return fork<std::vector<B>>([ps] { return sequence(ps); });
}

Once again sequence is a fold with map2, starting from unit of an empty collection. The outer fork makes par_map return immediately even for a long input.

7.5Laws

A law is an equation that must hold for every input. Laws make "correct" precise, guide the implementation, and (next chapter) become tests.

The map law

Define map(pa, f) as map2(pa, unit(nothing), (a, _) ↦ f(a)). A natural law:

map(unit(x), f) == unit(f(x))

Simplify it, as in algebra. Let f be the identity function: map(unit(x), id) == unit(x). Then generalise unit(x) to any y:

map(y, id) == y

This says map can't change the structure, only the values. And if map is properly generic (it can't inspect A), the original law follows from this simpler one for free. Laws that hold just because of a function's generic type are called free theorems.

The fork law, and a deadlock

fork should only change where something runs, not the result:

fork(x) == x

Try to break it. Run fork(fork(unit(42))) on a pool with one thread.

The outer fork submits a task, which takes the pool's only thread. Inside it, evaluating the inner fork submits a second task to the queue, then the outer task calls .get() on it and waits. The second task needs a thread. The only thread is the one waiting for it. Neither can proceed. (fork(unit(42)) alone is fine, because unit doesn't submit anything.)

auto* pool = new ThreadPool(1);   // leaked on purpose: its thread will be stuck forever
auto fut = fork(fork(unit(42)))(*pool);
fut.wait_for(300ms) == std::future_status::ready;   // false: deadlocked

The full listing runs exactly this and asserts that it deadlocks. With any fixed pool of N threads, enough nested forks deadlock. So the law fork(x) == x doesn't hold for this implementation, and writing the law down is what led us to the bug.

Blocking inside a pool task is the root problem. Any design where a task calls .get() on another task in the same bounded pool can deadlock. You'll find this bug in real code built on nested std::async with a custom executor, on boost::asio::thread_pool, and on Python's ThreadPoolExecutor.

7.6Fixing It: Never Block

Change the representation so nothing ever waits inside the pool. Instead of returning a future you wait on, a Par takes a callback to invoke when the result is ready:

template <typename A> using Callback = std::function<void(A)>;
template <typename A> using Par = std::function<void(ThreadPool&, Callback<A>)>;

template <typename A> Par<A> unit(A a) {
    return [a](ThreadPool&, Callback<A> cb) { cb(a); };
}

template <typename A> Par<A> fork(std::function<Par<A>()> pa) {
    return [pa](ThreadPool& pool, Callback<A> cb) {
        pool.submit([pa, cb, &pool] { pa()(pool, cb); });     // no waiting
    };
}

map2 is the interesting one: it must wait for two callbacks without blocking. Keep a little shared state, and let whichever result arrives second fire the final callback:

template <typename A, typename B, typename F>
auto map2(Par<A> pa, Par<B> pb, F f) -> Par<std::invoke_result_t<F, A, B>> {
    using C = std::invoke_result_t<F, A, B>;
    return [pa, pb, f](ThreadPool& pool, Callback<C> cb) {
        struct Pending { std::mutex m; std::optional<A> a; std::optional<B> b; };
        auto st = std::make_shared<Pending>();
        pa(pool, [st, f, cb](A a) {
            std::unique_lock lk(st->m);
            if (st->b) { auto b = *st->b; lk.unlock(); cb(f(a, b)); }   // second to arrive fires
            else st->a = a;
        });
        pb(pool, [st, f, cb](B b) {
            std::unique_lock lk(st->m);
            if (st->a) { auto a = *st->a; lk.unlock(); cb(f(a, b)); }
            else st->b = b;
        });
    };
}

template <typename A> A run(ThreadPool& pool, Par<A> p) {   // blocks once, OUTSIDE the pool
    std::promise<A> result;
    auto fut = result.get_future();
    p(pool, [&result](A a) { result.set_value(a); });
    return fut.get();
}

Now run(pool, fork(fork(unit(42)))) returns 42 on a single-thread pool, and so does the parallel sum of 10,000 numbers. The listing checks all of this, and ThreadSanitizer reports no data races.

The important part: the API didn't change. unit, fork, map2, sequence, par_map and sum are written exactly the same way. Every program built on the algebra keeps working. That's the payoff of designing the algebra before the representation.

The book's two representations are the same as ours: first ExecutorService => java.util.concurrent.Future[A], then a callback-based Future run through an actor. In C++ the callback style is what std::execution (senders/receivers, C++26) standardises: a sender describes work, and a receiver is the callback it completes into.

7.7Choosing Between Computations

Run one of two parallel computations depending on the result of a first:

template <typename A> Par<A> choice(Par<bool> cond, Par<A> t, Par<A> e);

Then one of N chosen by an int, then one from a std::map. Each time the shape is the same: get a value, use it to choose the next Par. Generalise:

template <typename A, typename F>                  // F: A -> Par<B>
auto flat_map(Par<A> pa, F f) -> std::invoke_result_t<F, A> {
    using PB = std::invoke_result_t<F, A>;
    return PB([pa, f](ThreadPool& pool, auto cb) {
        pa(pool, [f, cb, &pool](A a) { f(a)(pool, cb); });
    });
}

template <typename A> Par<A> choice(Par<bool> cond, Par<A> t, Par<A> e) {
    return flat_map(cond, [t, e](bool b) { return b ? t : e; });
}

We've found flat_map again, by a completely different route.

Write join(Par<Par<A>>) → Par<A> using flat_map. Then explain how flat_map could be written using join and map.

Show solution
template <typename A> Par<A> join(Par<Par<A>> ppa) {
    return flat_map(ppa, [](Par<A> pa) { return pa; });   // "the value IS the next computation"
}

// and the other way round:
// flat_map(pa, f) == join(map(pa, f))

Two equally good choices of primitive. This works for lists (where join is "flatten") and optionals (where it turns optional<optional<A>> into optional<A>) too.

The process: examples → wished-for API → primitives vs derived → laws → representation. Laws catch bugs before tests do, and a well-chosen algebra lets you swap the representation without breaking any users.
Algebra
A set of types and functions plus the laws relating them, independent of representation.
Primitive / derived combinator
Functions that depend on the representation vs functions written only with other combinators.
Law
An equation that must hold for all inputs, like map(y, id) == y.
Free theorem
A law that holds automatically because of a function's generic type.
Continuation / callback
A function to call with a result instead of returning it; the way to avoid blocking.
  • Design from usage examples; choose the representation last.
  • Make waiting and forking explicit and separate from description.
  • State laws. fork(x) == x found a deadlock in the blocking version, and we reproduced it.
  • A callback-based representation fixes it without changing the API.
  • Choosing the next computation from a result leads, again, to flat_map.
