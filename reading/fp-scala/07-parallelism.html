Designing a Library: Parallelism

Part II is about the design process more than any particular library. We design a small parallel-computation API from scratch: start from how we'd like to use it, discover the primitives, choose a representation late, and use algebraic laws to find a real deadlock bug.

7.1How Functional Design Works

In object-oriented design you usually start from the representation: what classes, what fields, what methods mutate them. Functional design inverts this:

  1. Write example code using the API you wish you had.
  2. Let the examples tell you what types and functions you need. Leave their implementations as ???.
  3. Find the smallest set of primitive functions; express everything else as derived combinators.
  4. Write down laws: equations the functions must satisfy.
  5. Only then pick a representation that satisfies the laws.

A set of types, functions and laws, with the representation left abstract, is called an algebra. That's what "algebraic design" means.

7.2Starting From an Example

Summing a sequence by divide and conquer:

def sum(ints: IndexedSeq[Int]): Int =
  if ints.size <= 1 then ints.headOption.getOrElse(0)
  else
    val (l, r) = ints.splitAt(ints.size / 2)
    sum(l) + sum(r)

The two halves are independent, so they could run in parallel. Invent a type for "a computation that may run in parallel and yields an A": Par[A]. We need a way to create one and a way to get the result:

def unit[A](a: => A): Par[A] = ???     // lift a computation, maybe evaluate it on another thread
def get[A](a: Par[A]): A = ???         // wait for the result
def sum(ints: IndexedSeq[Int]): Int =
  if ints.size <= 1 then ints.headOption.getOrElse(0)
  else
    val (l, r) = ints.splitAt(ints.size / 2)
    val sumL: Par[Int] = unit(sum(l))
    val sumR: Par[Int] = unit(sum(r))
    get(sumL) + get(sumR)

Now substitute sumL and sumR into the last line: get(unit(sum(l))) + get(unit(sum(r))). Scala evaluates left to right, so the left get blocks until the left half finishes before the right half even starts. Everything runs sequentially. The substitution model just exposed a design flaw: get is a side effect (waiting) that we called too early.

7.3Combine Without Waiting: map2

Instead of extracting values to add them, combine the parallel computations:

def map2[A, B, C](pa: Par[A], pb: Par[B])(f: (A, B) => C): Par[C] = ???

def sum(ints: IndexedSeq[Int]): Par[Int] =
  if ints.size <= 1 then unit(ints.headOption.getOrElse(0))
  else
    val (l, r) = ints.splitAt(ints.size / 2)
    map2(sum(l), sum(r))(_ + _)

The result is a Par[Int], a description. No waiting happens inside sum.

Should map2 evaluate its arguments eagerly or lazily? And should unit start a thread? If unit always forks, then unit(1) wastes a thread on nothing. Better to make forking explicit:

def unit[A](a: A): Par[A] = ???                 // already-computed value; no thread
def fork[A](a: => Par[A]): Par[A] = ???         // mark: run this on a separate logical thread
def lazyUnit[A](a: => A): Par[A] = fork(unit(a)) // derived!

def sum(ints: IndexedSeq[Int]): Par[Int] =
  if ints.size <= 1 then unit(ints.headOption.getOrElse(0))
  else
    val (l, r) = ints.splitAt(ints.size / 2)
    map2(fork(sum(l)), fork(sum(r)))(_ + _)

Now the programmer decides where parallelism happens, and lazyUnit fell out as a combination of two primitives. That's the design process working.

7.4Separating Description From Running

Where does the thread pool come from? If fork grabbed a global pool, the library would be hard to test and configure. Instead: Par values are pure descriptions, and a separate run function executes them with a pool you provide. Description vs evaluation again.

Now, finally, choose a representation. A Par needs a thread pool to run, and running gives a result we can wait on. Java's ExecutorService and Future fit:

import java.util.concurrent.{ExecutorService, Future, TimeUnit, Callable}

opaque type Par[A] = ExecutorService => Future[A]

object Par:
  extension [A](pa: Par[A]) def run(es: ExecutorService): Future[A] = pa(es)

  def unit[A](a: A): Par[A] = es => UnitFuture(a)

  private case class UnitFuture[A](get: A) extends Future[A]:
    def isDone = true
    def get(timeout: Long, units: TimeUnit) = get
    def isCancelled = false
    def cancel(evenIfRunning: Boolean): Boolean = false

  extension [A](pa: Par[A])
    def map2[B, C](pb: Par[B])(f: (A, B) => C): Par[C] =
      es =>
        val fa = pa(es)
        val fb = pb(es)
        UnitFuture(f(fa.get, fb.get))   // simple version; ignores timeouts

  def fork[A](a: => Par[A]): Par[A] =
    es => es.submit(new Callable[A] { def call = a(es).get })

Note that map2 starts both computations before waiting on either, which is exactly what the naive version in 7.2 got wrong.

This is std::async with explicit launch policy, but with the executor injected. fork is std::launch::async, unit is std::launch::deferred of an already-computed value, and run is where you finally call .get(). The difference is that a Par is a value you can build, pass around and combine before anything starts.

Write asyncF[A, B](f: A => B): A => Par[B], which evaluates f's result asynchronously. Then write parMap[A, B](ps: List[A])(f: A => B): Par[List[B]], mapping over a list in parallel. You'll need a sequence for Par.

Show solution
def asyncF[A, B](f: A => B): A => Par[B] =
  a => lazyUnit(f(a))

def sequence[A](ps: List[Par[A]]): Par[List[A]] =
  ps.foldRight(unit(List.empty[A]))((pa, acc) => pa.map2(acc)(_ :: _))

def parMap[A, B](ps: List[A])(f: A => B): Par[List[B]] =
  fork(sequence(ps.map(asyncF(f))))

Once again, sequence is the same fold with map2 and unit. The outer fork makes parMap return immediately, even for a long list.

7.5Laws

A law is an equation that must hold for every input. Laws make "correct" precise, they guide implementation, and (next chapter) they become tests.

The map law

Define map via map2: pa.map(f) = pa.map2(unit(()))((a, _) => f(a)). A natural law:

unit(x).map(f) == unit(f(x))

Simplify it, as you would in algebra. Set f = identity: unit(x).map(id) == unit(x). Then generalise unit(x) to any y:

y.map(id) == y

This says: map can't change the structure, only the values. And because map is parametrically polymorphic (it can't inspect A), the original law follows from this simpler one for free. Laws like that, which hold just because of the types, are called free theorems.

The fork law, and a deadlock

fork should only change where something runs, not the result:

fork(x) == x

Try to break it. Run with a fixed thread pool of size 1:

val es = java.util.concurrent.Executors.newFixedThreadPool(1)
fork(fork(unit(42))).run(es).get   // DEADLOCK

Trace it. The outer fork submits a task, and that task takes the pool's only thread. Inside it, a(es) evaluates the inner fork, which submits a second task to the queue, and then the outer task calls .get on it and waits. The second task needs a thread to run. The only thread is the one waiting for it. Neither can proceed. (fork(unit(42)) alone is fine, because unit doesn't submit anything.)

With any fixed pool of size N, enough nested forks deadlock. The law fork(x) == x doesn't hold for our implementation. Writing the law down is what led us to the bug.

Blocking inside a pool task is the root problem. Any implementation where a task calls .get on another task in the same bounded pool can deadlock. This is the same bug you'd hit with nested std::async on a fixed thread pool, or with futures.wait() inside a Python ThreadPoolExecutor worker.

7.6Fixing It: Never Block

The fix is to change the representation so nothing ever calls get inside the pool. Instead of returning a Java Future you wait on, a Par takes a callback to invoke when the result is ready:

// a result you can register a callback on, instead of blocking
trait Future[+A]:
  private[par] def apply(k: A => Unit): Unit

opaque type Par[+A] = ExecutorService => Future[A]

def unit[A](a: A): Par[A] =
  es => new Future[A] { def apply(cb: A => Unit): Unit = cb(a) }

def fork[A](a: => Par[A]): Par[A] =
  es => new Future[A]:
    def apply(cb: A => Unit): Unit =
      es.submit(new Callable[Unit] { def call = a(es)(cb) })   // no waiting

map2 is the interesting part: it must wait for two callbacks without blocking. The usual approach keeps a small piece of state (has A arrived? has B?) behind a lock or an actor, and calls f when the second arrives. Only the top-level run blocks, once, outside the pool, on a CountDownLatch.

The important part: the API didn't change. unit, fork, map2, sequence and parMap have the same signatures. Every program written against the algebra keeps working. That's the payoff of designing the algebra before the representation.

7.7Choosing Between Computations

Say we want to run one of two parallel computations, depending on the result of a first:

def choice[A](cond: Par[Boolean])(t: Par[A], f: Par[A]): Par[A]

Then one of N, chosen by an Int. Then one from a Map[K, Par[A]]. Each time the shape is the same: get a value, use it to choose the next Par. Generalise:

def flatMap[A, B](pa: Par[A])(f: A => Par[B]): Par[B]

def choice[A](cond: Par[Boolean])(t: Par[A], f: Par[A]): Par[A] =
  flatMap(cond)(b => if b then t else f)

We've found flatMap again, by a completely different route. And it can be split further into join(ppa: Par[Par[A]]): Par[A] plus map: flatMap(pa)(f) = join(pa.map(f)).

Show that flatMap and join can each be written in terms of the other (with map).

Show solution
def join[A](ppa: Par[Par[A]]): Par[A] =
  flatMap(ppa)(pa => pa)        // "the value IS the next computation"

def flatMap[A, B](pa: Par[A])(f: A => Par[B]): Par[B] =
  join(pa.map(f))

Two equally good choices of primitive. This works for List (where join is flatten) and Option too.

The process: example → wished-for API → primitives vs derived → laws → representation. Laws catch bugs before tests do, and a well-chosen algebra lets you swap the representation without breaking users.
Algebra
A set of types and functions plus the laws relating them, independent of representation.
Primitive / derived combinator
Functions that depend on the representation vs functions written using other combinators only.
Law
An equation that must hold for all inputs, like y.map(id) == y.
Free theorem
A law that holds automatically because of a function's polymorphic type.
Continuation / callback
A function to call with the result, instead of returning it. The way to avoid blocking.
  • Design from usage examples, and choose the representation last.
  • Make side effects like waiting and forking explicit and separate from description.
  • State laws. The law fork(x) == x found a deadlock in the blocking implementation.
  • A non-blocking, callback-based representation fixes it without changing the API.
  • Choosing a computation based on a result leads, again, to flatMap.
