Part IV · Effects and I/O

Effects, IO & Local Mutation

How a pure program talks to the world. We build an IO type that describes effects as values, hit a stack overflow, fix it by trampolining, and then use the type system to allow mutation that nobody outside can see.

13.1Factor the Effect Out

An impure function, mixing a decision with output:

case class Player(name: String, score: Int)

def contest(p1: Player, p2: Player): Unit =
  if p1.score > p2.score then println(s"${p1.name} wins")
  else if p2.score > p1.score then println(s"${p2.name} wins")
  else println("It's a draw")

Separate the pure logic from the effect, one layer at a time:

def winner(p1: Player, p2: Player): Option[Player] =             // pure: who won
  if p1.score > p2.score then Some(p1)
  else if p2.score > p1.score then Some(p2)
  else None

def winnerMsg(p: Option[Player]): String =                       // pure: what to say
  p.map(w => s"${w.name} wins").getOrElse("It's a draw")

def contest(p1: Player, p2: Player): Unit =                      // impure, but tiny
  println(winnerMsg(winner(p1, p2)))

This is the general shape: any function with side effects can be split into a pure core and two thin impure layers, one that gathers input and one that performs output. "Functional core, imperative shell." The rest of the chapter asks: can we make the shell pure too?

13.2A Simple IO Type

Make the effect a value, like Charge in Chapter 1:

trait IO[A]:
  self =>
  def unsafeRun: A                                 // performing it is the only impure part

  def map[B](f: A => B): IO[B] = new:
    def unsafeRun = f(self.unsafeRun)

  def flatMap[B](f: A => IO[B]): IO[B] = new:
    def unsafeRun = f(self.unsafeRun).unsafeRun

object IO:
  def apply[A](a: => A): IO[A] = new:          // suspend any side-effecting expression
    def unsafeRun = a

  given Monad[IO] with
    def unit[A](a: => A) = IO(a)
    extension [A](fa: IO[A])
      override def flatMap[B](f: A => IO[B]) = fa.flatMap(f)

def PrintLine(msg: String): IO[Unit] = IO(println(msg))
val ReadLine: IO[String] = IO(scala.io.StdIn.readLine())

A program is now a value of type IO[A]. Building it does nothing. Composing it is pure. Only unsafeRun, called once at the very edge (in main), performs anything.

def fahrenheitToCelsius(f: Double): Double = (f - 32) * 5.0 / 9.0

val converter: IO[Unit] =
  for
    _ <- PrintLine("Enter a temperature in degrees Fahrenheit:")
    d <- ReadLine.map(_.toDouble)
    _ <- PrintLine(f"${fahrenheitToCelsius(d)}%.1f °C")
  yield ()

@main def run(): Unit = converter.unsafeRun

And since IO is a monad, the whole toolkit applies: replicateM(10, ReadLine) reads ten lines, traverse runs an action per element, and you can write your own loops as functions:

def forever[A, B](a: IO[A]): IO[B] =
  a.flatMap(_ => forever(a))

val echo: IO[Nothing] = forever(ReadLine.flatMap(PrintLine))
An IO[A] is a recipe for interacting with the world, not the interaction. Because recipes are values, you can combine, repeat, retry, time-limit or test them before anything runs. The program's main function is "build one big recipe, then run it once".

13.3The Stack Overflow

Run forever(PrintLine("hi")).unsafeRun and it prints a few thousand times, then throws StackOverflowError. Look at flatMap's unsafeRun: it calls self.unsafeRun, then f(...).unsafeRun, which calls the next flatMap's unsafeRun, and so on. Every step adds a stack frame, and nothing ever returns. @tailrec can't help: these are calls through different objects.

Trampolining

The fix is to stop calling the next step and instead return a description of it. Then a single loop interprets the description, keeping its own explicit stack on the heap:

enum IO[A]:
  case Return(a: A)                                  // done, here's the value
  case Suspend(resume: () => A)                      // run this effect
  case FlatMap[A, B](sub: IO[A], k: A => IO[B]) extends IO[B]   // do sub, then continue with k

  def flatMap[B](f: A => IO[B]): IO[B] = FlatMap(this, f)
  def map[B](f: A => B): IO[B] = flatMap(a => Return(f(a)))

  @annotation.tailrec
  final def unsafeRun(): A = this match
    case Return(a)  => a
    case Suspend(r) => r()
    case FlatMap(x, f) => x match
      case Return(a)     => f(a).unsafeRun()
      case Suspend(r)    => f(r()).unsafeRun()
      case FlatMap(y, g) => y.flatMap(a => g(a).flatMap(f)).unsafeRun()   // reassociate

Every recursive call to unsafeRun is now a tail call, so it compiles to a loop. The last case uses the monad associativity law to rewrite (y flatMap g) flatMap f into y flatMap (a => g(a) flatMap f), rotating left-nested chains to the right so the loop always makes progress. A law from Chapter 11 is what makes the interpreter correct.

On a trampoline you don't climb a ladder of stack frames. Each bounce returns you to the same spot (the loop), with a note saying what to do next. However long the program, you never get higher than one bounce.

This is the same technique as turning a recursive tree walk into a loop with an explicit std::stack, or how a coroutine scheduler resumes continuations from a run loop instead of letting them call each other. The FlatMap nodes are the explicit continuation stack.

The same structure generalises: replace Suspend(() => A) with any type of "instruction" F[A] and you get the free monad, a program written in some instruction set, plus separate interpreters (one that performs real I/O, one that runs against an in-memory fake for tests). That's how you test effectful code without mocks.

13.4What IO Doesn't Give You

Be honest about the limits. IO doesn't make a program correct. Inside an IO, code can still have race conditions or ignore errors. What it gives you is: effects are visible in types (IO[Int] vs Int), programs are values you can compose and transform, and the pure parts stay pure. Real effect systems add a lot more on top: async and non-blocking I/O, cancellation, resource safety, structured concurrency, error handling. That's what cats-effect and ZIO are.

13.5Local Effects: Mutation Nobody Can See

Recall Exercise 1.3: a function that mutates local variables is still pure if no caller can observe the mutation. Quicksort on an array is fast precisely because it mutates in place. Can we write that inside a pure program, and have the compiler verify the mutation can't leak?

Yes, with a type called ST (state thread). Here's a sketch of the idea, where ST(a) wraps a value without touching the state and ST.lift wraps a state function:

opaque type ST[S, A] = S => (A, S)       // like State, tagged with a phantom type S

final class STRef[S, A] private (private var cell: A):
  def read: ST[S, A] = ST(cell)
  def write(a: => A): ST[S, Unit] = ST.lift(s => { cell = a; ((), s) })

object STRef:
  def apply[S, A](a: A): ST[S, STRef[S, A]] = ST(new STRef[S, A](a))

Every mutable reference is tagged with the same type S as the computation that created it. To run an ST computation, you must provide one that works for every S:

// a computation polymorphic in S
type RunnableST[A] = [s] => () => ST[s, A]

def runST[A](st: RunnableST[A]): A = ...    // picks an S internally and runs it

val p: RunnableST[(Int, Int)] = [s] => () =>
  for
    r1 <- STRef[s, Int](1)
    r2 <- STRef[s, Int](2)
    x  <- r1.read
    y  <- r2.read
    _  <- r1.write(y + 1)
    _  <- r2.write(x + 1)
    a  <- r1.read
    b  <- r2.read
  yield (a, b)

runST(p)   // (3, 2)

Why is this safe? Try to return the reference itself: the result type would be STRef[s, Int], which mentions s. But RunnableST[A] requires A not to depend on s, so it doesn't type-check. A mutable reference can't escape the computation that created it. Mutation happens; the type system proves nobody else can see it.

With an STArray built the same way, you can write an in-place quicksort whose signature is just def quicksort(xs: List[Int]): List[Int], pure from outside, mutating inside, and safe by construction.

Purity depends on what you choose to observe. Allocating memory is an effect if you watch the heap. Returning a fresh object is an effect if you compare with reference equality (eq). FP treats these as unobservable by convention. The useful question is always "what can callers of this function observe?"

Functional core, imperative shell
Design with pure logic in the middle and a thin layer of effects around it.
IO
A type whose values describe effectful programs; running them is separate.
Trampolining
Returning descriptions of the next step to a loop instead of calling it, avoiding stack growth.
Free monad
A monad built from any instruction set, interpreted later by a separate function.
ST / phantom type
A type parameter used only to tag values at compile time, here to stop mutable references escaping.
  • Any effectful function splits into a pure core and a thin effectful shell.
  • An IO type makes effects into composable values; unsafeRun happens once at the edge.
  • The naive IO overflows the stack; trampolining plus the associativity law fixes it.
  • ST lets you mutate locally with a compile-time guarantee that it can't leak.
  • Real-world effect systems (cats-effect, ZIO) build on these ideas.
