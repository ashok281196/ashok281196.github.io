Part IV · Effects and I/O

Effects, IO & Local Mutation

How a pure program talks to the world. We build an IO type that describes effects as values, watch it overflow the stack, fix it with a trampolined run loop, and then use templates to allow mutation the compiler proves nobody outside can see.

13.1Factor the Effect Out

An impure function that mixes a decision with output:

void contest(const Player& p1, const Player& p2) {
    if (p1.score > p2.score)      std::cout << p1.name << " wins\n";
    else if (p2.score > p1.score) std::cout << p2.name << " wins\n";
    else                          std::cout << "It's a draw\n";
}

Separate the pure logic from the effect, one layer at a time:

std::optional<Player> winner(const Player& p1, const Player& p2) {   // pure: who won
    if (p1.score > p2.score) return p1;
    if (p2.score > p1.score) return p2;
    return std::nullopt;
}
std::string winner_msg(const std::optional<Player>& p) {             // pure: what to say
    return p ? p->name + " wins" : "It's a draw";
}
void contest(const Player& p1, const Player& p2) {                   // impure, but tiny
    std::cout << winner_msg(winner(p1, p2)) << "\n";
}

This is the general shape: any function with side effects can be split into a pure core and thin impure layers that gather input and perform output. "Functional core, imperative shell." In C++ this alone is the most valuable thing in the chapter: it's how you make firmware logic, controllers and planners unit-testable without hardware. The rest of the chapter asks: can we make the shell a value too?

13.2A Simple IO Type

Make the effect a value, like Charge in Chapter 1:

template <typename A>
class IO {
    std::function<A()> thunk_;
public:
    using value_type = A;
    explicit IO(std::function<A()> f) : thunk_(std::move(f)) {}
    A unsafe_run() const { return thunk_(); }               // the ONLY place effects happen

    template <typename F> auto map(F f) const -> IO<std::invoke_result_t<F, A>> {
        auto self = *this;
        return IO<std::invoke_result_t<F, A>>([self, f] { return f(self.unsafe_run()); });
    }
    template <typename F> auto flat_map(F f) const -> std::invoke_result_t<F, A> {
        auto self = *this;
        return std::invoke_result_t<F, A>([self, f] { return f(self.unsafe_run()).unsafe_run(); });
    }
};

IO<std::monostate> print_line(std::string msg) {
    return IO<std::monostate>([msg] { std::cout << msg << "\n"; return std::monostate{}; });
}
IO<std::string> read_line() {
    return IO<std::string>([] { std::string s; std::getline(std::cin, s); return s; });
}

A program is now a value of type IO<A>. Building it does nothing. Composing it is pure. Only unsafe_run, called once at the edge (in main), performs anything:

IO<std::monostate> converter() {
    return print_line("Enter a temperature in degrees Fahrenheit:")
        .flat_map([](auto) { return read_line(); })
        .map([](std::string s) { return std::stod(s); })
        .flat_map([](double d) { return print_line(format_celsius(f_to_c(d))); });
}

int main() {
    auto program = converter();   // nothing printed yet
    program.unsafe_run();         // now it runs
}

The full listing points input and output at string streams and checks that building program prints nothing and running it prints exactly the expected text. Since IO is a monad, all of Chapter 11 applies: replicate_m(10, read_line()) reads ten lines, traverse runs an action per element, and loops can be written as ordinary functions.

An IO<A> is a recipe for interacting with the world, not the interaction. Because recipes are values, you can combine, repeat, retry, time-limit or test them before anything runs. main becomes "build one big recipe, then run it once".

13.3The Stack Overflow

Write a loop as recursion through flat_map:

IO<int> count_down(int n) {
    if (n == 0) return IO<int>([] { return 0; });
    return IO<int>([] { return 1; }).flat_map([n](int) { return count_down(n - 1); });
}

count_down(1000).unsafe_run();        // fine
count_down(1'000'000).unsafe_run();   // segmentation fault: stack overflow

Look at flat_map's thunk: it calls self.unsafe_run(), then f(...).unsafe_run(), which calls the next flat_map's thunk, and so on. Every step adds stack frames, and nothing returns until the very end. No compiler will turn calls through std::function objects into a loop.

Trampolining

Stop calling the next step; return a description of it instead, and let one loop run everything, keeping the pending continuations on an explicit stack on the heap. The IO becomes a small tree of nodes:

struct Node;
using NodePtr = std::shared_ptr<const Node>;
struct Pure  { std::any value; };                                    // done: here's the value
struct Delay { std::function<std::any()> thunk; };                   // perform this effect
struct Bind  { NodePtr sub; std::function<NodePtr(std::any)> k; };   // run sub, then continue with k
struct Node  { std::variant<Pure, Delay, Bind> v; };

std::any run_loop(NodePtr io) {
    std::vector<std::function<NodePtr(std::any)>> stack;      // continuations, on the heap
    for (;;) {
        if (auto* b = std::get_if<Bind>(&io->v)) {             // remember what to do after sub
            stack.push_back(b->k);
            io = b->sub;
            continue;
        }
        std::any value = std::holds_alternative<Pure>(io->v) ? std::get<Pure>(io->v).value
                                                              : std::get<Delay>(io->v).thunk();
        if (stack.empty()) return value;
        auto k = std::move(stack.back());
        stack.pop_back();
        io = k(std::move(value));                              // bounce back to the top of the loop
    }
}

A typed IO<A> wrapper puts a type-safe pure, delay, map and flat_map on top (inside, values travel as std::any, because one loop has to run steps of every type). Now count_down(1'000'000) runs in constant stack, and so does a million left-nested flat_maps, ((x >>= f) >>= f) >>= …, because the loop simply pushes each continuation as it descends.

On a trampoline you don't climb a ladder of stack frames. Each bounce lands you back on the same spot (the loop) with a note saying what to do next. However long the program, you never get higher than one bounce.

The same chain must also be destroyed without recursion. A million-deep chain of Bind nodes held by shared_ptr is destroyed recursively by default, and the first version of the listing crashed there, after the program had already run successfully. Node needs a destructor that unlinks the chain in a loop, the same fix as for List in Chapter 3. Garbage-collected runtimes never hit this.

The book's trampolined IO has the same three cases (Return, Suspend, FlatMap). Its interpreter is a @tailrec function that handles a left-nested FlatMap by reassociating it, using the monad associativity law to rewrite (y flatMap g) flatMap f as y flatMap (a => g(a) flatMap f). Our explicit continuation stack achieves the same thing. Generalising Delay to any "instruction set" gives the book's free monad: a program as data, run by interchangeable interpreters, for example a real one and an in-memory fake for tests.

13.4What IO Doesn't Give You

IO doesn't make a program correct. Inside an effect, code can still race or ignore errors. What it gives you is that effects are visible in types (IO<int> vs int), programs are values you can compose and transform, and the pure parts stay pure. Production effect systems add async I/O, cancellation, resource safety and structured concurrency on top. In C++ that role is played by coroutine-based frameworks and std::execution, where a sender is a description of asynchronous work that does nothing until it's connected and started.

13.5Local Effects: Mutation Nobody Can See

Recall Exercise 1.3: a function that mutates local variables is still pure if no caller can observe the mutation. In-place quicksort is fast precisely because it mutates. So:

std::vector<int> quicksort(std::vector<int> xs) {   // by value: a private copy
    // ... sort xs in place, Hoare partition ...
    return xs;
}

This is pure, and in C++ it's the everyday way to write fast pure functions: take by value, mutate the copy, return it. The book asks for more: can the compiler guarantee that a mutable reference created inside never escapes? The book's answer is a type called ST; here's the same guarantee in C++ templates.

template <typename S, typename T>
class STRef {                                       // a mutable cell tagged with its scope type S
    std::shared_ptr<T> cell_;
    explicit STRef(T v);                            // private: only a scope can create one
    friend class STScope<S>;
public:
    const T& read() const;
    void write(T v) const;
};

template <typename S> class STScope {
public:
    template <typename T> STRef<S, T> new_ref(T v) const;
};

template <typename F> auto run_st(F f) {
    // instantiate f with two DIFFERENT scope tags
    using R1 = decltype(f(std::declval<const STScope<Tag1>&>()));
    using R2 = decltype(f(std::declval<const STScope<Tag2>&>()));
    static_assert(std::is_same_v<R1, R2>, "an STRef escaped its scope");
    return f(STScope<Tag1>{});
}
int r = run_st([](const auto& scope) {
    auto r1 = scope.new_ref(1);
    auto r2 = scope.new_ref(2);
    int x = r1.read(), y = r2.read();
    r1.write(y + 1);
    r2.write(x + 1);
    return r1.read() * 10 + r2.read();         // 32
});

run_st([](const auto& scope) { return scope.new_ref(1); });
// error: static assertion failed: an STRef escaped its scope

Why does it work? The lambda is generic over the scope type. If it returns a plain value, the result type is the same whatever the scope tag. If it tries to return an STRef, the result type mentions the tag (STRef<Tag1, int> vs STRef<Tag2, int>), and the static_assert fires. A reference can't leave the computation that created it. (The listing compiles a test file with exactly that escape and confirms the error.)

The book's runST requires a computation that works "for all S" (a rank-2 type), so a reference typed with S can't appear in the result. Our two-tag check is a C++ approximation of that idea. Rust's borrow checker enforces a stronger version of the same guarantee for every reference in the language.

Purity depends on what you choose to observe. Allocating memory is an effect if you watch the heap; returning a fresh object is one if you compare addresses. FP treats these as unobservable by convention. The useful question is always "what can callers of this function observe?"

Functional core, imperative shell
Pure logic in the middle, a thin layer of effects around it.
IO
A type whose values describe effectful programs; running them is separate.
Trampolining
Returning descriptions of the next step to a loop instead of calling it, so the stack doesn't grow.
Free monad
A monad built from an instruction set, interpreted later by a separate function.
ST / phantom type
A type parameter used only as a compile-time tag, here to stop mutable references escaping.
  • Any effectful function splits into a pure core and a thin effectful shell.
  • An IO type makes effects composable values; unsafe_run happens once at the edge.
  • The naive IO overflows the stack; a run loop with an explicit continuation stack fixes it.
  • In C++, also destroy long node chains iteratively.
  • Local mutation is pure if it can't be observed; templates can even prove references don't escape.
