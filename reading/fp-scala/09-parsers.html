Parser Combinators

The purest exercise in algebraic design: decide the operations of a parsing library and write a JSON parser with them before deciding how a parser is represented. Then implement six primitives in C++ and watch the whole grammar work, with useful error messages.

9.1What We're Building

A parser turns text into structured data: "[1, 2, true]" into a JSON array. A parser combinator library gives you small parsers (match a string, match a regex) and functions that combine them (this then that, this or that, many of this). You write the grammar as ordinary code, with no separate grammar file or code generator.

This chapter pushes "algebra first" to the limit: decide the operations, write a JSON parser against them, and only at the end pick a representation.

9.2Primitives, From Examples

Start with the simplest things we'd want to parse, and invent an operation for each. Think of this as the header file of the library, before any .cpp exists:

template <typename A> class Parser;   // representation: not decided yet

Parser<std::string> string(std::string s);               // match exactly s
Parser<std::string> regex(std::string pattern);          // match a regex at this position
template <typename A> Parser<A> succeed(A a);            // consume nothing, always succeed
template <typename A> Parser<A> operator|(Parser<A> p, Parser<A> p2);   // p, or else p2
template <typename A> std::variant<A, ParseError> run(const Parser<A>& p, std::string_view input);

Laws come immediately:

run(string(s), s)            == s
run(succeed(a), anything)    == a
run(string("ab") | string("cd"), "cd") == "cd"

Repetition and slices

Parse "zero or more of p":

template <typename A> Parser<std::vector<A>> many(Parser<A> p);
template <typename A, typename F> auto map(Parser<A> p, F f);   // transform the result

Counting a's is now map(many(char_('a')), size), but that builds a vector just to count it. A better primitive, slice, returns the piece of input a parser consumed and ignores its result:

template <typename A> Parser<std::string> slice(Parser<A> p);

map(slice(many(char_('a'))), [](std::string s) { return s.size(); });   // no vector built

Sequencing

"One or more a's" needs "p, then many(p)": two parsers in sequence.

template <typename A, typename B, typename F> auto map2(Parser<A> pa, Parser<B> pb, F f);

template <typename A> Parser<std::vector<A>> many1(Parser<A> p) {
    return map2(p, many(p), [](A a, std::vector<A> v) { v.insert(v.begin(), a); return v; });
}

Context sensitivity

Parse a digit n, then exactly n letter a's ("3aaa"). The second parser depends on the first one's result, which map2 can't express. You know what can:

template <typename A, typename F> auto flat_map(Parser<A> p, F f);   // F: A -> Parser<B>

Parser<int> counted_as() {
    return flat_map(regex("[0-9]"), [](std::string d) {
        int n = d[0] - '0';
        return map(list_of_n(n, char_('a')), [n](std::vector<char>) { return n; });
    });
}

Write map and map2 using only flat_map and succeed.

Show solution
template <typename A, typename F>
auto map(Parser<A> p, F f) -> Parser<std::invoke_result_t<F, A>> {
    using B = std::invoke_result_t<F, A>;
    return flat_map(p, [f](A a) { return succeed<B>(f(a)); });
}

template <typename A, typename B, typename F>
auto map2(Parser<A> pa, Parser<B> pb, F f) -> Parser<std::invoke_result_t<F, A, B>> {
    return flat_map(pa, [pb, f](A a) { return map(pb, [a, f](B b) { return f(a, b); }); });
}

The same derivations as for optional, State and Par. succeed plays the role of unit.

The primitives are string, regex, succeed, slice, | and flat_map (plus error-reporting ones below). Everything else (map, map2, product, many1, list_of_n, sep) is derived. An implementation only has to provide those few functions.

9.3A JSON Parser, Before Any Implementation

JSON as a sum type. std::vector may hold an incomplete type, so the variant can mention JSON inside JSON:

struct JSON {
    std::variant<std::nullptr_t, double, std::string, bool,
                 std::vector<JSON>,                              // array
                 std::vector<std::pair<std::string, JSON>>> v;  // object
};

A few more derived helpers make grammars pleasant: skip whitespace, keep only the left or right result of a sequence, separate by a delimiter.

template <typename A, typename B> Parser<B> skip_l(Parser<A> pa, Parser<B> pb) {
    return map2(slice(pa), pb, [](std::string, B b) { return b; });
}
template <typename A, typename B> Parser<A> skip_r(Parser<A> pa, Parser<B> pb) {
    return map2(pa, slice(pb), [](A a, std::string) { return a; });
}
Parser<std::string> whitespace() { return regex("\\s*"); }
template <typename A> Parser<A> token(Parser<A> p) { return skip_r(p, whitespace()); }
Parser<std::string> tok(std::string s) { return token(string(std::move(s))); }

template <typename A, typename S>
Parser<std::vector<A>> sep(Parser<A> p, Parser<S> separator) {
    return map2(p, many(skip_l(separator, p)),
                [](A a, std::vector<A> v) { v.insert(v.begin(), a); return v; })
         | succeed(std::vector<A>{});
}

Now the grammar, written only with combinators:

Parser<JSON> json_value();                       // declared first: the grammar is recursive

Parser<std::string> quoted() {
    return skip_r(skip_l(string("\""), regex("[^\"]*")), tok("\""));
}

Parser<JSON> json_literal() {
    return as(tok("null"),  JSON{nullptr})
         | as(tok("true"),  JSON{true})
         | as(tok("false"), JSON{false})
         | map(token(regex("-?[0-9]+(\\.[0-9]+)?([eE][-+]?[0-9]+)?")),
               [](std::string s) { return JSON{std::stod(s)}; })
         | map(quoted(), [](std::string s) { return JSON{s}; });
}

Parser<JSON> json_array() {
    return scope("array", map(surround(tok("["), tok("]"), sep(json_value(), tok(","))),
                              [](std::vector<JSON> vs) { return JSON{vs}; }));
}

Parser<JSON> json_object() {
    auto keyval = product(quoted(), skip_l(tok(":"), json_value()));
    return scope("object", map(surround(tok("{"), tok("}"), sep(keyval, tok(","))),
                               [](auto kvs) { return JSON{kvs}; }));
}

Parser<JSON> json_value() {
    return lazy<JSON>([] { return json_literal() | json_object() | json_array(); });
}
Parser<JSON> json() { return skip_l(whitespace(), json_value()); }

That's a whole JSON parser (strings without escapes, for brevity), and it reads almost like the JSON spec.

One C++-specific detail: json_value calls json_array, which calls json_value. If building a parser immediately built its sub-parsers, constructing the grammar would recurse forever. lazy wraps a parser-builder and runs it on first use, which breaks the cycle. It plays the role of the book's by-name parameters.

The book writes the API as trait Parsers[Parser[+_]], an interface that's generic over the parser type constructor, and writes the JSON parser as a function taking any implementation of that trait. C++ can't easily abstract over a template like that (we'll meet template template parameters in Chapter 11), so here the "algebra" is a set of free-function declarations, and the JSON grammar only calls those.

In C++ terms: Boost.Spirit and PEGTL are parser combinator libraries that encode the grammar in templates and resolve it at compile time, which is fast but heavy on build time. Here a parser is an ordinary runtime value (a std::function). It's slower, but you can build parsers dynamically, pass them around and test them like any other value.

9.4Error Reporting

A parser that only says "failed" is useless on real input. We want the position and a stack of context ("in object, in array, expected ']'"). Add two primitives:

template <typename A> Parser<A> label(std::string msg, Parser<A> p);   // on failure, replace the message
template <typename A> Parser<A> scope(std::string msg, Parser<A> p);   // on failure, add outer context

struct Location {
    std::string_view input;
    size_t offset = 0;
    int line() const;   // computed from offset
    int col() const;
};
struct ParseError { std::vector<std::pair<Location, std::string>> stack; };

With scope already in the JSON grammar above, parsing { "a": [1, 2 } reports:

1:1 object
1:8 array
1:14 expected "]"

Committed vs backtracking

There's a subtle design choice in |. Take product(string("abra"), string("cadabra")) | other on "abraxyz". The left side matched "abra" and then failed. Should | try other from the start? For good error messages, usually not: once a parser has consumed input it has committed, and that branch's error is the useful one. To allow backtracking explicitly, wrap with attempt:

template <typename A> Parser<A> attempt(Parser<A> p);   // a failure here counts as "consumed nothing"

run(ab_cad | other, "abraxyz");            // error: committed to the first branch
run(attempt(ab_cad) | other, "abraxyz");   // backtracks and succeeds with other

By default | only tries the right side if the left failed without consuming input. Parsec, FastParse, cats-parse and PEGTL's must<> all make some version of this choice.

9.5Finally, a Representation

A parser takes the input at some position and either fails with an error, or succeeds with a value and the number of characters consumed:

template <typename A> struct Success { A value; size_t consumed; };
struct Failure { ParseError error; bool committed; };
template <typename A> using Result = std::variant<Success<A>, Failure>;

template <typename A> using Parser = std::function<Result<A>(Location)>;

Each primitive is a few lines. The three that matter most:

Parser<std::string> string(std::string w) {
    return [w](Location l) -> Result<std::string> {
        if (l.input.substr(l.offset).starts_with(w)) return Success<std::string>{w, w.size()};
        return Failure{{{{l, "expected \"" + w + "\""}}}, false};
    };
}

template <typename A> Parser<A> operator|(Parser<A> p, Parser<A> p2) {
    return [p, p2](Location l) -> Result<A> {
        auto r = p(l);
        if (auto* f = std::get_if<Failure>(&r); f && !f->committed) return p2(l);   // uncommitted: try p2
        return r;
    };
}

template <typename A, typename F>
auto flat_map(Parser<A> p, F f) -> std::invoke_result_t<F, A> {
    using B = typename parser_value<std::invoke_result_t<F, A>>::type;
    return [p, f](Location l) -> Result<B> {
        auto r = p(l);
        auto* s = std::get_if<Success<A>>(&r);
        if (!s) return std::get<Failure>(r);
        auto r2 = f(s->value)(l.advance(s->consumed));
        if (auto* s2 = std::get_if<Success<B>>(&r2))
            return Success<B>{std::move(s2->value), s->consumed + s2->consumed};
        auto fail = std::get<Failure>(r2);
        fail.committed = fail.committed || s->consumed > 0;   // consumed input → committed
        return fail;
    };
}

regex, slice, attempt, label, scope and lazy are in the full listing; altogether the representation is about 120 lines. The JSON grammar from 9.3 runs on it unchanged and parses {"robot": "PiPER", "dof": 6, "arms": [1, 2.5, true, null], "ok": false}.

Make many a loop. Derived recursively as "map2(p, many(p)) | succeed({})", it recurses once per repetition, and a 20,000-element JSON array overflows the stack. The listing implements many as a primitive with a loop (and checks the 20,000-element case). That's a representation change; the grammar doesn't notice. Similarly, std::regex is slow; a production version would hand-write the number and string matchers.

9.6Part II in One Paragraph

Three libraries: parallelism, testing, parsing. Each was designed the same way: usage first, a small set of primitives, laws, representation last. And each ended up with unit/succeed, map, map2, flat_map and some form of sequence (list_of_n, many). Part III gives that recurring shape names and writes it down once.

Parser combinator
A function that builds a parser from smaller parsers.
Context-sensitive grammar
A grammar where what to parse next depends on what was just parsed; needs flat_map.
Commit / backtrack
Whether, after consuming input and failing, an alternative may retry from the original position.
Lazy parser
A parser built on first use, which lets recursive grammars refer to themselves.
  • Decide the operations before any implementation, and write real grammars against them.
  • About six primitives are enough; many1, map2, sep and the rest are derived.
  • Recursive grammars need laziness (lazy in C++).
  • Design error reporting in: scope, label, commit vs attempt.
  • A ~120-line representation runs a full JSON grammar, and can be optimised without touching it.
