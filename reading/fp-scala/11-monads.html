Part III · Common Structures

Monads

Since Chapter 3 we've written unit, map, map2, flat_map and sequence again and again for every type. Here we write them once. That needs something C++ doesn't directly have, abstraction over a type constructor, so we build it with tag types and trait specialisations, then meet the monad laws and what a monad really is.

11.1The Duplication Problem

Here's map2 for four types we've written:

// optional
a.and_then([&](A x) { return b.transform([&](B y) { return f(x, y); }); });
// State
sa.flat_map([=](A x) { return sb.map([=](B y) { return f(x, y); }); });
// Gen
ga.flat_map([=](A x) { return gb.map([=](B y) { return f(x, y); }); });
// Parser
flat_map(pa, [=](A x) { return map(pb, [=](B y) { return f(x, y); }); });

Identical logic. Only the type constructor differs: optional<_>, State<S, _>, Gen<_>, Parser<_>. To write map2 once, we need to be generic over "some template F applied to A".

11.2Abstracting Over F<_> in C++

A template template parameter (template <template <typename> class F>) almost works, but breaks on templates with extra parameters like std::vector<T, Alloc> or State<S, A>. The robust trick is a tag type with a nested alias template, one per type constructor:

struct OptionalK { template <typename A> using F = std::optional<A>; };
struct VectorK   { template <typename A> using F = std::vector<A>; };

template <typename S>
struct StateK    { template <typename A> using F = State<S, A>; };   // fix S, leave A open

StateK<int> is "State<int, _>": a two-parameter template with one parameter fixed. Now a type class is a primary template with one specialisation per tag:

template <typename K> struct Monad;     // must provide unit(a) and flat_map(fa, f)

template <> struct Monad<OptionalK> {
    template <typename A> static std::optional<A> unit(A a) { return a; }
    template <typename A, typename Fn>
    static auto flat_map(const std::optional<A>& fa, Fn f) { return fa.and_then(f); }
};

template <> struct Monad<VectorK> {
    template <typename A> static std::vector<A> unit(A a) { return {a}; }
    template <typename A, typename Fn>
    static auto flat_map(const std::vector<A>& fa, Fn f) {
        std::invoke_result_t<Fn, const A&> out;
        for (const auto& a : fa) { auto bs = f(a); out.insert(out.end(), bs.begin(), bs.end()); }
        return out;
    }
};

template <typename S> struct Monad<StateK<S>> {
    template <typename A> static State<S, A> unit(A a) {
        return {[a](S s) { return std::pair{a, s}; }};
    }
    template <typename A, typename Fn> static auto flat_map(const State<S, A>& fa, Fn f) {
        using SB = std::invoke_result_t<Fn, A>;
        return SB{[fa, f](S s) { auto [a, s1] = fa.run(s); return f(a).run(s1); }};
    }
};

Each type supplies two functions. That's the whole cost of membership.

The book writes trait Monad[F[_]] { def unit[A](a: => A): F[A]; extension [A](fa: F[A]) def flatMap[B](f: A => F[B]): F[B] }, with F[_] a higher-kinded type parameter, and given instances like Monad[Option]. For State it writes a type lambda, [x] =>> State[S, x], which is exactly what our StateK<S>::F is. Our tag + specialisation pattern is how C++ libraries (and papers on C++ FP) encode the same thing.

11.3Write the Derived Functions Once

Now everything we derived by hand in Part I is written a single time, generic over the tag K:

template <typename K, typename FA, typename Fn>
auto map(const FA& fa, Fn f) {
    using A = typename FA::value_type;
    using B = std::invoke_result_t<Fn, const A&>;
    return Monad<K>::flat_map(fa, [f](const A& a) { return Monad<K>::template unit<B>(f(a)); });
}

template <typename K, typename FA, typename FB, typename Fn>
auto map2(const FA& fa, const FB& fb, Fn f) {
    using A = typename FA::value_type;
    using B = typename FB::value_type;
    return Monad<K>::flat_map(fa, [fb, f](const A& a) {
        return map<K>(fb, [a, f](const B& b) { return f(a, b); });
    });
}

template <typename K, typename A, typename Fn>
auto traverse(const std::vector<A>& as, Fn f) {
    using B = typename std::invoke_result_t<Fn, const A&>::value_type;
    typename K::template F<std::vector<B>> acc = Monad<K>::template unit<std::vector<B>>({});
    for (auto it = as.rbegin(); it != as.rend(); ++it)
        acc = map2<K>(f(*it), acc, [](const B& b, std::vector<B> v) { v.insert(v.begin(), b); return v; });
    return acc;
}

template <typename K, typename FA>
auto sequence(const std::vector<FA>& fas) { return traverse<K>(fas, [](const FA& fa) { return fa; }); }

template <typename K, typename FA>
auto replicate_m(int n, const FA& fa) { return sequence<K>(std::vector<FA>(n, fa)); }

(We read the element type from FA::value_type, which optional, vector and our own types all provide; C++ can't deduce A from K::F<A> directly.) Now look at replicate_m across monads:

replicate_m<OptionalK>(3, std::optional{1});   // optional{vector{1,1,1}}: n copies, or nothing
replicate_m<VectorK>(2, std::vector{0, 1});    // {{0,0},{0,1},{1,0},{1,1}}: every combination

State<int, int> tick{[](int s) { return std::pair{s, s + 1}; }};
replicate_m<StateK<int>>(3, tick).run(10);   // ({10, 11, 12}, 13): run it three times

For Gen it would mean "a list of n random values" (list_of_n); for Parser, "parse exactly n times" (also list_of_n). One generic function, a different meaningful behaviour for each monad.

11.4The Monad Laws

As with monoids, laws define the abstraction. They're neatest stated with Kleisli composition, which composes two "monadic functions" A → F<B> and B → F<C>:

template <typename K, typename F1, typename F2>
auto compose(F1 f, F2 g) {
    return [f, g](const auto& a) { return Monad<K>::flat_map(f(a), g); };
}

The laws:

compose(compose(f, g), h) == compose(f, compose(g, h))    associativity
compose(f, unit)          == f                            right identity
compose(unit, f)          == f                            left identity

Those are exactly the monoid laws, with compose as combine and unit as the identity. A monad is a monoid one level up, over functions A → F<B>. The full listing checks all three for optional on several inputs.

Associativity is what makes chains of and_then safe to refactor: you can pull any run of consecutive steps out into a helper function, or inline one back, without changing behaviour.

Write join(F<F<A>>) → F<A> generically with flat_map. What does it do for vector, and for optional?

Show solution
template <typename K, typename FFA>
auto join(const FFA& ffa) {
    using FA = typename FFA::value_type;
    return Monad<K>::flat_map(ffa, [](const FA& fa) { return fa; });
}

join<VectorK>(std::vector<std::vector<int>>{{1}, {2, 3}});    // {1, 2, 3}: flatten
join<OptionalK>(std::optional<std::optional<int>>(std::optional<int>(7)));   // optional{7}

Careful in C++: std::optional{std::optional{7}} deduces optional<int> (a copy), not a nested optional. Spell out the type. There are three equivalent minimal sets of monad operations: unit + flat_map, unit + compose, and unit + map + join.

11.5So What Is a Monad?

Look at the simplest possible monad, one that does nothing extra:

template <typename A> struct Id { A value; using value_type = A; };
struct IdK { template <typename A> using F = Id<A>; };
template <> struct Monad<IdK> {
    template <typename A> static Id<A> unit(A a) { return {a}; }
    template <typename A, typename Fn> static auto flat_map(const Id<A>& fa, Fn f) { return f(fa.value); }
};

With Id, flat_map(Id{x}, a ↦ ...) is just "let a = x in ...": plain variable binding. Every other monad is "variable binding, plus something extra happens between the steps":

MonadWhat happens between steps
Idnothing; plain sequencing
optionalmay stop early with no result
expected<_, E>may stop early with an error
vectormay branch into many results (try every combination)
State<S, _>a state is threaded along
Genrandomness is threaded along
Parserinput position is threaded; may fail or backtrack
Parsteps may run on other threads
A monad is a programmable semicolon. In C++, ; means "do the next statement". A monad's flat_map lets you define what "next" means: stop if empty, try every branch, pass the state along, continue on another thread. The chain of steps is the program; the monad is the rule for how the steps connect.

So a monad isn't a container, and it isn't specifically about side effects. It's a minimal interface (unit and an associative flat_map) for sequencing computations where each step can depend on the previous result. Different monads give that sequencing different extra behaviour.

The book shows these chains as for-comprehensions, which read like ordinary sequential code. C++ lacks that sugar, so long monadic chains nest lambdas. C++20 coroutines can provide it: a coroutine whose co_await calls and_then gives "do-notation" for optional or expected, and that's essentially what std::execution and async frameworks do for futures.

11.6Reader: One More Useful Monad

Many functions need the same configuration passed in. The Reader monad represents "a computation that needs an R":

template <typename R, typename A>
struct Reader { using value_type = A; std::function<A(const R&)> run; };
template <typename R> struct ReaderK { template <typename A> using F = Reader<R, A>; };

template <typename R> struct Monad<ReaderK<R>> {
    template <typename A> static Reader<R, A> unit(A a) { return {[a](const R&) { return a; }}; }
    template <typename A, typename Fn> static auto flat_map(const Reader<R, A>& fa, Fn f) {
        using RB = std::invoke_result_t<Fn, A>;
        return RB{[fa, f](const R& r) { return f(fa.run(r)).run(r); }};   // same r to every step
    }
};

struct Config { std::string base_url; int retries; };
Reader<Config, Config> ask() { return {[](const Config& c) { return c; }}; }

auto endpoint = map<ReaderK<Config>>(ask(), [](const Config& c) {
    return c.base_url + "/v1/data?retries=" + std::to_string(c.retries);
});
endpoint.run(Config{"https://api.example.com", 3});

It's dependency injection with no framework. If you've written C++ code where every function takes a const Context& first and passes it to every callee, Reader is that pattern, with flat_map doing the passing.

Monads don't compose in general. optional is a monad and State is a monad, but there's no generic way to combine them into a monad for "State that may fail". Real libraries use specific monad transformers or a single effect type that bundles the common capabilities. The abstraction in the next chapter does compose.

Type constructor
A template that takes a type and gives a type: optional<_>, vector<_>, State<S, _>.
Higher-kinded abstraction
Code generic over a type constructor. In C++: tag types with nested alias templates.
Monad
A type constructor with unit and an associative flat_map that obey the identity laws.
Kleisli composition
Composing A → F<B> with B → F<C> using flat_map.
Reader
The monad of computations that read a shared, read-only environment.
  • Abstract over the type constructor to write map2, traverse, replicate_m once.
  • C++ encoding: a tag per type constructor, a Monad<Tag> specialisation per type.
  • Monad = unit + flat_map with associativity and identity laws (the monoid laws for Kleisli composition).
  • A monad defines what "do this, then that" means for a type.
  • Monads don't compose generically, which motivates the next chapter.
