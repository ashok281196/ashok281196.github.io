Errors as Values

Exceptions break referential transparency and hide failure from the type system. We replace them with std::optional and std::expected, first writing map and flat_map ourselves to see how they work, then using C++23's transform, and_then and value_or to write failure-aware code that reads like the happy path.

4.1What's Wrong With Exceptions

int failing_fn() {
    int y = [] () -> int { throw std::runtime_error("fail!"); }();
    try { return 42 + 5 + y; }
    catch (...) { return 43; }
}

Calling this throws: y is computed before the try. Now substitute y by its definition, the way the substitution model says we should be able to:

int failing_fn2() {
    try { return 42 + 5 + [] () -> int { throw std::runtime_error("fail!"); }(); }
    catch (...) { return 43; }    // now returns 43
}

Same expression, different result, depending on where it sits. A throw isn't referentially transparent: its meaning depends on which try surrounds it at run time.

Two more problems:

  • Not in the type. int parse(const std::string&) says nothing about failing. Callers forget, and you find out in production. (noexcept only tells you when something can't throw.)
  • Doesn't play with higher-order functions. Pass a throwing lambda to std::transform and an exception halfway through leaves the output partly written.

The fix is Chapter 1's move again: represent failure as a value, in the return type.

4.2std::optional: Maybe a Value

std::optional<double> mean(const std::vector<double>& xs) {
    if (xs.empty()) return std::nullopt;
    double s = 0; for (double x : xs) s += x;
    return s / xs.size();
}

The signature tells the truth: "you might not get a double." The caller can't use the result as a double without dealing with the empty case.

(Well, almost can't: *opt on an empty optional is undefined behaviour. Treat operator* on an optional you haven't checked the way you'd treat a raw pointer. The combinators below are how you avoid needing it.)

4.3Building map and flat_map Ourselves

If every caller wrote if (opt) ... else ... by hand, code would be unreadable. Write the two key combinators once. First map: apply a function to the value if there is one.

template <typename A, typename F>
auto opt_map(const std::optional<A>& oa, F f)
    -> std::optional<std::invoke_result_t<F, const A&>> {
    if (!oa) return std::nullopt;
    return f(*oa);
}

Then flat_map, for when the function itself can fail (returns an optional). Using map there would give optional<optional<B>>; flat_map flattens:

template <typename A, typename F>
auto opt_flat_map(const std::optional<A>& oa, F f)
    -> std::invoke_result_t<F, const A&> {
    if (!oa) return std::nullopt;
    return f(*oa);
}

That's all there is to it. C++23 put exactly these into the standard:

From here on we use the standard names.

Reading it as a pipeline

struct Employee { std::string name, dept; std::optional<std::string> manager; };
std::optional<Employee> lookup_by_name(const std::string& name);

std::string manager_of(const std::string& name) {
    return lookup_by_name(name)
        .and_then([](const Employee& e) { return e.manager; })   // may have no manager
        .transform(to_upper)
        .value_or("(no manager)");
}

Each step is written as if the value is there. If a step produces "nothing", the rest are skipped and value_or supplies the fallback. Error handling hasn't gone; it's been moved into the combinators.

Use transform (map) when your function always succeeds. Use and_then (flat_map) when your function can itself fail. Handle the failure once, at the end, with value_or or an explicit check.

Using and_then and mean, write variance(xs): the mean of (x - m)² for each x, where m is the mean.

Show solution
std::optional<double> variance(const std::vector<double>& xs) {
    return mean(xs).and_then([&](double m) {
        std::vector<double> sq;
        for (double x : xs) sq.push_back(std::pow(x - m, 2));
        return mean(sq);
    });
}

The empty case is handled once, by the first mean. and_then because the inner step also returns an optional.

4.4Lifting Ordinary Functions

Do we have to rewrite every existing function to take optionals? No; we lift them:

template <typename F>
auto lift(F f) {
    return [f]<typename A>(const std::optional<A>& oa) { return oa.transform(f); };
}

auto abs_o = lift([](double d) { return std::fabs(d); });
abs_o(std::optional{-2.5});   // optional(2.5)

Now a function of two arguments. An insurance quote needs age and number of speeding tickets, both parsed from strings that might be malformed:

double insurance_rate(int age, int tickets);

std::optional<int> to_int(const std::string& s) {
    int v{};
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::nullopt;
    return v;
}

(That's the pattern for exception-throwing or error-code APIs: convert at the boundary, and from then on it's a value. std::from_chars doesn't throw, which is why we prefer it to std::stoi here.) To combine two optionals with a two-argument function, we need map2:

Write map2(a, b, f) for optionals using and_then and transform. Use it for parse_insurance_rate_quote(age, tickets).

Show solution
template <typename A, typename B, typename F>
auto map2(const std::optional<A>& a, const std::optional<B>& b, F f)
    -> std::optional<std::invoke_result_t<F, const A&, const B&>> {
    return a.and_then([&](const A& aa) {
        return b.transform([&](const B& bb) { return f(aa, bb); });
    });
}

std::optional<double> parse_insurance_rate_quote(const std::string& age,
                                                 const std::string& tickets) {
    return map2(to_int(age), to_int(tickets), insurance_rate);
}

The shape and_then outside, transform inside comes up constantly. Scala and Haskell have syntax for it (a for-comprehension / do-notation) that flattens the nesting. C++ doesn't, so with three or four steps the lambdas nest deeper. When that gets ugly, an early-return style with explicit checks is a perfectly good C++ alternative, as long as the function still returns an optional instead of throwing.

4.5sequence and traverse

We have a list of strings and want to parse them all, failing if any fails.

template <typename A, typename F>
auto traverse(const std::vector<A>& as, F f)
    -> std::optional<std::vector<typename std::invoke_result_t<F, const A&>::value_type>> {
    using B = typename std::invoke_result_t<F, const A&>::value_type;
    std::vector<B> out;
    for (const auto& a : as) {
        auto ob = f(a);
        if (!ob) return std::nullopt;       // one failure fails the whole thing
        out.push_back(std::move(*ob));
    }
    return out;
}

template <typename A>
std::optional<std::vector<A>> sequence(const std::vector<std::optional<A>>& as) {
    return traverse(as, [](const std::optional<A>& o) { return o; });
}

traverse(std::vector<std::string>{"1", "2", "3"}, to_int);   // optional(vector{1,2,3})
traverse(std::vector<std::string>{"1", "x", "3"}, to_int);   // nullopt

traverse applies a fallible function to each element and swaps the layers: from "a vector of maybe-values" to "maybe a vector". Remember it: in Chapter 12 it turns out to work for far more than vectors and optionals.

The book writes traverse as a foldRight with map2, starting from Some(Nil). That's the same computation; in C++ we write the loop, which is clearer and stack-safe. Keep the fold version in mind, though, because the map2-based definition is what generalises later.

4.6std::expected: Failure With a Reason

nullopt says that something failed, not why. std::expected<T, E> holds either a T or an error E, and has the same combinators:

std::expected<int, std::string> safe_div(int x, int y) {
    if (y == 0) return std::unexpected("division by zero");
    return x / y;
}

struct Person { std::string name; int age; };

std::expected<std::string, std::string> mk_name(const std::string& n) {
    if (n.empty()) return std::unexpected("name is empty");
    return n;
}
std::expected<int, std::string> mk_age(int a) {
    if (a < 0) return std::unexpected("age is out of range");
    return a;
}

std::expected<Person, std::string> mk_person(const std::string& n, int a) {
    return mk_name(n).and_then([&](std::string name) {
        return mk_age(a).transform([&](int age) { return Person{name, age}; });
    });
}

mk_person("", -1).error();   // "name is empty" — only the FIRST error

It's the same nesting as map2 for optionals. The unexpected value plays the role of nullopt but carries the reason. Notice how similar the two types' combinators are. Keep noticing that.

and_then stops at the first error. It has to: the second step might depend on the first's result. But here name and age are independent, and a user filling in a form wants to see both problems. That needs a different, less powerful abstraction, which you'll meet in Chapter 12.

Write catch_non_fatal(f): call f() and return its result in an expected, with any std::exception converted to an error string.

Show solution
template <typename F>
auto catch_non_fatal(F f) -> std::expected<std::invoke_result_t<F>, std::string> {
    try { return f(); }
    catch (const std::exception& e) { return std::unexpected(std::string(e.what())); }
}

auto r = catch_non_fatal([] { return std::stoi("nope"); });   // error: "stoi"

Taking a callable rather than a value is essential. If the caller evaluated the expression first, it would throw before reaching the try. The book uses a by-name parameter for the same reason.

  • Convert exceptions and error codes to values at library boundaries.
