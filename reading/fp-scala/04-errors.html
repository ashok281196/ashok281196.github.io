Errors as Values

Exceptions break referential transparency and hide failure from the type system. We replace them with Option and Either, and learn the handful of combinators (map, flatMap, getOrElse, map2, traverse) that make failure-aware code read like the happy path.

4.1What's Wrong With Exceptions

def failingFn(i: Int): Int =
  val y: Int = throw Exception("fail!")
  try
    val x = 42 + 5
    x + y
  catch case e: Exception => 43

Calling this throws. Now apply substitution: replace y with its definition inside the try:

def failingFn2(i: Int): Int =
  try
    val x = 42 + 5
    x + ((throw Exception("fail!")): Int)
  catch case e: Exception => 43    // returns 43

Same code, different result, depending on where the expression sits. So throw isn't referentially transparent: its meaning depends on which try block surrounds it at runtime.

Two more problems:

  • Not type-safe. def parse(s: String): Int says nothing about failing. Callers forget, and you find out in production.
  • Doesn't work with higher-order functions. If you pass a function that throws into map, map has no way to know or handle it.

The fix is the same move as Chapter 1: represent the failure as a value, and put it in the return type.

4.2Option: Maybe There's a Value

enum Option[+A]:
  case Some(get: A)
  case None

A function that might not have an answer returns Option:

def mean(xs: Seq[Double]): Option[Double] =
  if xs.isEmpty then None
  else Some(xs.sum / xs.length)

The signature now tells the truth: "you might not get a Double." The caller can't use the result as a Double without dealing with None. The compiler won't allow it.

This is std::optional<T>, and the C++23 monadic operations transform, and_then and or_else are exactly map, flatMap and orElse below. Either is std::expected<T, E>. C++ arrived at the same design for the same reasons.

4.3The Option Toolkit

If every caller pattern-matched every Option, code would be unreadable. Instead we write a few combinators once:

enum Option[+A]:
  case Some(get: A)
  case None

  def map[B](f: A => B): Option[B] = this match
    case None    => None
    case Some(a) => Some(f(a))

  def flatMap[B](f: A => Option[B]): Option[B] = this match
    case None    => None
    case Some(a) => f(a)

  def getOrElse[B >: A](default: => B): B = this match
    case None    => default
    case Some(a) => a

  def orElse[B >: A](ob: => Option[B]): Option[B] = this match
    case None => ob
    case _    => this

  def filter(p: A => Boolean): Option[A] = this match
    case Some(a) if p(a) => this
    case _               => None

Two new bits of syntax:

  • B >: A means "B is a supertype of A". It's needed because Option is covariant. You can say someDog.getOrElse(someCat) and get an Animal.
  • default: => B is a by-name parameter: it's evaluated only if used. getOrElse(expensiveFallback()) doesn't run the fallback when there's a value. Chapter 5 is about this idea.

Reading it as a pipeline

case class Employee(name: String, dept: String, manager: Option[String])
def lookupByName(name: String): Option[Employee] = ???

val managerOfJoe: String =
  lookupByName("Joe")
    .flatMap(_.manager)        // Joe might not exist, or might have no manager
    .map(_.toUpperCase)
    .getOrElse("(no manager)")

Each step is written as if the value is there. If any step returns None, the rest are skipped and None falls through to getOrElse. The error handling is still there; it's just been moved into flatMap.

Use map when your function always succeeds. Use flatMap when your function can itself fail (returns an Option). Handle the failure once, at the end, with getOrElse or a match.

Using flatMap and the mean function above, write variance(xs: Seq[Double]): Option[Double], the mean of math.pow(x - m, 2) for each x, where m is the mean.

Show solution
def variance(xs: Seq[Double]): Option[Double] =
  mean(xs).flatMap(m => mean(xs.map(x => math.pow(x - m, 2))))

The empty case is handled once, by the first mean. flatMap because the inner computation also returns Option.

4.4Lifting Ordinary Functions

Do we need to rewrite every existing function to accept Options? No. We lift them:

def lift[A, B](f: A => B): Option[A] => Option[B] =
  _.map(f)

val absO: Option[Double] => Option[Double] = lift(math.abs)

Now a function of two arguments. Insurance quotes need age and number of tickets, both parsed from strings that might be malformed:

def insuranceRate(age: Int, tickets: Int): Double = ???

def toIntOption(s: String): Option[Int] =
  try Some(s.toInt)
  catch case _: NumberFormatException => None

(This is the right way to deal with an exception-throwing library: catch it at the boundary and convert it to a value.) To combine two Options with a two-argument function, we need map2:

Write def map2[A, B, C](a: Option[A], b: Option[B])(f: (A, B) => C): Option[C]. Then use it to write parseInsuranceRateQuote(age: String, tickets: String): Option[Double].

Show solution
def map2[A, B, C](a: Option[A], b: Option[B])(f: (A, B) => C): Option[C] =
  a.flatMap(aa => b.map(bb => f(aa, bb)))

def parseInsuranceRateQuote(age: String, tickets: String): Option[Double] =
  map2(toIntOption(age), toIntOption(tickets))(insuranceRate)

The nesting "flatMap on the outer, map on the inner" comes up constantly. Scala has syntax for it:

def map2[A, B, C](a: Option[A], b: Option[B])(f: (A, B) => C): Option[C] =
  for
    aa <- a
    bb <- b
  yield f(aa, bb)

A for-comprehension is just sugar: every <- except the last becomes flatMap, the last becomes map. It works for any type with those methods, which is why it reads like a loop for lists and like sequential steps for Option.

4.5sequence and traverse

We have a list of strings and want to parse them all. If any fails, the whole thing fails.

Write def sequence[A](as: List[Option[A]]): Option[List[A]]. It returns Some of all values if every element is Some, else None. (Use Scala's built-in List from here on.)

Show solution
def sequence[A](as: List[Option[A]]): Option[List[A]] =
  as.foldRight(Some(Nil): Option[List[A]])((oa, acc) => map2(oa, acc)(_ :: _))

Start from Some(Nil), and at each element use map2 to prepend the value to the accumulated list. One None anywhere makes map2 return None, and it stays None.

Using it: sequence(strings.map(toIntOption)). That walks the list twice: once to build a list of Options, once to sequence it. traverse does both in one pass:

def traverse[A, B](as: List[A])(f: A => Option[B]): Option[List[B]] =
  as.foldRight(Some(Nil): Option[List[B]])((a, acc) => map2(f(a), acc)(_ :: _))

def sequence[A](as: List[Option[A]]): Option[List[A]] =
  traverse(as)(identity)

traverse(List("1", "2", "3"))(toIntOption)   // Some(List(1, 2, 3))
traverse(List("1", "x", "3"))(toIntOption)   // None

Remember traverse. In Chapter 12 it turns out to work for far more than List and Option, and it's one of the most useful functions in real FP code.

4.6Either: Failure With a Reason

None says that something failed, not why. Either carries the reason:

enum Either[+E, +A]:
  case Left(value: E)      // failure, by convention
  case Right(value: A)     // success ("right" as in correct)

  def map[B](f: A => B): Either[E, B] = this match
    case Right(a) => Right(f(a))
    case Left(e)  => Left(e)

  def flatMap[EE >: E, B](f: A => Either[EE, B]): Either[EE, B] = this match
    case Right(a) => f(a)
    case Left(e)  => Left(e)

  def orElse[EE >: E, AA >: A](b: => Either[EE, AA]): Either[EE, AA] = this match
    case Left(_)  => b
    case Right(a) => Right(a)

Notice that the definitions are nearly identical to Option's. Left(e) plays the role of None but keeps e. Keep noticing that.

def safeDiv(x: Int, y: Int): Either[String, Int] =
  if y == 0 then Left("division by zero") else Right(x / y)

case class Person(name: String, age: Int)

def mkName(name: String): Either[String, String] =
  if name.isBlank then Left("Name is empty.") else Right(name)

def mkAge(age: Int): Either[String, Int] =
  if age < 0 then Left("Age is out of range.") else Right(age)

def mkPerson(name: String, age: Int): Either[String, Person] =
  for
    n <- mkName(name)
    a <- mkAge(age)
  yield Person(n, a)

mkPerson("", -1)   // Left("Name is empty.")  — only the FIRST error

flatMap stops at the first error. It has to: the second step might depend on the result of the first. But in mkPerson, name and age are independent, and a user filling in a form wants to see both problems. That needs a different abstraction, less powerful than flatMap, which you'll meet in Chapter 12.

Write def catchNonFatal[A](a: => A): Either[Throwable, A] that runs a and captures any non-fatal exception as a Left.

Show solution
import scala.util.control.NonFatal

def catchNonFatal[A](a: => A): Either[Throwable, A] =
  try Right(a)
  catch case NonFatal(t) => Left(t)

The by-name parameter is essential: if a were evaluated before entering the function, the exception would be thrown before the try. NonFatal deliberately doesn't catch things like OutOfMemoryError.

4.7In the Standard Library

Scala's own Option, Either and Try work as described. Standard Either is right-biased, so map and flatMap work on Right, just like ours. traverse isn't in the standard library. It comes from the cats library, which we'll meet at the end of the book.

Option
A value that may be absent: Some(a) or None.
Either
A success Right(a) or a failure Left(e) that carries the error.
Lifting
Turning A => B into F[A] => F[B], usually with map.
map2
Combine two wrapped values with a two-argument function.
traverse
Apply a failing function to each element, collecting results or failing as a whole.
By-name parameter (=> A)
An argument evaluated only when (and each time) it's used.
  • Exceptions aren't RT and aren't in the type. Return Option or Either instead.
  • Catch exceptions at library boundaries and turn them into values.
  • Write the happy path with map, flatMap or a for-comprehension. Handle failure once at the end.
  • map2, sequence and traverse combine many fallible values.
  • Option and Either have nearly identical combinators. That's a clue.
