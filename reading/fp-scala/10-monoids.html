Monoids

Our first abstraction defined purely by its laws. A monoid is a type with an associative combine and an identity. That's all, and it's enough to fold any collection, split work across cores, and build complex aggregations out of simple ones.

10.1Spot the Pattern

"foo" + "bar"      // string concatenation, identity ""
3 + 4              // integer addition,       identity 0
3 * 4              // integer multiplication, identity 1
true && false      // boolean and,            identity true
List(1) ++ List(2) // list append,            identity Nil

Each has a binary operation and a special "do-nothing" value. And each satisfies two laws:

  • Associativity: (x op y) op z == x op (y op z). Grouping doesn't matter.
  • Identity: x op empty == x and empty op x == x.

A type with such an operation and identity is a monoid. In code:

trait Monoid[A]:
  def combine(a1: A, a2: A): A
  def empty: A

val stringMonoid: Monoid[String] = new:
  def combine(a1: String, a2: String) = a1 + a2
  val empty = ""

def listMonoid[A]: Monoid[List[A]] = new:
  def combine(a1: List[A], a2: List[A]) = a1 ++ a2
  val empty = Nil

The trait alone says almost nothing. The laws are what make something a monoid. Note that the same type can have several monoids: Int under + and under *.

A monoid is like a box of identical Lego bricks: any two snap together into a bigger brick of the same kind, it doesn't matter which pairs you snap first, and there's a "nothing" brick that changes nothing when attached. That's enough to build anything out of any number of pieces, in any order of assembly.

Give monoids for Int addition, Boolean or, Option[A] (keep the first Some), and A => A (endofunctions, under composition).

Show solution
val intAddition: Monoid[Int] = new:
  def combine(x: Int, y: Int) = x + y
  val empty = 0

val booleanOr: Monoid[Boolean] = new:
  def combine(x: Boolean, y: Boolean) = x || y
  val empty = false

def firstOption[A]: Monoid[Option[A]] = new:
  def combine(x: Option[A], y: Option[A]) = x.orElse(y)
  val empty = None

def endoMonoid[A]: Monoid[A => A] = new:
  def combine(f: A => A, g: A => A) = f.andThen(g)
  val empty = identity

Every one of these also has a "dual": combine with the arguments swapped. For firstOption the dual keeps the last Some; for endofunctions it composes the other way.

10.2Folding With Monoids

Look at foldLeft's type, and at the monoid:

def foldLeft[B](z: B)(op: (B, A) => B): B
// with A = B, a monoid's empty fits z and combine fits op
val words = List("Hic", "Est", "Index")
words.foldLeft(stringMonoid.empty)(stringMonoid.combine)    // "HicEstIndex"
words.foldRight(stringMonoid.empty)(stringMonoid.combine)   // same, by associativity

The laws guarantee foldLeft and foldRight give the same answer. That's what lets an implementation choose the most efficient order.

What if the elements aren't already of the monoid type? Map them first:

def combineAll[A](as: List[A], m: Monoid[A]): A =
  as.foldLeft(m.empty)(m.combine)

def foldMap[A, B](as: List[A], m: Monoid[B])(f: A => B): B =
  as.foldLeft(m.empty)((b, a) => m.combine(b, f(a)))

foldMap(List("a", "bb", "ccc"), intAddition)(_.length)   // 6

foldMap is so general that foldLeft and foldRight can themselves be written with it, using the endofunction monoid. (That's a classic puzzle; try it.)

10.3Associativity Means Parallelism

Because grouping doesn't matter, these are equal:

((a op b) op c) op d       // fold left: a chain, depth 3
(a op b) op (c op d)       // balanced: a tree, depth 2

In the balanced form, a op b and c op d don't depend on each other: they can run in parallel. So:

def foldMapV[A, B](as: IndexedSeq[A], m: Monoid[B])(f: A => B): B =
  if as.isEmpty then m.empty
  else if as.length == 1 then f(as(0))
  else
    val (l, r) = as.splitAt(as.length / 2)
    m.combine(foldMapV(l, m)(f), foldMapV(r, m)(f))

Swap the recursion for Par from Chapter 7 and it runs on all cores. Any monoid gives you a correct parallel reduction for free.

This is exactly the contract of std::reduce with an execution policy, as opposed to std::accumulate. std::reduce(std::execution::par, ...) requires the operation to be associative and commutative, because it regroups and reorders. A monoid states the associativity requirement in the type. It's also the contract of MapReduce's combiners and of Spark's reduce.

Floating-point addition isn't associative. (1e20 + -1e20) + 1.0 == 1.0, but 1e20 + (-1e20 + 1.0) == 0.0. A parallel fold over doubles may give slightly different answers from a sequential one. It's "close enough" to a monoid for most uses, but don't be surprised when results change with the number of threads.

10.4A Clever Monoid: Counting Words in Parallel

Split a big text into chunks and count words in parallel. The trouble is that a chunk boundary might fall in the middle of a word: "lorem ipsum do" | "lor sit amet". We need a summary of each chunk that can be combined correctly. Design the type so it has a monoid:

enum WC:
  case Stub(chars: String)                         // no whitespace seen: maybe part of a word
  case Part(lStub: String, words: Int, rStub: String)
  // lStub: partial word at the left edge; words: complete words; rStub: partial word at the right edge

val wcMonoid: Monoid[WC] = new:
  val empty = WC.Stub("")
  def combine(a: WC, b: WC) = (a, b) match
    case (WC.Stub(x), WC.Stub(y))             => WC.Stub(x + y)
    case (WC.Stub(x), WC.Part(l, w, r))       => WC.Part(x + l, w, r)
    case (WC.Part(l, w, r), WC.Stub(y))       => WC.Part(l, w, r + y)
    case (WC.Part(l1, w1, r1), WC.Part(l2, w2, r2)) =>
      WC.Part(l1, w1 + (if (r1 + l2).isEmpty then 0 else 1) + w2, r2)

The key line is the last case: where two parts meet, the right stub of the first and the left stub of the second join into one word (if non-empty).

def countWords(s: String): Int =
  def wc(c: Char): WC =
    if c.isWhitespace then WC.Part("", 0, "")
    else WC.Stub(c.toString)
  def unstub(s: String) = if s.isEmpty then 0 else 1
  foldMapV(s.toIndexedSeq, wcMonoid)(wc) match
    case WC.Stub(s)       => unstub(s)
    case WC.Part(l, w, r) => unstub(l) + w + unstub(r)
When a computation needs to be split up, ask: what summary of a chunk can I combine associatively? Designing that summary type with a monoid in mind is a general technique for parallel and incremental algorithms.

10.5Foldable: Folding Anything

foldMap works on lists. Trees, lazy lists and options can also be folded. Abstract over the container:

trait Foldable[F[_]]:
  extension [A](as: F[A])
    def foldRight[B](acc: B)(f: (A, B) => B): B
    def foldLeft[B](acc: B)(f: (B, A) => B): B
    def foldMap[B](f: A => B)(using m: Monoid[B]): B =
      as.foldLeft(m.empty)((b, a) => m.combine(b, f(a)))
    def combineAll(using m: Monoid[A]): A =
      as.foldLeft(m.empty)(m.combine)
    def toList: List[A] =
      as.foldRight(List.empty[A])(_ :: _)

F[_] is a type constructor, as in Chapter 9. A Foldable[Tree] instance says "here's how to fold a Tree of anything".

The using clause is new. It asks the compiler to find a Monoid[B] automatically from the given instances in scope:

given Foldable[List] with
  extension [A](as: List[A])
    def foldRight[B](acc: B)(f: (A, B) => B) = as.foldRight(acc)(f)   // List's own method
    def foldLeft[B](acc: B)(f: (B, A) => B) = as.foldLeft(acc)(f)

given intAdditionGiven: Monoid[Int] = intAddition
given Monoid[String] = stringMonoid

List(1, 2, 3).foldMap(_ * 10)      // uses the given Monoid[Int]: 60

These are type classes: a trait describing a capability (Monoid, Foldable), instances for specific types, and functions that request an instance with using. It's how Scala FP libraries attach abstractions to types without inheritance.

Type classes are close to C++20 concepts plus explicit specialisation. template<typename T> requires Monoid<T> checks the operations exist; a Scala type class also passes the implementation, so Int can have two monoids and you choose one at the call site. A closer analogy is a traits class, like std::char_traits<C> or std::hash<T>, found automatically.

10.6Composing Monoids

Monoids combine into bigger monoids. If A and B are monoids, so is the pair (A, B):

given productMonoid[A, B](using ma: Monoid[A], mb: Monoid[B]): Monoid[(A, B)] with
  def combine(x: (A, B), y: (A, B)) = (ma.combine(x(0), y(0)), mb.combine(x(1), y(1)))
  val empty = (ma.empty, mb.empty)

A Map whose values are a monoid is a monoid (merge keys, combine values on collision). A function whose result is a monoid is a monoid. That lets you compute several aggregates in one pass:

// count and sum in a single fold, then compute the mean
val (count, total) = List(4, 8, 15, 16, 23, 42).foldMap(x => (1, x))
val mean = total.toDouble / count     // 18.0

The pair monoid is found automatically from Monoid[Int] and Monoid[Int]. Nest it further for min, max, histograms (a Map monoid) and so on, all in one traversal, and all parallelisable.

Write mapMergeMonoid[K, V](using Monoid[V]): Monoid[Map[K, V]]. Then use it with foldMap to write bag[A](as: IndexedSeq[A]): Map[A, Int], which counts occurrences.

Show solution
given mapMergeMonoid[K, V](using mv: Monoid[V]): Monoid[Map[K, V]] with
  def combine(a: Map[K, V], b: Map[K, V]) =
    (a.keySet ++ b.keySet).map { k =>
      k -> mv.combine(a.getOrElse(k, mv.empty), b.getOrElse(k, mv.empty))
    }.toMap
  val empty = Map()

def bag[A](as: IndexedSeq[A]): Map[A, Int] =
  foldMapV(as, summon[Monoid[Map[A, Int]]])(a => Map(a -> 1))

bag(Vector("a", "rose", "is", "a", "rose"))
// Map(a -> 2, rose -> 2, is -> 1)

summon[T] fetches the given instance of T.

  • A monoid is a combine operation plus an identity, satisfying associativity and identity laws.
  • Associativity makes folds order-independent and parallelisable.
  • To parallelise a problem, design a chunk summary type with a monoid (like word count).
  • Foldable abstracts folding over containers. Type classes attach monoids to types.
  • Monoids compose: products, maps and functions of monoids are monoids, giving multi-aggregate single passes.
