Monoids

Our first abstraction defined purely by its laws. A monoid is a type with an associative combine and an identity. That's all, and it's enough to fold any range, split work across cores, and build complex aggregations from simple ones. In C++ it's a concept plus "instance" structs, the same way std::plus works.

10.1Spot the Pattern

"foo" + "bar"          string concatenation,   identity ""
3 + 4                  integer addition,       identity 0
3 * 4                  integer multiplication, identity 1
true || false          boolean or,             identity false
concat(v1, v2)         vector append,          identity {}

Each has a binary operation and a "do-nothing" value, and each satisfies two laws:

  • Associativity: (x ⊕ y) ⊕ z == x ⊕ (y ⊕ z). Grouping doesn't matter.
  • Identity: x ⊕ empty == x and empty ⊕ x == x.

A type with such an operation and identity is a monoid. Note that the same type can have several: int under + and under *. So in C++ a monoid isn't a property of a type; it's a separate little struct, an instance, that names the type and supplies the two operations:

template <typename M>
concept Monoid = requires(const typename M::type& a, const typename M::type& b) {
    { M::empty() }        -> std::convertible_to<typename M::type>;
    { M::combine(a, b) }  -> std::convertible_to<typename M::type>;
};

struct StringConcat {
    using type = std::string;
    static type empty() { return ""; }
    static type combine(const type& a, const type& b) { return a + b; }
};

struct IntAddition {
    using type = int;
    static type empty() { return 0; }
    static type combine(int a, int b) { return a + b; }
};

The concept checks the operations exist. It can't check the laws, and the laws are what make something a monoid. (Chapter 8's property tests can.)

A monoid is a box of identical Lego bricks: any two snap together into a bigger brick of the same kind, it doesn't matter which pairs you snap first, and there's a "nothing" brick that changes nothing. That's enough to build anything from any number of pieces, assembled in any grouping.

The book writes trait Monoid[A] { def combine(a1: A, a2: A): A; def empty: A } and passes instances as values or givens found by the compiler. Our instance structs are the C++ equivalent, passed as template arguments, the way std::plus<> or a comparator is.

Write monoids for bool under ||, std::optional<T> (keep the first engaged one), and functions T → T under composition. What is each one's "dual"?

Show solution
struct BoolOr {
    using type = bool;
    static type empty() { return false; }
    static type combine(bool a, bool b) { return a || b; }
};

template <typename T> struct FirstOptional {
    using type = std::optional<T>;
    static type empty() { return std::nullopt; }
    static type combine(const type& a, const type& b) { return a ? a : b; }
};

template <typename T> struct Endo {
    using type = std::function<T(T)>;
    static type empty() { return [](T t) { return t; }; }
    static type combine(type f, type g) { return [f, g](T t) { return g(f(t)); }; }  // f, then g
};

template <Monoid M> struct Dual {     // same monoid, arguments swapped
    using type = typename M::type;
    static type empty() { return M::empty(); }
    static type combine(const type& a, const type& b) { return M::combine(b, a); }
};

Dual<FirstOptional> keeps the last engaged optional; Dual<Endo> composes the other way round. Every monoid has a dual.

10.2Folding With Monoids

A monoid's empty is exactly the starting value a fold needs, and combine is exactly its step. And since we can map elements into the monoid first, we get the workhorse of this chapter:

template <Monoid M, std::ranges::input_range R, typename F>
typename M::type fold_map(const R& xs, F f) {
    auto acc = M::empty();
    for (const auto& x : xs) acc = M::combine(acc, f(x));
    return acc;
}

fold_map<IntAddition>(std::vector<std::string>{"a", "bb", "ccc"},
                       [](const std::string& s) { return (int)s.size(); });   // 6

Associativity guarantees that folding from the left or the right gives the same answer, which lets the implementation choose the most efficient order.

Note the std::ranges::input_range constraint: fold_map works for vectors, lists, sets, views, even our LazyList with an iterator. The book defines a Foldable type class for "things you can fold"; in C++ that's simply the range concepts.

fold_map is so general that fold_right can be written with it, using the endofunction monoid: map each element a to the function b ↦ f(a, b), compose them all (with Dual<Endo> for the right order), and apply the result to the starting value. The full listing does exactly that.

10.3Associativity Means Parallelism

Because grouping doesn't matter, these are equal:

((a ⊕ b) ⊕ c) ⊕ d       a chain: depth 3, strictly sequential
(a ⊕ b) ⊕ (c ⊕ d)       a tree:  depth 2, the two halves are independent

In the balanced form, a ⊕ b and c ⊕ d don't depend on each other, so they can run on different cores:

template <Monoid M, typename A, typename F>
typename M::type fold_map_par(std::span<const A> as, F f, int depth = 3) {
    if (depth == 0 || as.size() < 2) return fold_map_balanced<M>(as, f);
    auto l = as.first(as.size() / 2), r = as.subspan(as.size() / 2);
    auto left = std::async(std::launch::async, [=] { return fold_map_par<M>(l, f, depth - 1); });
    auto right = fold_map_par<M>(r, f, depth - 1);
    return M::combine(left.get(), right);
}

Any monoid gives you a correct parallel reduction for free. You don't have to think about the operation at all, only about whether it's a monoid.

This is precisely the contract of std::reduce (and std::transform_reduce, which is fold_map) with an execution policy, as opposed to std::accumulate. std::reduce requires the operation to be associative (and commutative) because it regroups and reorders, and the initial value should be an identity. It's also the contract of MPI_Reduce, CUDA's reductions and Spark's reduce.

Floating-point addition isn't associative. (1e20 + -1e20) + 1.0 == 1.0, but 1e20 + (-1e20 + 1.0) == 0.0. A parallel sum of doubles can differ from a sequential one, and change with the thread count. It's close enough to a monoid for most uses, but it explains "non-deterministic" results from std::reduce and GPU reductions.

10.4A Clever Monoid: Counting Words in Parallel

Split a big text into chunks and count words in parallel. The trouble: a chunk boundary can fall mid-word, as in "lorem ipsum do" | "lor sit amet". We need a summary of each chunk that can be combined correctly. Design the summary type so it has a monoid:

struct Stub { std::string chars; };                                  // no whitespace seen: maybe part of a word
struct Part { std::string l_stub; int words; std::string r_stub; };   // partial | complete words | partial
using WC = std::variant<Stub, Part>;

struct WCMonoid {
    using type = WC;
    static type empty() { return Stub{""}; }
    static type combine(const WC& a, const WC& b) {
        return std::visit(overloaded{
            [](const Stub& x, const Stub& y) -> WC { return Stub{x.chars + y.chars}; },
            [](const Stub& x, const Part& p) -> WC { return Part{x.chars + p.l_stub, p.words, p.r_stub}; },
            [](const Part& p, const Stub& y) -> WC { return Part{p.l_stub, p.words, p.r_stub + y.chars}; },
            [](const Part& p1, const Part& p2) -> WC {
                int joined = (p1.r_stub + p2.l_stub).empty() ? 0 : 1;   // stubs meeting at the seam: one word
                return Part{p1.l_stub, p1.words + joined + p2.words, p2.r_stub};
            },
        }, a, b);
    }
};

std::visit over two variants at once gives a 2×2 pattern match. The key case is the last: where two parts meet, the right stub of the first and the left stub of the second join into one word, if non-empty. Each character maps to a WC (whitespace → empty Part, other → one-char Stub), and fold_map_par does the rest in parallel.

To parallelise a computation, ask: what summary of a chunk can I combine associatively? Designing that summary type with a monoid in mind is a general technique for parallel, distributed and incremental algorithms.

10.5Composing Monoids

Monoids combine into bigger monoids. If A and B have monoids, so does the pair:

template <Monoid MA, Monoid MB> struct ProductMonoid {
    using type = std::pair<typename MA::type, typename MB::type>;
    static type empty() { return {MA::empty(), MB::empty()}; }
    static type combine(const type& x, const type& y) {
        return {MA::combine(x.first, y.first), MB::combine(x.second, y.second)};
    }
};

// count and sum in ONE pass, then the mean
std::vector<int> data{4, 8, 15, 16, 23, 42};
auto [count, total] = fold_map<ProductMonoid<IntAddition, IntAddition>>(
    data, [](int x) { return std::pair{1, x}; });
double mean = double(total) / count;   // 18.0

A std::map whose values form a monoid is a monoid (merge keys, combine values on collision). Functions returning a monoid form a monoid. Nest them for min, max, histograms and so on, all computed in one traversal, all parallelisable.

Write MapMerge<K, MV>, a monoid for std::map<K, V> given a monoid MV for the values. Use it to write bag(vector<A>) → map<A, int>, which counts occurrences.

Show solution
template <typename K, Monoid MV> struct MapMerge {
    using type = std::map<K, typename MV::type>;
    static type empty() { return {}; }
    static type combine(type a, const type& b) {
        for (const auto& [k, v] : b) {
            auto it = a.find(k);
            a[k] = MV::combine(it == a.end() ? MV::empty() : it->second, v);
        }
        return a;
    }
};

template <typename A> std::map<A, int> bag(const std::vector<A>& as) {
    return fold_map<MapMerge<A, IntAddition>>(as, [](const A& a) { return std::map<A, int>{{a, 1}}; });
}

bag(std::vector<std::string>{"a", "rose", "is", "a", "rose"});   // {a: 2, is: 1, rose: 2}

Taking a by value and modifying the local copy is fine: it's local mutation, invisible to callers.

Instance struct

Map each element into a monoid, then combine everything. std::transform_reduce.

A function between monoids that preserves combine: size(a + b) == size(a) + size(b).
  • A monoid is a combine operation plus an identity, obeying associativity and identity laws.
  • In C++: a concept for the operations, instance structs for each monoid, laws checked by tests.
  • Associativity makes folds order-independent and parallel; it's the std::reduce contract.
  • To parallelise a problem, design a chunk summary type with a monoid (like the word count).
  • Monoids compose (pairs, maps, functions), giving many aggregates in one pass.
