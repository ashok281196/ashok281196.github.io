What Functional Programming Actually Is

One constraint, no side effects, and why taking it seriously makes code easier to test, reuse and reason about. We'll refactor one impure function into a pure one and watch new abilities appear.

1.1The Definition

Functional programming means building programs out of pure functions. A pure function has no side effects: the only thing it does is compute a result from its inputs.

A side effect is anything a function does besides returning a value:

  • modifying a variable outside its own scope, or mutating an argument
  • throwing an exception
  • printing, reading input, writing a file, making a network call
  • reading the clock, generating a random number

That list looks like most of what useful programs do, and that's the fair objection. The answer, which the whole book builds toward, is that FP doesn't stop you doing these things. It changes where they happen. The core of the program is pure and only describes effects. A thin outer layer actually performs them.

FP does not ban effects. It pushes them to the edges, so that the large, interesting middle of your program is made of functions you can understand in isolation.

1.2A Function With Side Effects

Here's a typical piece of code: book a train ticket and charge the customer's card.

class Ticket(val route: String, val price: Int)

class PaymentGateway:
  def charge(card: String, amount: Int): Unit =
    // talks to the bank over the network
    ???

class BookingService:
  def book(card: String, route: String, gateway: PaymentGateway): Ticket =
    val t = Ticket(route, 450)
    gateway.charge(card, t.price)   // side effect!
    t

It works, but look at what it costs us:

  1. Testing is awkward. To test book we need a fake PaymentGateway, a mock framework, and checks that charge was called exactly once with the right amount.
  2. It doesn't compose. A family books four tickets. Calling book four times hits the bank four times, with four fees and four chances to fail halfway. We'd like one charge for the total, but the charge is fused into book.

1.3Step 1: Return the Effect Instead of Doing It

The fix is to make the charge a value. Instead of performing the charge, book returns a description of the charge alongside the ticket.

case class Charge(card: String, amount: Int):
  def combine(other: Charge): Charge =
    if card == other.card then Charge(card, amount + other.amount)
    else throw IllegalArgumentException("different cards")

class BookingService:
  def book(card: String, route: String): (Ticket, Charge) =
    val t = Ticket(route, 450)
    (t, Charge(card, t.price))

book is now pure. It doesn't know a payment gateway exists. Some other part of the program, the outer layer, takes the Charge and actually sends it to the bank.

(combine still throws. We'll fix that in Chapter 4, when errors become values too.)

1.4Step 2: Collect New Abilities for Free

Because charges are values, we can work with them like any data:

def bookMany(card: String, route: String, n: Int): (List[Ticket], Charge) =
  val bookings = List.fill(n)(book(card, route))
  val (tickets, charges) = bookings.unzip
  (tickets, charges.reduce((c1, c2) => c1.combine(c2)))

Four tickets, one charge. We reused book unchanged. And since it's just values, we can go further: merge all charges from a whole day per card, before sending anything to the bank.

def coalesce(charges: List[Charge]): List[Charge] =
  charges.groupBy(_.card).values.map(_.reduce(_.combine(_))).toList

Testing is now an equality check: assert(book("c1", "BLR-JAI") == ...). No mocks.

The impure version is a chef who cooks and also pays the supplier while plating. The pure version writes the supplier's invoice and puts it on a spike. At the end of the day someone pays all the invoices in one go. The chef's job got simpler, and the restaurant can now batch, audit or cancel payments.

1.5Referential Transparency

We need a precise test for "pure". Here it is.

An expression is referentially transparent (RT) if you can replace it with its result anywhere in the program without changing what the program means. A function is pure if calling it with RT arguments always gives an RT expression.

2 + 3 is RT: wherever it appears you can write 5 and nothing changes. Now strings:

val x = "Hello"
val r1 = x.reverse       // "olleH"
val r2 = x.reverse       // "olleH"
// replace x with its definition:
val r1b = "Hello".reverse
val r2b = "Hello".reverse   // same results; x is RT

Now something mutable:

val sb = StringBuilder("Hello")
val y  = sb.append(", World")
val r1 = y.toString     // "Hello, World"
val r2 = y.toString     // "Hello, World"

// substitute y with its definition:
val sb2 = StringBuilder("Hello")
val r1b = sb2.append(", World").toString   // "Hello, World"
val r2b = sb2.append(", World").toString   // "Hello, World, World"  ← different!

append is not RT: the same expression gave two different answers because it changed hidden state. That's the whole problem with side effects. You can't understand an expression by looking at it. You also need to know everything that happened before.

1.6The Substitution Model

RT gives you a simple way to reason about code: replace things with their definitions, like simplifying algebra.

def square(n: Int) = n * n
def sumOfSquares(a: Int, b: Int) = square(a) + square(b)

sumOfSquares(3, 4)
= square(3) + square(4)
= 3 * 3 + 4 * 4
= 9 + 16
= 25

Each step is a local rewrite. You never need to ask "what is the state of memory right now?" This is local reasoning, and it's what lets you understand a 30-line pure function without reading the 3,000 lines around it.

You already prize this in C++. A constexpr function the compiler can evaluate at compile time is basically RT. A const member function that doesn't touch mutable fields is a step toward it. Data races are what you get when two threads break RT on shared state at once. FP applies that discipline to the whole program by default, not just to the hot paths you've had to debug.

1.7Why It's Worth It

  • Modularity. A pure function's behaviour is entirely in its signature and body. Anyone can reuse it without knowing its context.
  • Testability. Inputs in, outputs out. You'll see in Chapter 8 that this enables property-based testing: checking a law against thousands of random inputs.
  • Concurrency. Immutable data can be shared across threads without locks.
  • Refactoring. If you can always replace an expression with its value, extracting, inlining and reordering code is safe.

"Pure" is about what callers can observe, not how the function is written inside. A function that builds a local mutable array, fills it in a loop, and returns an immutable copy is still pure: no one outside can tell. Chapter 13 makes this precise with the ST type. Don't refuse an efficient local loop for ideological reasons.

1.8Exercises

Which of these are referentially transparent? (a) math.max(3, 7) (b) System.currentTimeMillis() (c) List(1,2,3).map(_ + 1) (d) scala.util.Random.nextInt(10) (e) println("hi")

Show solution

(a) and (c) are RT. (b) and (d) give different results each call, so you can't replace them with any one value. (e) returns () every time, but replacing println("hi") with () deletes the printing, which changes the program's meaning. Not RT.

Fix Charge.combine so the case "different cards" can't throw. Hint: what could the function return instead of a Charge?

Show solution

Return a value that can say "no result": Option[Charge].

def combine(other: Charge): Option[Charge] =
  if card == other.card then Some(Charge(card, amount + other.amount))
  else None

The type now tells callers the truth: combining can fail. Chapter 4 is all about making this pleasant to work with.

This function uses a mutable variable. Is it pure?

def sumTo(n: Int): Int =
  var acc = 0
  for i <- 1 to n do acc += i
  acc
Show solution

Yes. acc is created, mutated and dropped inside the call, so no caller can observe it. sumTo(10) can always be replaced with 55. Purity is about the outside view.

Side effect
Anything a function does other than return a value: mutation, I/O, exceptions, reading the clock.
Pure function
A function whose result depends only on its inputs and which has no side effects.
Referential transparency
An expression can be replaced by its value without changing the program's meaning.
Substitution model
Reasoning about code by repeatedly replacing names with their definitions, like algebra.
  • FP is programming with pure functions. Effects move to the edge of the program.
  • Turn effects into values (a Charge instead of a charge) and you can combine, batch and test them.
  • RT is the test for purity: replace an expression with its result and nothing changes.
  • RT enables the substitution model and local reasoning.
