What Functional Programming Actually Is

One constraint, no side effects, and why taking it seriously makes code easier to test, reuse and reason about. We refactor one impure C++ function into a pure one and watch new abilities appear.

1.1The Definition

Functional programming means building programs out of pure functions. A pure function has no side effects: the only thing it does is compute a result from its arguments.

A side effect is anything a function does besides returning a value:

  • modifying a global, a static, a member through this, or an argument passed by non-const reference
  • throwing an exception
  • printing, reading input, writing a file, sending a packet
  • reading the clock, generating a random number

That looks like most of what useful programs do, and it's a fair objection. The answer, which the whole book builds toward, is that FP doesn't stop you doing these things. It changes where they happen. The core of the program is pure and only describes effects. A thin outer layer performs them.

FP does not ban effects. It pushes them to the edges, so that the large, interesting middle of your program is made of functions you can understand in isolation.

1.2A Function With Side Effects

A typical piece of code: book a train ticket and charge the customer's card.

struct Ticket { std::string route; int price; };

struct PaymentGateway {
    void charge(const std::string& card, int amount);   // talks to the bank
};

Ticket book(const std::string& card, const std::string& route, PaymentGateway& gw) {
    Ticket t{route, 450};
    gw.charge(card, t.price);     // side effect, hidden inside
    return t;
}

It works, but look at what it costs:

  1. Testing is awkward. To test book you need a fake gateway (a virtual interface, or a template parameter, or gMock) and checks that charge was called exactly once with the right amount.
  2. It doesn't compose. A family books four tickets. Calling book four times hits the bank four times, with four fees and four chances to fail halfway. You'd like one charge for the total, but the charge is fused into book.

1.3Step 1: Return the Effect Instead of Doing It

Make the charge a value. Instead of performing it, book returns a description of it alongside the ticket:

struct Charge {
    std::string card;
    int amount;
    bool operator==(const Charge&) const = default;

    Charge combine(const Charge& other) const {
        if (card != other.card) throw std::invalid_argument("different cards");
        return {card, amount + other.amount};
    }
};

struct Booking { Ticket ticket; Charge charge; };

Booking book(const std::string& card, const std::string& route) {
    Ticket t{route, 450};
    return {t, Charge{card, t.price}};
}

book is now pure. It doesn't know a payment gateway exists. Some other part of the program, the outer layer, takes the Charge and sends it to the bank.

(combine still throws. We'll fix that in the exercises, and properly in Chapter 4.)

1.4Step 2: New Abilities for Free

Because charges are values, you can work with them like any data:

std::pair<std::vector<Ticket>, Charge>
book_many(const std::string& card, const std::string& route, int n) {
    std::vector<Ticket> tickets;
    Charge total{card, 0};
    for (int i = 0; i < n; ++i) {
        auto [t, c] = book(card, route);
        tickets.push_back(t);
        total = total.combine(c);
    }
    return {tickets, total};
}

Four tickets, one charge, and book was reused unchanged. Go further: merge a whole day's charges per card before anything reaches the bank.

std::vector<Charge> coalesce(const std::vector<Charge>& charges) {
    std::map<std::string, int> by_card;
    for (const auto& c : charges) by_card[c.card] += c.amount;
    std::vector<Charge> out;
    for (const auto& [card, amt] : by_card) out.push_back({card, amt});
    return out;
}

Testing is now an equality check: assert(book("c1", "BLR-JAI").charge == Charge{"c1", 450}). No mocks, no interfaces.

(Yes, book_many and coalesce mutate local variables. That's fine: no caller can see it. More on this in 1.7.)

The impure version is a chef who cooks and also pays the supplier while plating. The pure version writes the supplier's invoice and puts it on a spike. At the end of the day someone pays all the invoices at once. The chef's job got simpler, and the restaurant can now batch, audit or cancel payments.

1.5Referential Transparency

We need a precise test for "pure". Here it is.

An expression is referentially transparent (RT) if you can replace it with its result anywhere in the program without changing what the program means. A function is pure if calling it with RT arguments always gives an RT expression.

2 + 3 is RT: write 5 anywhere instead and nothing changes. A std::string used as a value is RT too:

const std::string x = "Hello";
std::string r1(x.rbegin(), x.rend());   // "olleH"
std::string r2(x.rbegin(), x.rend());   // "olleH" — same expression, same result

Now a mutating member function:

std::string sb = "Hello";
std::string& y = sb.append(", World");
std::string a = y;                      // "Hello, World"

// substitute y with the expression that defined it:
std::string b = sb.append(", World");   // "Hello, World, World"  ← different!

append isn't RT: the same expression gave two answers because it changed hidden state. That's the whole problem with side effects. You can't understand an expression by looking at it; you also need to know everything that happened to sb before.

1.6The Substitution Model

RT gives you a simple way to reason: replace things with their definitions, as in algebra.

constexpr int square(int n) { return n * n; }
constexpr int sum_of_squares(int a, int b) { return square(a) + square(b); }

sum_of_squares(3, 4)
= square(3) + square(4)
= 3 * 3 + 4 * 4
= 9 + 16
= 25

Each step is a local rewrite. You never ask "what's in memory right now?" This is local reasoning: it lets you understand a 30-line pure function without reading the 3,000 lines around it.

You already rely on this in C++. A constexpr function the compiler evaluates at compile time is doing exactly this substitution, which is why constexpr code can't do I/O. Optimisers do it too: common-subexpression elimination is only valid for expressions the compiler can prove are RT.

The book uses the same examples with Scala's String (immutable, RT) and StringBuilder (mutable, not RT). In C++, a const std::string plays the first role and append on a non-const string plays the second.

1.7Why It's Worth It

  • Modularity. A pure function's behaviour is entirely in its signature and body. Anyone can reuse it without knowing its context.
  • Testability. Inputs in, outputs out. In Chapter 8 this enables property-based testing: checking a law against thousands of random inputs.
  • Concurrency. Immutable data can be shared across threads with no locks. Data races are, by definition, two threads breaking RT on shared state.
  • Refactoring. If an expression can always be replaced by its value, extracting, inlining and reordering code is safe.

"Pure" is about what callers can observe, not how the function is written inside. A function that builds a local std::vector, fills it in a loop and returns it by value is still pure: no one outside can tell. In C++ this is the normal, fast way to write pure functions. Chapter 13 shows how far the idea goes. Don't give up an efficient local loop for ideological reasons.

1.8Exercises

Which are referentially transparent? (a) std::max(3, 7) (b) std::chrono::steady_clock::now() (c) std::views::iota(1, 4) (d) rand() % 10 (e) std::cout << "hi"

Show solution

(a) and (c) are RT. (b) and (d) give different results each call, so you can't replace them with any one value. (e) returns std::cout every time, but replacing the expression with std::cout deletes the printing, which changes the program. Not RT.

Fix Charge::combine so the "different cards" case can't throw. What could it return instead of a Charge?

Show solution
std::optional<Charge> combine(const Charge& other) const {
    if (card != other.card) return std::nullopt;
    return Charge{card, amount + other.amount};
}

The return type now tells callers the truth: combining can fail. Chapter 4 is about making this pleasant to work with.

This function uses a mutable variable. Is it pure?

int sum_to(int n) {
    int acc = 0;
    for (int i = 1; i <= n; ++i) acc += i;
    return acc;
}
Show solution

Yes. acc is created, mutated and destroyed inside the call, so no caller can observe it. sum_to(10) can always be replaced with 55. You could even mark it constexpr.

Side effect
Anything a function does other than return a value: mutation visible outside, I/O, exceptions, reading the clock.
Pure function
A function whose result depends only on its arguments and which has no side effects.
Referential transparency
An expression can be replaced by its value without changing the program's meaning.
Substitution model
Reasoning by replacing names with their definitions, like algebra (and like constexpr evaluation).
  • FP is programming with pure functions. Effects move to the edge of the program.
  • Turn effects into values (a Charge instead of a charge) and you can combine, batch and test them.
  • RT is the test for purity: replace an expression with its result and nothing changes.
  • Local mutation that callers can't see doesn't break purity.
