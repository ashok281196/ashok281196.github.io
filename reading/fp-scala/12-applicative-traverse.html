Applicative & Traversable

Most functions we derived from Monad only ever used map2 and unit. Making those the primitives gives a weaker abstraction, Applicative, with more instances: validation that reports every error, applicatives that compose, and a traverse that works over any structure, including trees.

12.1A Weaker Interface

Look back at Chapter 11. traverse, sequence and replicate_m only used map2 and unit; they never called flat_map directly. So make those two the primitives of a separate type class:

template <typename K> struct Applicative;   // must provide unit(a) and map2(fa, fb, f)

template <> struct Applicative<OptionalK> {
    template <typename A> static std::optional<A> unit(A a) { return a; }
    template <typename A, typename B, typename Fn>
    static auto map2(const std::optional<A>& a, const std::optional<B>& b, Fn f)
        -> std::optional<std::invoke_result_t<Fn, const A&, const B&>> {
        if (a && b) return f(*a, *b);
        return std::nullopt;
    }
};

template <typename K, typename A, typename Fn>     // written once, for every applicative
auto traverse(const std::vector<A>& as, Fn f) {
    using B = typename std::invoke_result_t<Fn, const A&>::value_type;
    auto acc = Applicative<K>::unit(std::vector<B>{});
    for (const auto& a : as)
        acc = Applicative<K>::map2(acc, f(a), [](std::vector<B> v, const B& b) { v.push_back(b); return v; });
    return acc;
}

Every monad is an applicative functor (define map2 with flat_map and map, as in Chapter 11). Not every applicative is a monad. Why would we want the weaker one?

12.2The Real Difference

// Monad: the second computation is CHOSEN using the first result
flat_map(fa, [](A a) { return a > 0 ? fb : fc; });

// Applicative: both computations are FIXED up front; only their values are combined
map2(fa, fb, std::plus{});

With map2, the whole structure of the computation is known before anything runs. With flat_map, it's discovered as it runs. That trade gives each side something:

  • Monad: more power for the user; later steps can depend on earlier results.
  • Applicative: more freedom for the implementer; since steps are independent, an applicative can run them in parallel, inspect the whole structure in advance, or keep going after a failure.
A monadic program is a conversation: what you ask next depends on the answer you just got. An applicative program is a printed form: every question is on the page before anyone answers. You can't adapt a form to earlier answers, but you can hand page 1 and page 2 to two people at once, and you can list every unanswered question at the end.

Build systems are a neat C++ example. A Makefile or CMake graph declares all dependencies up front: applicative. That's what lets make -j parallelise and lets tools draw the graph. A build step that decides what to build next based on output it just produced (dynamic dependencies, like C++20 modules scanning) is monadic, and is much harder for the build system to plan.

12.3Validation: Report Every Error

Back to Chapter 4. std::expected's and_then stops at the first error, so a user with a bad name and a bad age only hears about the name. The fields are independent, so we don't need flat_map. We need an applicative that keeps errors from both sides:

template <typename E, typename A> struct Valid { A value; };
template <typename E>             struct Invalid { std::vector<E> errors; };   // ALL of them
template <typename E, typename A>
struct Validated {
    using value_type = A;
    std::variant<Valid<E, A>, Invalid<E>> v;
    bool ok() const { return v.index() == 0; }
    // value(), errors() accessors
};
template <typename E> struct ValidatedK { template <typename A> using F = Validated<E, A>; };

template <typename E> struct Applicative<ValidatedK<E>> {
    template <typename A> static Validated<E, A> unit(A a) { return {Valid<E, A>{a}}; }
    template <typename A, typename B, typename Fn>
    static auto map2(const Validated<E, A>& a, const Validated<E, B>& b, Fn f) {
        using C = std::invoke_result_t<Fn, const A&, const B&>;
        if (a.ok() && b.ok()) return Validated<E, C>{Valid<E, C>{f(a.value(), b.value())}};
        std::vector<E> errs;                                   // keep errors from BOTH sides
        if (!a.ok()) errs.insert(errs.end(), a.errors().begin(), a.errors().end());
        if (!b.ok()) errs.insert(errs.end(), b.errors().begin(), b.errors().end());
        return Validated<E, C>{Invalid<E>{errs}};
    }
};

A lawful flat_map for this type would have to stop at the first error (it can't run the second step without the first's value), so Validated is deliberately an applicative and not a monad.

Validated<std::string, User> valid_user(const std::string& n, int a, const std::string& e) {
    using AP = Applicative<ValidatedK<std::string>>;
    auto name_age = AP::map2(valid_name(n), valid_age(a),
                             [](std::string n, int a) { return std::pair{n, a}; });
    return AP::map2(name_age, valid_email(e), [](std::pair<std::string, int> na, std::string e) {
        return User{na.first, na.second, e};
    });
}

valid_user("", -5, "nope").errors();
// { "name is empty", "age -5 out of range", "bad email 'nope'" }

All three errors in one pass. This is what form validation, config loading and command-line parsing should do. And traverse<ValidatedK<std::string>>(ages, valid_age) checks a whole list and reports every bad entry.

Use the least powerful abstraction that does the job. If your steps don't depend on each other, an applicative gives you more: parallelism, error accumulation, static analysis.

12.4Laws, and Composition

Applicative laws, in terms of map2 and unit:

map2(unit(()), fa, (_, a) ↦ a) == fa                 left identity
map2(fa, unit(()), (a, _) ↦ a) == fa                 right identity
product(product(fa, fb), fc) ≅ product(fa, product(fb, fc))   associativity (up to tuple nesting)

Identity and associativity once more: a monoid, at one more level of abstraction.

And unlike monads, applicatives compose. If F and G are applicatives, so is F<G<_>>:

template <typename K1, typename K2> struct ComposeK {
    template <typename A> using F = typename K1::template F<typename K2::template F<A>>;
};

template <typename K1, typename K2> struct Applicative<ComposeK<K1, K2>> {
    template <typename A> static auto unit(A a) {
        return Applicative<K1>::unit(Applicative<K2>::unit(a));
    }
    template <typename FGA, typename FGB, typename Fn>
    static auto map2(const FGA& fga, const FGB& fgb, Fn f) {
        using GA = typename FGA::value_type;
        using GB = typename FGB::value_type;
        return Applicative<K1>::map2(fga, fgb, [f](const GA& ga, const GB& gb) {
            return Applicative<K2>::map2(ga, gb, f);       // combine inner layer inside outer layer
        });
    }
};

ComposeK<OptionalK, ValidatedK<std::string>> is an applicative for "maybe present, and if present, validated" with no new code. A composition of Par and Validated would give "validate many inputs in parallel, collecting all errors".

12.5Traverse: Beyond Vectors

So far traverse walks a vector. But you can traverse an optional, a tree, a map's values. The idea has two dimensions of generality: the structure being walked, and the applicative effect applied at each element.

StructureEffectMeaning
vectoroptionalparse every item; fail if any fails
vectorValidatedcheck every item; report all failures
TreeParprocess every node in parallel, keep the tree shape
map<K, _>futurefetch a value for every key concurrently
optionalexpectedvalidate an optional field only if present

For a rose tree, each node has a value and a vector of children:

template <typename A> struct Tree { A head; std::vector<Tree> children; };

template <typename K, typename A, typename Fn,
          typename B = typename std::invoke_result_t<Fn, const A&>::value_type>
auto traverse_tree(const Tree<A>& t, Fn f) -> typename K::template F<Tree<B>> {
    auto kids = traverse<K>(t.children, [f](const Tree<A>& c) -> typename K::template F<Tree<B>> {
        return traverse_tree<K>(c, f);
    });
    return Applicative<K>::map2(f(t.head), kids,
        [](const B& b, std::vector<Tree<B>> cs) { return Tree<B>{b, cs}; });
}

Apply f to the head, traverse the children (reusing vector's traverse), and rebuild the node with map2. The shape is always preserved: a tree comes back as a tree with the same shape, or the effect says why not. (A recursive function needs an explicit return type in C++, hence the trailing ->.)

A traverse with an applicative effect is also called "map with an effect". And sequence (traverse with the identity function) swaps the layers: vector<optional<A>> becomes optional<vector<A>>, a map<K, future<V>> becomes future<map<K, V>>.

Write traverse_opt<K>(optional<A>, f), returning K::F<optional<B>>.

Show solution
template <typename K, typename A, typename Fn>
auto traverse_opt(const std::optional<A>& oa, Fn f) {
    using B = typename std::invoke_result_t<Fn, const A&>::value_type;
    if (!oa) return Applicative<K>::unit(std::optional<B>{});        // nothing to do: just wrap
    return map<K>(f(*oa), [](const B& b) { return std::optional<B>(b); });
}

Empty stays empty (wrapped in the effect); a value gets f applied and is rewrapped. map here is derived from map2 and unit.

12.6Traverse Generalises Map and Fold

Two surprising facts:

map is traverse with no effect. Use the identity applicative (Id<A> from Chapter 11) and traverse is just map.

fold_map is traverse with a monoid. Every monoid gives an applicative that ignores its value type, called Const: unit is the monoid's empty, and map2 is its combine. Traversing with it accumulates a monoid value across the structure, which is exactly fold_map.

And with the State applicative, traverse can carry state across any structure. Numbering every element, for a vector or a tree, with the same labelling function:

template <typename A> auto label = [](const A& a) {
    return State<int, std::pair<A, int>>{[a](int i) { return std::pair{std::pair{a, i}, i + 1}; }};
};

traverse<StateK<int>>(std::vector<std::string>{"a", "b", "c"}, label<std::string>).run(0);
// ({("a",0), ("b",1), ("c",2)}, 3)

traverse_tree<StateK<int>>(char_tree, label<char>).run(0);
// every node numbered in pre-order, tree shape unchanged

One function, written once, working across structures and effects. That's the payoff of Part III.

Applicative functor
unit + map2 with identity and associativity laws. Combines independent effects.
Validated
An applicative like expected that accumulates errors instead of stopping at the first.
Traverse
Walking a structure with an applicative effect, keeping its shape.
Const applicative
An applicative built from a monoid, ignoring its value type; turns traverse into fold_map.
  • Applicative = unit + map2. Every monad is one; not the other way round.
  • Applicative steps are fixed in advance, so they can run in parallel or accumulate errors.
  • Validated reports every error; use it for independent checks.
  • Applicatives compose (ComposeK); monads don't.
  • traverse is generic in both structure and effect, and subsumes map and fold_map.
