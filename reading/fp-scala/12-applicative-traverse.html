Applicative & Traversable

Most of the functions we derived from Monad only ever used map2 and unit. Making those the primitives gives a weaker abstraction, Applicative, with more instances: validation that collects every error, applicatives that compose, and a traverse that works over any data structure.

12.1A Weaker Interface

Look back at the Monad trait. sequence, traverse and replicateM were written using only map2 and unit, never flatMap directly. So split it out:

trait Applicative[F[_]] extends Functor[F]:
  def unit[A](a: => A): F[A]

  extension [A](fa: F[A])
    def map2[B, C](fb: F[B])(f: (A, B) => C): F[C]

    def map[B](f: A => B): F[B] =
      fa.map2(unit(()))((a, _) => f(a))

    def product[B](fb: F[B]): F[(A, B)] =
      fa.map2(fb)((_, _))

  def traverse[A, B](as: List[A])(f: A => F[B]): F[List[B]] =
    as.foldRight(unit(List.empty[B]))((a, acc) => f(a).map2(acc)(_ :: _))

  def sequence[A](fas: List[F[A]]): F[List[A]] = traverse(fas)(identity)

trait Monad[F[_]] extends Applicative[F]:
  extension [A](fa: F[A])
    def flatMap[B](f: A => F[B]): F[B]
    override def map2[B, C](fb: F[B])(f: (A, B) => C): F[C] =
      fa.flatMap(a => fb.map(b => f(a, b)))

Every monad is an applicative functor. Not every applicative is a monad. Why would we want the weaker one?

12.2The Real Difference

// Monad: the second computation is CHOSEN using the first result
fa.flatMap(a => if a > 0 then fb else fc)

// Applicative: both computations are FIXED up front; only the values are combined
fa.map2(fb)((a, b) => a + b)

With map2, the structure of the computation is known before anything runs. With flatMap, it's only known as it runs. That gives each side something:

  • Monad: more power for the user. Later steps can depend on earlier results.
  • Applicative: more freedom for the implementer. Since steps are independent, an applicative can run them in parallel, inspect the whole structure ahead of time, or keep going after a failure.
A monadic program is a conversation: what you ask next depends on the answer you just got. An applicative program is a printed form: every question is on the page before anyone answers. You can't adapt a form to earlier answers, but you can hand page 1 and page 2 to two people at once, and you can list every unanswered question at the end.

Parsers make it concrete. An applicative parser is a fixed grammar: name ** age ** email. A monadic parser can read a header and choose a format, which is more expressive. But applicative parsers can be analysed and optimised before running, which monadic ones can't, because the next parser is hidden inside a function.

12.3Validation: Collecting Every Error

Recall the form from Chapter 4. Either's flatMap stops at the first error, so a user with a bad name and a bad age only hears about the name. The fields are independent, so we don't need flatMap. We need an applicative that collects errors:

enum Validated[+E, +A]:
  case Valid(get: A)
  case Invalid(errors: List[E])    // keep all of them

given validatedApplicative[E]: Applicative[[x] =>> Validated[E, x]] with
  def unit[A](a: => A) = Validated.Valid(a)
  extension [A](fa: Validated[E, A])
    override def map2[B, C](fb: Validated[E, B])(f: (A, B) => C): Validated[E, C] =
      (fa, fb) match
        case (Validated.Valid(a), Validated.Valid(b))       => Validated.Valid(f(a, b))
        case (Validated.Invalid(e1), Validated.Invalid(e2)) => Validated.Invalid(e1 ++ e2)
        case (e @ Validated.Invalid(_), _)                  => e
        case (_, e @ Validated.Invalid(_))                  => e

The case with two Invalids is the point: both error lists are kept. This would break the monad laws if we also defined a flatMap (which can't know the second step's errors without the first's value), so Validated is an applicative but deliberately not a monad.

import Validated.*

def validName(n: String): Validated[String, String] =
  if n.isBlank then Invalid(List("name is empty")) else Valid(n)

def validAge(a: Int): Validated[String, Int] =
  if a < 0 || a > 150 then Invalid(List(s"age $a out of range")) else Valid(a)

def validEmail(e: String): Validated[String, String] =
  if e.contains("@") then Valid(e) else Invalid(List(s"bad email '$e'"))

case class User(name: String, age: Int, email: String)

def validUser(n: String, a: Int, e: String): Validated[String, User] =
  validName(n).map2(validAge(a))((_, _)).map2(validEmail(e)) { case ((n, a), e) => User(n, a, e) }

validUser("", -5, "nope")
// Invalid(List("name is empty", "age -5 out of range", "bad email 'nope'"))

All three errors, in one pass. This is what form validation and config loading should do, and it's why the cats library ships Validated next to Either.

Use the least powerful abstraction that does the job. If your steps don't depend on each other, an applicative gives you more: parallelism, error accumulation, static analysis.

12.4Applicative Laws and Composition

The laws, in terms of map2 and unit:

unit(()).map2(fa)((_, a) => a) == fa                     // left identity
fa.map2(unit(()))((a, _) => a) == fa                     // right identity
fa.product(fb).product(fc) == fa.product(fb.product(fc))  // associativity (up to tuple nesting)

Identity and associativity again: a monoid, at one more level of abstraction.

And unlike monads, applicatives compose. If F and G are applicatives, so is F[G[_]]:

def compose[F[_], G[_]](F: Applicative[F], G: Applicative[G]): Applicative[[x] =>> F[G[x]]] =
  new:
    def unit[A](a: => A) = F.unit(G.unit(a))
    extension [A](fga: F[G[A]])
      override def map2[B, C](fgb: F[G[B]])(f: (A, B) => C) =
        F.map2(fga)(fgb)((ga, gb) => G.map2(ga)(gb)(f))

(F.map2(x)(y)(f) is the explicit way to call an extension method from a specific instance.) For example, Par composed with Validated gives "validate many inputs in parallel, collecting all errors" without writing anything new.

12.5Traverse: Beyond Lists

So far, traverse works on List. But nothing about it is specific to lists. You can traverse a tree, an Option, a Map's values. Abstract over the container too:

trait Traverse[F[_]] extends Functor[F], Foldable[F]:
  extension [A](fa: F[A])
    def traverse[G[_]: Applicative, B](f: A => G[B]): G[F[B]]

  extension [G[_]: Applicative, A](fga: F[G[A]])
    def sequence: G[F[A]] = fga.traverse(ga => ga)

G[_]: Applicative is shorthand for "and a using Applicative[G] parameter". So traverse has two dimensions of generality: the structure being walked (F), and the effect applied at each element (G). Some combinations:

F (structure)G (effect)Meaning
ListOptionparse every item; fail if any fails
ListValidatedcheck every item; report all failures
TreeParprocess every node in parallel, keep the tree shape
Map[K, _]Future / IOfetch a value for every key concurrently
OptionEithervalidate an optional field only if present

And sequence swaps the layers: List[Option[A]] becomes Option[List[A]], a Map[K, Future[V]] becomes Future[Map[K, V]].

Write Traverse instances for Option and for a rose tree case class Tree[+A](head: A, tail: List[Tree[A]]). You only need traverse; assume map and the fold methods are filled in.

Show solution
// Option: if empty, there's nothing to do but wrap; otherwise apply f and rewrap
extension [A](oa: Option[A])
  def traverse[G[_], B](f: A => G[B])(using G: Applicative[G]): G[Option[B]] =
    oa match
      case Some(a) => f(a).map(Some(_))
      case None    => G.unit(None)

// Tree: apply f to the head, traverse the children (a List of Trees), rebuild
extension [A](ta: Tree[A])
  def traverse[G[_], B](f: A => G[B])(using G: Applicative[G]): G[Tree[B]] =
    f(ta.head).map2(G.traverse(ta.tail)(t => t.traverse(f)))(Tree(_, _))

The structure is always preserved: a Some stays a Some, the tree keeps its shape. Traverse is "map with an effect".

12.6Traverse Generalises Map and Fold

Two surprising facts:

map is traverse with no effect. Use the identity "applicative" Id[x] = x: fa.traverse[Id, B](f) is just fa.map(f). So every Traverse is a Functor.

foldMap is traverse with a monoid. Every monoid gives an applicative that ignores its type parameter: Const[M, x] = M, with unit = M.empty and map2 = M.combine. Traversing with it accumulates a monoid value across the structure, which is foldMap. So every Traverse is a Foldable.

And with the State applicative, traverse can carry state across a structure: number every node of a tree, or zip it with a list.

// label each element with its index, for ANY traversable structure
extension [F[_]: Traverse, A](fa: F[A])
  def zipWithIndex: F[(A, Int)] =
    fa.traverse[[x] =>> State[Int, x], (A, Int)](a =>
      for
        i <- State.get[Int]
        _ <- State.set(i + 1)
      yield (a, i)
    ).run(0)(0)

One function, written once, and it works for lists, trees, options and maps. That's the payoff of Part III.

Validated
An applicative like Either that accumulates errors instead of stopping at the first.
Traverse
A type class for structures you can walk with an applicative effect, keeping their shape.

Shorthand for a using Applicative[G] parameter.

  • Applicative = unit + map2. Every monad is one; not the other way round.
  • Applicative steps are fixed in advance, so they can run in parallel or accumulate errors.
  • Validated collects all errors; use it for independent checks.
  • Applicatives compose; monads don't.
  • traverse generalises over both the structure and the effect, and subsumes map and foldMap.
